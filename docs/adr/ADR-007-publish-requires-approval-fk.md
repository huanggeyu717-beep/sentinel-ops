# ADR-007: 发布必须靠外键强制, 而不是靠应用层自觉

日期: 2026-08-07 (W3 开工前评审)
状态: 已采纳

## 背景

`CLAUDE.md` 不变量 1: "LLM 永远没有副作用执行权限; publish 必须存在 approvals 记录
(**DB 层校验**)"。

W3 开工前检查发现, 这句话里的"DB 层校验"目前是空的。`policy_versions` 有一列 `status`,
发布就是把它改成 `'published'`; `approvals` 表与它之间没有任何强制关联。任何一条 SQL
都能直接把状态改成已发布。真正在拦的只有应用层代码里的一个判断 —— 而应用层代码可以被
绕过, 也可能在某次重构里被人顺手删掉, **删掉之后没有任何测试会红**。

这与 W1 的 ruff 红灯 (声明用 strict 实际没开)、W2 的 mypy 空转 (写在文档里但不在 CI 跑)
是同一类问题: **声明的和执行的不是一回事**。区别是这次踩在项目最核心的主张上 ——
"模型永不直接执行副作用, 必须人工审批"如果只靠应用层自觉, 这句话就不成立。

## 决策

**一、把"发布"这个动作变成一张独立的表, 审批 id 设为 NOT NULL 外键。**

```sql
CREATE TABLE policy_publications (
    policy_version_id bigint NOT NULL REFERENCES policy_versions(id),
    approval_id       bigint NOT NULL REFERENCES approvals(id),   -- 关键
    ...
);
CREATE UNIQUE INDEX policy_publications_one_active
    ON policy_publications (policy_id) WHERE revoked_at IS NULL;
```

想发布就必须插入这一行, 而插入必须提供一个真实存在的 approval id。
**没有审批记录, 这一行在物理上插不进去**, 与应用代码写成什么样无关。

**二、划一条判断线: 不变量下沉到数据库, 可能有例外的业务规则留在应用层。**

| 规则 | 放哪 | 理由 |
|---|---|---|
| 发布必须有审批 | 数据库 (NOT NULL 外键) | 永远不该有例外 |
| 一条策略同时只有一个生效版本 | 数据库 (partial unique index) | 永远不该有例外 |
| 不得自己批自己 | **数据库 CHECK + 应用层 403** | 不变量, 但需要可读的错误信息 |
| 跨区派单需显式放行 | 应用层 (SPEC-003 决策 7) | **本来就有例外**, 且例外要留痕 |
| 含通知的策略冷却下限 300 秒 | 应用层 (静态验证器) | 是校验建议, 阈值会调 |

"不得自己批自己"两层都做: 数据库那行 CHECK 是兜底, 成本只有一行;
应用层负责先返回 403 并写审计, 因为数据库约束被违反时抛出来的是 IntegrityError,
对用户没有任何意义。**数据库保证它不可能发生, 应用层保证它发生时人话说得清楚。**

## 考虑过但没选的方案

**数据库触发器。** 在 `policy_versions` 上挂一个 BEFORE UPDATE 触发器,
状态改成 published 时去查 approvals。效果等价, 但:

- 触发器在 Alembic 里手写麻烦, 写 downgrade 更麻烦, 而本项目所有迁移都手写
  (ADR-006: 无 ORM 模型, autogenerate 用不了);
- **触发器是看不见的逻辑** —— 读表结构的人不会知道它存在, 排查问题时要先想到"是不是
  有触发器"才查得到。外键写在表定义里, 谁读谁看见;
- 触发器里的查询逻辑本身也可能写错, 而外键约束是数据库自己实现的, 不会写错。

**只在应用层判断 (维持现状)。** 就是当前状态, 已经证明是空的。

**给 `policy_versions` 加一列 `approval_id`。** 不用新建表就能做到 NOT NULL 外键。
没选是因为它把"这一版加工到哪一步"和"现在线上跑的是哪一版"两个不同的事实塞进同一行,
而这两件事的生命周期不同: 版本不可变, 发布却要能撤销、能回滚、能被新版本取代。
分成两张表之后, 回滚就是"撤销当前发布 + 重新发布旧版本, 复用它当年那条审批记录",
不需要改任何历史行。

## 代价

- 多一张表, 查询"当前生效版本"要多一次 join。可接受: 生效策略集在进程内有缓存,
  发布/撤销时失效, 不是热路径。
- 迁移 `0007` 要写四段 DDL 与对应的 downgrade。
- 数据库约束被违反时抛出的异常需要在应用层翻译成人话, 否则用户看到的是 IntegrityError。

## 后果

这是本项目"约束下沉到数据库"的第三次应用, 三次连起来是一条完整的主线:

1. **W1** —— 幂等唯一键 `(device_id, 业务标识, ts)`, 重放不产生重复行;
2. **W2** —— 事故 partial unique index `(sensor_id) WHERE status <> 'resolved'`,
   同一传感器不会开出两个未解决事故;
3. **W3** —— 发布的审批外键, 没批过就发不出去。

一句话: **凡是必须永远成立的规则, 由数据库保证, 不靠代码自觉。**

验收里有五条专门证明这一点的测试 (SPEC-006 验收 11–15): 绕过应用层直接写数据库,
看约束拦不拦得住。这类测试比端到端流程测试更值钱 —— 端到端证明的是"正常路径能走通",
这几条证明的是"异常路径走不通"。
