**已修：CI 的 `engine` job 红灯（2026-08-05）**
- 根因：CI 每次都 `pip install ruff` 装最新版，开发机上装的是旧版。ruff 0.16
  扩大了「默认规则集」，同一份代码被新版判出 11 处问题 —— 代码没变，CI 结果变了。
  当初的猜测（"CI 的 ruff 版本更新引入了新默认规则"）是对的。
- 修复三件事：
  1. **锁版本**：CI 与 `apps/api/pyproject.toml` 统一 `ruff==0.16.1`；
  2. **显式声明规则集**：新增仓库根 `ruff.toml`（`select = E/W/F/I/UP/B/SIM/RUF`，
     `line-length=100`，`target-version=py312`），不再依赖工具默认值；
     中文全角标点触发的 `RUF001/002/003` 整体 ignore；
  3. **单一配置源**：删掉 `apps/api/pyproject.toml` 里的 `[tool.ruff]`
     （ruff 按「离文件最近的配置」生效，分散配置会让不同目录悄悄用不同规则）。
- 顺带修掉的 11 处：嵌套 `with`/`if` 合并、`typing.Iterator` → `collections.abc`、
  `Union[A,B]` → `A | B`、`__all__` 排序、导入排序、5 处 SQL 长行折行。
  **全部是写法调整，没有改任何业务逻辑。**
- 取舍记录见 `docs/adr/ADR-005-pin-lint-toolchain.md`。
- 本地已用与 CI 完全一致的命令复跑：ruff `All checks passed`，
  测试 24 条全绿（policy_engine 5 / device-sim 6 / api 13，api 跑在真实 Postgres 16 上）。
- 顺带做了一件结构性的事：**CI 的具体命令全部下沉到 `scripts/ci/`**，
  `.github/workflows/ci.yml` 只剩"准备环境 + 调用脚本"。
  `make lint` / `make test` 和 CI 从此执行**同一份文件**，不再是两份会跑偏的命令。
- 换机器 / 新对话接手时：先 `make dev-tools` 对齐工具链版本，
  再 `make lint`（版本不一致会直接报错并告诉你该装哪个版本）。
- 新增根目录 `pytest.ini`：**跑测试不再需要先 `pip install -e packages/policy_engine`**。
  之前那步一旦本机换了 Python 解释器就失效，报的却是 `ModuleNotFoundError`，
  看着像代码坏了、其实是环境没配好。CI 里仍保留 editable 安装，那是在验证打包本身没坏。
- **本机 Python 已对齐到 3.12**（2026-08-05）。此前 brew 装的是 3.14，而 CI 与两个
  Dockerfile 都是 3.12 —— 属于同一类"本机 ≠ CI"风险，只是没人拦：
  `requires-python = ">=3.12"` 是下限不是固定值，3.14 一路畅通。
  做法：项目内建 venv（`.venv/`，已在 .gitignore），用 brew 的 python@3.12 建。
  **每开一个新终端进项目要先 `source .venv/bin/activate`**，`make lint` 版本不符会提醒。
- **遗留风险：`3.12` 这个数字在仓库里硬写了 4 遍** —— `ci.yml` 两处
  （engine / api job）、`apps/api/Dockerfile`、`apps/device-sim/Dockerfile`。
  将来升级 Python 时漏改任何一处都不会报错（典型漏网场景：漏改 device-sim 的
  Dockerfile，CI 四条全绿，但模拟器容器跑着和别处不同的 Python）。
  待办：把版本收敛成单一事实源（`.python-version` + CI 引用它 + 校验脚本比对
  两个 Dockerfile），让不一致当场变成 CI 红灯。同 ADR-005 的思路，尚未实施。

**已完成：迁移改用 Alembic（2026-08-06）**
- 版本图代替文件名排序。此前两个人各加一个 `0003_` 不会冲突报错，只会静默乱套。
- **基线不翻写**：`0001_baseline` 直接执行 W1 那份 `0001_initial.sql` 原文，
  不手抄成 `op.create_table(...)`。24 张表抄漏一个约束不会有任何报错。
  已验证：全新库用 Alembic 建出的表结构，与 W1 老迁移器建出的**逐字一致**（472 行 DDL）。
- **老库平滑接管**：启动时若发现"有 `schema_migrations` 台账、但没有 `alembic_version`"，
  就按台账 stamp 对应版本，不执行任何建表语句。你开发机上已有的库不用重建。
- **保留启动时自动升级**，没有改成命令行 `alembic upgrade head`。官方教程都教后者，
  但那会变成"只有 Docker 里能建表"，本地和 CI 又得各写一套。
- 迁移用同步驱动 psycopg（多加一个依赖），应用运行时仍走 asyncpg。原因与代价见
  `docs/adr/ADR-006-alembic-migrations.md`。
- **autogenerate 用不了**：业务代码写原生 SQL，没有 ORM 模型，没有可比对的对象，
  迁移一律手写。这是选原生 SQL 时就付的账。
- Dockerfile 必须 COPY `alembic.ini` + `alembic/` + `migrations/` 三者，少一个容器启动即挂。
  已就地注释，并用"照 COPY 清单复刻目录"的方式验证过（含故意漏 COPY 的反向验证）。
- 新增命令：`make migrate` / `make migrate-status` / `make migrate-down` /
  `make migrate-new id=0003_xxx m="说明"`。
- 验证：全新库建表、老库接管、重复执行幂等、downgrade 一步再升回、
  24 条测试全绿（含用全新库和老库各跑一遍 API 测试）、lint 通过。

**已完成：事故生命周期 + RFID 接单（SPEC-003，2026-08-06）**
- 状态机 open → assigned → acknowledged → resolved 落地在
  `services/incident_service.py`；推进全部用条件更新（`UPDATE ... WHERE status = 旧状态`），
  受影响行数为 0 即 409 —— 并发两次"解决"只有一个成功（有专门测试）。
- 每次流转在同一请求事务里写 incident_events（时间线）+ audit_log（审计）。
- 「转湿即开事故」是 W2 硬编码占位，W3 由 Policy 引擎接管后整体删除。
  去重靠 partial unique index（`(sensor_id) WHERE status <> 'resolved'`），
  持续报湿只累加 `sensor_still_wet` 时间线。
- RFID 接单复用 `/ingest`（不新增接口）：卡→员工，取**刷卡设备所在区域**里最早的
  open/assigned 事故 → acknowledged。找不到人/事故时刷卡照常落库（遥测事实不丢），
  返回 `matched: false` + 原因码（unknown_card / no_open_incident_in_zone /
  transition_conflict）。**刷卡不校验刷卡人属于哪个区**——见下方修订 2 的不对称设计。
- 自动解决是事件驱动的：干燥事件到达时距最后一条湿读数超过稳定窗口
  （`SENTINEL_AUTO_RESOLVE_DRY_SECONDS`，默认 300s）才关单，`resolved_by='auto_sensor_dry'`；
  人工解决记 `employee:{id}`（取 X-Actor 头，SPEC-004 JWT 落地后改从 token 取）。
  已知边界：传感器最后报干后彻底静默不会触发自动关单（周期上报的传感器不受影响，
  彻底静默会先变成心跳离线告警）。
- 迁移 `0003_incidents`（Alembic 手写 + downgrade，已验证降一步再升回）：
  assigned_at / resolved_by 两列 + 三个索引。
- 顺带：`requirements-dev.txt` 补上 mypy —— 此前 `make lint` 里的 mypy 步骤在全新 venv
  会直接 command not found。mypy 的完整配置见下方独立小节。

**已完成：SPEC-003 实现后评审的三条修订（2026-08-06）**

代码写完之后逐行读了一遍，发现三处该改的，都已落地（迁移 `0004_incident_ack_by`）：

1. **拆出 `acknowledged_by_employee_id`**。原实现用 `COALESCE` 把刷卡人回填进
   `assigned_employee_id`，信息没丢（时间线里有），但列表接口会让前端把
   "派给 Alex" 显示成 "Alex 已接单"，而实际到场的是 Bo。现在两个字段各记各的，
   还能统计"派单命中率"。
2. **派单按区域约束、刷卡不按区域约束**——这个不对称是刻意的，已从"实现细节"
   提升为 SPEC-003 的显式决策 7。派单默认只能派给同区员工（员工无区域也算跨区），
   否则 422；要跨区必须显式传 `allow_cross_zone=true`，此时审计日志记
   `cross_zone: true` 加双方 zone_id。刷卡则完全不看刷卡人属于哪个区。
   理由：安排工作按区域分工，紧急情况谁在现场谁上。
3. **允许改派**。原实现 `assign` 限定 `WHERE status = 'open'`，派出去就改不了，
   主管派错人只能等对方接单。放宽为 `status IN ('open','assigned')`，
   改派单独记 `reassigned` 事件，detail 带前后两个人。

另外 CC 自己加的一处（SPEC 里没写）：`X-Actor` 解析出的员工号会**回表验证**，
对不上就记空。因为这个请求头现在谁都能填，不验证的话脏 id 会撞外键。

**已完成：mypy 分档并纳入 CI（2026-08-06）**

- 起因：`CLAUDE.md` 写着 "mypy strict"，实际既没开 strict、也**根本不在 CI 里跑**——
  只有本人记得敲 `make lint` 时才检查，等于没有拦截作用。和 W1 的 ruff 红灯同源：
  **声明的和执行的不一致**。

  其中 74% 来自测试。测试是用完即弃的胶水代码，强制标注收益低；应用代码要被别人读、
  W3 还要往上接策略引擎，类型信息在那里才值钱。
- 严格档**逐模块打开**：白名单在 `mypy.ini`，补完一个模块的标注就加一个，
  任何时刻 `make lint` 都是绿的，不会出现"先红一大片，等以后慢慢还"。
  截至 2026-08-06，`apps/api/app` 与 `packages` 下的模块已全部补完并纳入。
- 坑：`strict = True` 只能写在全局小节，写进按模块的小节会被当成全局开关，
  把测试代码一起卷进去。所以 `mypy.ini` 里是逐条列出严格档包含的检查项。

- 补标注时真正有价值的是 5 处：SQLAlchemy 的 `scalar_one_or_none()` / `mappings()`
