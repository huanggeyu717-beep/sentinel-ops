**已修：CI 的 `engine` job 红灯（2026-08-05）**
- 根因：CI 每次都 `pip install ruff` 装最新版，开发机上装的是旧版。ruff 0.16
  扩大了「默认规则集」，同一份代码被新版判出 11 处问题 —— 代码没变，CI 结果变了。
  当初的猜测（"CI 的 ruff 版本更新引入了新默认规则"）是对的。
- 修复三件事：
  1. **锁版本**：CI 与 `apps/api/pyproject.toml` 统一 `ruff==0.16.1`；
  2. **显式声明规则集**：新增仓库根 `ruff.toml`（`select = E/W/F/I/UP/B/SIM/RUF`，
     `line-length=100`，`target-version=py312`），不再依赖工具默认值；
     中文全角标点触发的 `RUF001/002/003` 整体 ignore；
  3. **单一配置源**：删掉 `apps/api/pyproject.toml` 里的 `[tool.ruff]`
     （ruff 按「离文件最近的配置」生效，分散配置会让不同目录悄悄用不同规则）。
- 顺带修掉的 11 处：嵌套 `with`/`if` 合并、`typing.Iterator` → `collections.abc`、
  `Union[A,B]` → `A | B`、`__all__` 排序、导入排序、5 处 SQL 长行折行。
  **全部是写法调整，没有改任何业务逻辑。**
- 取舍记录见 `docs/adr/ADR-005-pin-lint-toolchain.md`。
- 本地已用与 CI 完全一致的命令复跑：ruff `All checks passed`，
  测试 24 条全绿（policy_engine 5 / device-sim 6 / api 13，api 跑在真实 Postgres 16 上）。
- 顺带做了一件结构性的事：**CI 的具体命令全部下沉到 `scripts/ci/`**，
  `.github/workflows/ci.yml` 只剩"准备环境 + 调用脚本"。
  `make lint` / `make test` 和 CI 从此执行**同一份文件**，不再是两份会跑偏的命令。
- 换机器 / 新对话接手时：先 `make dev-tools` 对齐工具链版本，
  再 `make lint`（版本不一致会直接报错并告诉你该装哪个版本）。
- 新增根目录 `pytest.ini`：**跑测试不再需要先 `pip install -e packages/policy_engine`**。
  之前那步一旦本机换了 Python 解释器就失效，报的却是 `ModuleNotFoundError`，
  看着像代码坏了、其实是环境没配好。CI 里仍保留 editable 安装，那是在验证打包本身没坏。
- **本机 Python 已对齐到 3.12**（2026-08-05）。此前 brew 装的是 3.14，而 CI 与两个
  Dockerfile 都是 3.12 —— 属于同一类"本机 ≠ CI"风险，只是没人拦：
  `requires-python = ">=3.12"` 是下限不是固定值，3.14 一路畅通。
  做法：项目内建 venv（`.venv/`，已在 .gitignore），用 brew 的 python@3.12 建。
  **每开一个新终端进项目要先 `source .venv/bin/activate`**，`make lint` 版本不符会提醒。
- **遗留风险：`3.12` 这个数字在仓库里硬写了 4 遍** —— `ci.yml` 两处
  （engine / api job）、`apps/api/Dockerfile`、`apps/device-sim/Dockerfile`。
  将来升级 Python 时漏改任何一处都不会报错（典型漏网场景：漏改 device-sim 的
  Dockerfile，CI 四条全绿，但模拟器容器跑着和别处不同的 Python）。
  待办：把版本收敛成单一事实源（`.python-version` + CI 引用它 + 校验脚本比对
  两个 Dockerfile），让不一致当场变成 CI 红灯。同 ADR-005 的思路，尚未实施。

**已完成：JWT 登录与 RBAC（SPEC-004，2026-08-07）**

- `users` 加 `employee_id` 可空外键指向 `employees`（迁移 `0005_users_employee_link`）。
  两张表原本互不关联，而 SPEC-003 的 actor 记 `employee:{id}`、`audit_log.user_id` 指
  `users.id`，这条缝一直被 `X-Actor` 占位符盖着。列**必须可空**：种子三个账号正好覆盖
  三种真实关系——admin 有账号但不是现场员工；Chris/Alex 有账号也绑员工；
  Bo Wang 只刷卡从不登录。设成必填的话，第一种和第三种都得靠编数据绕过去。
- token 走 **httpOnly + SameSite=Lax cookie**，同时接受 `Authorization: Bearer`
  作为备用通道（`/docs` 的 Authorize 按钮和 curl 只会走请求头，而"`/docs` 可交互调用"
  是 W1 就立的验收项）。登录响应体**不回 token 原文**，否则"JavaScript 读不到"这个
  前提是自己破坏掉的。
- `X-Actor` 请求头**整体删除**，不留兼容。用 grep 断言零残留。
- **跨区派单收归 manager**。实现后评审时发现一个死路：operator 拿到 422
  「要跨区请传 allow_cross_zone=true」，照做又得到 403。因为权限检查排在业务确认
  后面。改成**权限先判、业务后判**——没资格的人根本看不到那句提示。
- **登录限流按来源 IP，不按账号**。按账号锁本身是漏洞：攻击者故意去错几次
  `chris@example.com` 就能把真正的 Chris 关在门外，限流反过来成了拒绝服务的工具。
  只计失败，登录成功即清账。默认**不信 `X-Forwarded-For`**（客户端可以随便写，
  直接采信等于把限流关掉）。计数在进程内存，有 IP 数上界，见
  `services/rate_limit.py` 里写明的已知边界。
- **两条登录失败路径的耗时拉平**。"不区分邮箱不存在与密码不对"只做到一半是没用的：
  实测邮箱不存在时 0.002ms、密码错时 269ms，差约 15 万倍，攻击者靠计时就能枚举出
  哪些邮箱注册过。修法是邮箱不存在时也拿一个预置假哈希跑一次 bcrypt 做无用功。

- `GET /drills/scenarios` / `POST /drills/{scenario}` / `GET /drills/{drill_id}`：
  网页上一键触发场景回放。事件投递**不拼 SQL 也不 HTTP 自调**，而是调与 `/ingest`
  同一个 service 函数并复用同一个 pydantic 模型校验——演练与真机走同一份校验逻辑。
- 演练状态放内存，不进 `agent_tasks`（那张表有审计/重试/死信语义，演练是一次性演示
  动作）。只保留最近 N 次，超出丢最旧——内存里的东西必须有上界。代价（重启即丢）
  写在响应的 `note` 字段里。
- **同一场景不允许并发**，重复启动 409。`start_drill` 刻意是**同步函数**：
  asyncio 单线程事件循环里，同步函数的"检查—登记"之间不会被别的协程插进来，
  这就是那把锁。改成 async 就破了，所以专门写了一条断言它不是协程的回归测试。
