- 根因：CI 每次都 `pip install ruff` 装最新版，开发机上装的是旧版。ruff 0.16
  扩大了「默认规则集」，同一份代码被新版判出 11 处问题 —— 代码没变，CI 结果变了。
  当初的猜测（"CI 的 ruff 版本更新引入了新默认规则"）是对的。
- 修复三件事：
  1. **锁版本**：CI 与 `apps/api/pyproject.toml` 统一 `ruff==0.16.1`；
  2. **显式声明规则集**：新增仓库根 `ruff.toml`（`select = E/W/F/I/UP/B/SIM/RUF`，
     `line-length=100`，`target-version=py312`），不再依赖工具默认值；
     中文全角标点触发的 `RUF001/002/003` 整体 ignore；
  3. **单一配置源**：删掉 `apps/api/pyproject.toml` 里的 `[tool.ruff]`
     （ruff 按「离文件最近的配置」生效，分散配置会让不同目录悄悄用不同规则）。
- 顺带修掉的 11 处：嵌套 `with`/`if` 合并、`typing.Iterator` → `collections.abc`、
  `Union[A,B]` → `A | B`、`__all__` 排序、导入排序、5 处 SQL 长行折行。
  **全部是写法调整，没有改任何业务逻辑。**
- 取舍记录见 `docs/adr/ADR-005-pin-lint-toolchain.md`。
- 本地已用与 CI 完全一致的命令复跑：ruff `All checks passed`，
  测试 24 条全绿（policy_engine 5 / device-sim 6 / api 13，api 跑在真实 Postgres 16 上）。
- 顺带做了一件结构性的事：**CI 的具体命令全部下沉到 `scripts/ci/`**，
  `.github/workflows/ci.yml` 只剩"准备环境 + 调用脚本"。
  `make lint` / `make test` 和 CI 从此执行**同一份文件**，不再是两份会跑偏的命令。
- 换机器 / 新对话接手时：先 `make dev-tools` 对齐工具链版本，
  再 `make lint`（版本不一致会直接报错并告诉你该装哪个版本）。
- 新增根目录 `pytest.ini`：**跑测试不再需要先 `pip install -e packages/policy_engine`**。
  之前那步一旦本机换了 Python 解释器就失效，报的却是 `ModuleNotFoundError`，
  看着像代码坏了、其实是环境没配好。CI 里仍保留 editable 安装，那是在验证打包本身没坏。
- **本机 Python 已对齐到 3.12**（2026-08-05）。此前 brew 装的是 3.14，而 CI 与两个
  Dockerfile 都是 3.12 —— 属于同一类"本机 ≠ CI"风险，只是没人拦：
  `requires-python = ">=3.12"` 是下限不是固定值，3.14 一路畅通。
  做法：项目内建 venv（`.venv/`，已在 .gitignore），用 brew 的 python@3.12 建。
  **每开一个新终端进项目要先 `source .venv/bin/activate`**，`make lint` 版本不符会提醒。
- **遗留风险：`3.12` 这个数字在仓库里硬写了 4 遍** —— `ci.yml` 两处
  （engine / api job）、`apps/api/Dockerfile`、`apps/device-sim/Dockerfile`。
  将来升级 Python 时漏改任何一处都不会报错（典型漏网场景：漏改 device-sim 的
  Dockerfile，CI 四条全绿，但模拟器容器跑着和别处不同的 Python）。
  待办：把版本收敛成单一事实源（`.python-version` + CI 引用它 + 校验脚本比对

**已完成：JWT 登录与 RBAC（SPEC-004，2026-08-07）**

- `users` 加 `employee_id` 可空外键指向 `employees`（迁移 `0005_users_employee_link`）。
  两张表原本互不关联，而 SPEC-003 的 actor 记 `employee:{id}`、`audit_log.user_id` 指
  `users.id`，这条缝一直被 `X-Actor` 占位符盖着。列**必须可空**：种子三个账号正好覆盖
  三种真实关系——admin 有账号但不是现场员工；Chris/Alex 有账号也绑员工；
  Bo Wang 只刷卡从不登录。设成必填的话，第一种和第三种都得靠编数据绕过去。
- token 走 **httpOnly + SameSite=Lax cookie**，同时接受 `Authorization: Bearer`
  作为备用通道（`/docs` 的 Authorize 按钮和 curl 只会走请求头，而"`/docs` 可交互调用"
  是 W1 就立的验收项）。登录响应体**不回 token 原文**，否则"JavaScript 读不到"这个
  前提是自己破坏掉的。
- `X-Actor` 请求头**整体删除**，不留兼容。用 grep 断言零残留。
- **跨区派单收归 manager**。实现后评审时发现一个死路：operator 拿到 422
  「要跨区请传 allow_cross_zone=true」，照做又得到 403。因为权限检查排在业务确认
  后面。改成**权限先判、业务后判**——没资格的人根本看不到那句提示。
- **登录限流按来源 IP，不按账号**。按账号锁本身是漏洞：攻击者故意去错几次
  `chris@example.com` 就能把真正的 Chris 关在门外，限流反过来成了拒绝服务的工具。
  只计失败，登录成功即清账。默认**不信 `X-Forwarded-For`**（客户端可以随便写，
  直接采信等于把限流关掉）。计数在进程内存，有 IP 数上界，见
  `services/rate_limit.py` 里写明的已知边界。
- **两条登录失败路径的耗时拉平**。"不区分邮箱不存在与密码不对"只做到一半是没用的：
  实测邮箱不存在时 0.002ms、密码错时 269ms，差约 15 万倍，攻击者靠计时就能枚举出
  哪些邮箱注册过。修法是邮箱不存在时也拿一个预置假哈希跑一次 bcrypt 做无用功。

  原系统把 `sensorZoneMap` 写成前端常量、刷新即丢，这正是本项目要修的毛病之一。
- `GET /drills/scenarios` / `POST /drills/{scenario}` / `GET /drills/{drill_id}`：
  网页上一键触发场景回放。事件投递**不拼 SQL 也不 HTTP 自调**，而是调与 `/ingest`
  同一个 service 函数并复用同一个 pydantic 模型校验——演练与真机走同一份校验逻辑。
- 演练状态放内存，不进 `agent_tasks`（那张表有审计/重试/死信语义，演练是一次性演示
  动作）。只保留最近 N 次，超出丢最旧——内存里的东西必须有上界。代价（重启即丢）
  写在响应的 `note` 字段里。
- **同一场景不允许并发**，重复启动 409。`start_drill` 刻意是**同步函数**：
  asyncio 单线程事件循环里，同步函数的"检查—登记"之间不会被别的协程插进来，
  这就是那把锁。改成 async 就破了，所以专门写了一条断言它不是协程的回归测试。

## 工作方法（W1–W3 三周跑通，W4 沿用）

两个 AI 分工：**评审方**（写 SPEC 与文档、复核代码）与 **CC**（Claude Code，写代码）。
一周切成两到三段，每段走完整一轮：

1. **评审方先把 SPEC 逐条评审**，有问题当场说，讨论定稿。SPEC 定稿之后才动手。
2. **评审方写一段 prompt 给 CC。** prompt **只写 SPEC 里没有的东西**——文件边界、
   报告格式、易错点指路——**不复述 SPEC 内容**。复述一遍就是同一个事实存两份，
   改了 SPEC 这边不跟着改就走散了。
3. **CC 交完成报告**，本人贴回评审方。
4. **评审方逐行复核代码，不只信报告。** 前两周有两次报告与实际代码对不上，
   都是看代码才发现的。
5. **复核的结论必须是跑出来的，不是推断出来的。** W3 有一次评审方"看代码看出一个 bug"，
   写脚本一跑发现根本不存在——推理链条看着无懈可击，事实是错的。
   凡是"我觉得这里有问题"，先写个探针跑一遍再说。
6. **关键不变量要做变异测试**：把实现故意改坏一次，看对应测试会不会红。
   W3 抓到过一条测试，注释写着"若实现把两个键合并这条会红"，实际把键合并之后
   **它照样绿**——光读代码看不出来，必须动手破坏一次。
   这一条是 W3 最值钱的产出，W4 继续做。

几条已经吃过亏的小规矩：

- **报数字必须带上产生它的配置。** W3 有一次 CC 报"回放触发 65 次"，评审方按另一种
  作用域算出 35 次，试了几种配置才对上——它用的是 zone 分桶但没写。
- **CC 的报告里必须有一节"与 SPEC 不一致的地方，逐条列出"。** 这条要求把"偏离"
  从错误变成了可以正大光明汇报的东西，W3 后半程 CC 开始能对 SPEC 提出有依据的异议，
  纠正过评审方两次。
- **CC 越界改动要主动报**，不擅自改冻结的文件；认为冻结文件里有真 bug 时先停下来说。

### 第三段：HTTP 路由 + SSE + Automation Studio

四个端点 + SSE，前端 `features/studio/`。几处关键决定：

- **SSE 从数据库尾随读**（0.3 秒轮询 `get_timeline`），不建内存事件总线——那会让
  "Trace 的事实源只有一个"作废，且任务与连接不在同一进程就失效。
  `id:` 发任务自己的 `seq`，`Last-Event-ID` 从那之后接着推；**`status` 快照事件不带 `id`**
  （占了 `seq` 会让续传漏东西）。
- **POST 自开事务、提交之后才 spawn**——后台协程的认领在新会话里，看不见未提交的行。
- **并发上界用"同步预留槽位"**：`reserve_task_slot()` 是无 `await` 的同步操作，
  单线程事件循环里不会被打断，所以上界是真的上界而不是"多数时候的上界"。
  手法与 SPEC-005 里 `start_drill` 刻意是同步函数完全一致（这条经验第二次用上）。
- **后台任务的强引用存模块级 set + `done_callback` discard**——`asyncio.create_task`
  返回的对象若无强引用可能在跑完前被垃圾回收，表现是任务随机消失、日志里什么都没有。
- 去重命中返回 **200 而不是 4xx**（用户明明什么都没等到，报"重复提交"会让人一头雾水）。

**容器里抓到一个真缺陷**：`apps/api/Dockerfile` 从没 COPY 过 `apps/device-sim/seed/`，
所以容器里每条 Agent 任务的 `simulate_policy` 都落死信，而宿主机测试全绿——
**这条路只有容器里才断**。已修。

**这已经是同一类的第三次**（W2 的 alembic 三件套、scenarios 目录、这次的 seed CSV），
但性质不同：前两次是**快炸**（漏了容器起不来），这次是**慢炸**（容器起得来、界面打得开，
只有当有人点"模拟"才断）。**CI 的 docker job 只有 `docker compose build`，从不启动、
从不调一次接口——它只拦得住快炸。** 待办见本章末尾。

**变异 21 的手法被实测推翻**：SPEC 原本沿用 W3 留下的设想"路由门在碰数据库之前就拒绝，
给一个不存在的版本号，有门 403、没门变 404"。实测不成立——`publish_version` 的
`has_permission` 排在读版本那句 SQL **之前**，拆掉路由门后 service 层照样查库前就 403。
**这不是缺陷，是纵深防御比当初设想的还早一层。** SPEC 已回填，并写明更结实的钉子
（断言"请求根本没走到 service"：替身记调用次数，有门为 0、没门为 1），留 W5/W6 换。

## W5 CI 盘点：每个 job 现在**实际**检查了什么（2026-08-10）

起因：`lint` 这道检查在 CI 里躺了四天什么都不干（defect-log 案例 5，教训二）。
既然一条检查可以这样躺着，就得把其余的也逐条翻一遍。
**下面写的是"它现在实际检查了什么"，不是"它应该检查什么"。**

盘完之后 CI 是五个 job：`lint` / `engine` / `api` / `docker` / `web`。

### lint（ruff + mypy，本次新拆出来的独立 job）

**实际检查**：ruff 扫 `packages apps/api apps/device-sim evals`；
mypy 扫 `apps/api packages/policy_engine packages/scenario evals`，
109 个源文件，严格档按 `mypy.ini` 白名单逐模块生效。装全量依赖，所以
**它现在是真的在检查类型**（W2 到 W5 之间它一条都没检查成）。

**拦不住**：

- **`scripts/dev/` 下 11 个 `.py` 不在任何 ruff 或 mypy 目标里** ——
  而 `record_cassettes.py` / `probe_*.py` 是**仓库里唯一会真花钱的代码**，
  `CLAUDE.md` 协作红线还专门要求临时脚本必须落在这个目录。
  最该被看一眼的地方，恰好一道静态检查都没有；
- **`apps/device-sim` 在 ruff 目标里、不在 mypy 目标里** ——
  它的类型从来没被检查过；
- **同一个 `packages/` 目录，ruff 按目录收、mypy 逐个点名**
  （`packages/policy_engine packages/scenario`）。将来出现第三个包时，
  ruff 收得到、mypy 收不到，而且不会有任何东西报错 ——
  正是 `test-unit.sh` 那句注释警告过的形状，只是换了个位置又长了一次；
- **`make lint-fix` 自己另抄了一份目标清单**（`ruff check --fix packages
  apps/api apps/device-sim evals`），是 CI 与本机之间**唯一一处会漂的地方**。
  `make lint` 调的是 `scripts/ci/lint.sh`，与 CI 同源，这一条成立；`lint-fix` 不是。

**按设计如此、不是缺陷**：`check-tool-versions.sh` 只在 `CI != true` 时跑。
它是本机护栏（确认本机 ruff 与锁定版本一致），CI 上不需要，因为 CI 自己装锁定版本。

**这份依赖贫瘠现在是一项被断言守着的资产**，不再只是一句 job 名字：

### docker（"镜像可构建"）

`docker compose build api device-sim`。

**实际检查**：两个 Dockerfile 能解析、基础镜像能拉、`pip install` 能装完，
以及**每一条 `COPY` 的源路径在构建上下文里存在**（缺一个 COPY 源，build 当场失败）。
这就是它拦得住"快炸"的原因，W2 的 alembic 三件套与 scenarios 目录都是这样被拦下的。

**拦不住**（三条，第一条已是记过的债）：

1. **根本没写的 `COPY` 行。** build 不知道代码需要什么。W4 的 seed CSV 就是这一种：
   build 全绿、容器起得来、界面打得开，只有有人点"模拟"才断。
   **这就是 defect-log 案例 5 教训一里的第 3 例**，它的对策（build 之后在容器里

2. **容器从不启动。** 迁移跑不跑得起来、`app.main` 能不能 import、CMD 对不对，

3. **`web` 与 `sim-replay` 两个 compose 服务从不 build。**
   `apps/web/Dockerfile` 在 CI 里一次都没有被构建过 —— 而 README 承诺的是

   `npm install` 现解现装 —— 镜像里的依赖版本与 CI 里的可以不同。

### web

`npm ci || npm install`、`npm run typecheck`、`npm run build`。

**拦不住**：

- **`npm ci || npm install` 这个 fallback 让锁文件形同虚设。**

   结论必须是跑出来的 —— 对付的就是这一件事。**这是整个项目的那条主线。**

4. **深度思考不是免费的**: 7/20 条即便把超时放宽到出厂 3 倍 (180 秒) 仍然超时 ——

## 协作方式的调整 (2026-08-10, 从 W5 的用量教训来)

W5 单周的用量约等于 W1–W4 之和。拆开看, **九成的成本花在"对话很长"这件事本身上**,
不是花在任何一件具体的事上 —— 每一轮都要把整个对话重读一遍, 到后期回一句话
也要先重读三四十万 token。三条改法:

1. **一段一个对话, 不要一周一个。** W5 评审方那一节从头到尾 70 多轮。
   拆成"第一段 / 第二段 / 修补"几节, 每节开头读 SPEC + 本文件即可 ——
   **`docs/` 本来就是自足的, 交接不必靠对话记忆。**

   只给文件名, 评审方用桥接读、且可以只读需要的部分。粘进来的东西
   此后每一轮都在为它付钱, 而且终端表格粘进来是乱码, 又贵又难读。
3. **截图发一张就够。** W5 里 6 张图只有 3 张是不同的, 每张发了两遍。
