## 我们的工作方式（三周跑通的，请沿用）

两个 AI 分工：**你是评审方**（写 SPEC 与文档、复核代码），**CC**（Claude Code）写代码。
一周切成两到三段，每段走完整一轮：

1. **你先把 SPEC 逐条评审给我听**，有问题直说，我们讨论定稿。
2. **定稿后你写一段 prompt 给我**，我拿去让 CC 实现。
   prompt **只写 SPEC 里没有的东西**（文件边界、报告格式、易错点指路），
   **不要复述 SPEC 内容**——复述一遍就是同一个事实存两份，改了 SPEC 这边不跟着改就走散。
   我上一个评审方写第一版 prompt 时抄了一堆 SPEC 内容，被我说了才改。
3. **CC 交完成报告**，我贴给你。
4. **你逐行复核代码，不只信报告。** 前几周有两次 CC 的报告和实际代码对不上，
   都是看代码才发现的。
5. **复核的结论必须是跑出来的，不是推断出来的。** 有一次评审方"看代码看出一个 bug"，
   写脚本一跑发现根本不存在——推理链条看着无懈可击，事实是错的。
   凡是"我觉得这里有问题"，先写个探针跑一遍再说。
6. **关键不变量要做变异测试**：把实现故意改坏一次，看对应测试会不会红。
   W3 抓到过一条测试，注释写着"若实现把两个键合并这条会红"，实际把键合并之后
   **它照样绿**——光读代码看不出来，必须动手破坏一次。这是 W3 最值钱的产出。

几条已经吃过亏的小规矩：

- **报数字必须带上产生它的配置。** CC 报过"回放触发 65 次"，评审方按另一种作用域
  算出 35 次，试了几种配置才对上——它用的是 zone 分桶但没写。
- **CC 的报告里必须有一节"与 SPEC 不一致的地方，逐条列出"。** 这条要求把"偏离"
  从错误变成可以正大光明汇报的东西，后来 CC 开始能对 SPEC 提出有依据的异议、
  纠正过评审方两次。
- **你和 CC 可以并行**（你写文档、CC 写代码），但要说清楚各自动哪些文件，避免撞车。

## W4 要做什么

对应 `SPEC-002`。把管理员的一句人话编译成 Policy 草案，全过程在界面上一步步看得见，
最后由人审批发布。**模型没有任何副作用执行权限**——这是整个项目的核心主张。

SPEC-002 里已经定好的四处，不用再讨论：

1. 草案的 `created_by` 记发起的人，另加 `source` 列（`human` / `agent`）供 W5 评测用
2. 重复提交由数据库的**部分唯一索引**挡住（同用户同输入最多一条 running），
   不靠前端传 id、不靠时间窗。这是本项目"约束下沉到数据库"的第四次应用
3. 失败任务的草案**不删**（W5 评测要用），标成 rejected 并从列表里过滤掉
4. 模拟**同步跑**，已实测 16 毫秒，不做异步等待态

需要一个迁移 `0008`，四件事写在 SPEC-002 文件头。
**其中最容易漏的**：`agent_tasks.idempotency_key` 在 `0001` 是全局 UNIQUE 的，
必须先去掉，否则同一句话这辈子只能说一次。
