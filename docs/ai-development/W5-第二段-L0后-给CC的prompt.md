### 2. cassette —— 采纳你的方案, 但有一个前提条件

冒烟子集 (L2 的 core 10 条, 约 0.3 MiB) 进版本库、全量留 `.llm-cache/<run_id>/`,
同意。1.04 MiB × 五臂 × 重跑几轮确实会让仓库明显发胖, 而 cassette 是一堆
hash 命名、没人会去读的 blob。

**但这个方案有一个前提, 现在还不成立**: 不进库就意味着**换台机器 / 改了 grader
之后没法重新判分**。而 W5 一定会改 grader。

所以 **`results.jsonl` 必须存 `artifact`** (SPEC 第五节已写全字段):

```
artifact:
  final_policy      产出的 Policy body 原文 (没有则 null)
  draft_bodies[]    修复循环里每一版的 body (从 agent_steps 取)
  missing_slots     追问时报的槽位
  error_codes       验证器实际报出的码
  tool_calls[]      成功执行的工具调用名 (must_not 判定要用)
  terminal_status   agent_tasks 的终态与 error_code
```

有了它, **重新判分就是一个对归档文件的纯函数** —— 不需要 cassette、不需要数据库、
不花一分钱。cassette 于是只剩"证明离线复跑这条路走得通"这一个职责, 10 条足够。

**L0 已经跑完了**, 归档里没有 `artifact`。两件事:

- 加上这个字段;
- **L0 要重跑**(理由见下面第 3 条, 不是单为这个)。

## 二、数据集两处 + 我的处置

**你先停下来说、没有动 `evals/datasets/`, 这个处理是对的。**
但两处的根因不一样, 处置也不一样:

### `simple-015` / `fault-006` 同文被顺带注入 —— 这是 runner 的 bug, 不是数据集的问题

**故障注入按输入文本匹配, 这本身就是错的。** 用例的身份是 `case_id`, 不是它的
输入文本 —— 两条用例碰巧说同一句话是完全合法的 (而且 `fault-006` 与 `simple-015`
同文正是刻意的对照设计)。改成**按 `case_id` 匹配**, 数据集一个字不用动。

改完 `simple-015` 就干净了 —— 它现在的 tokens / 调用数 / 墙钟都被那次多余的重试
污染过, 虽然不影响判分, 但那是一个复现不了的数字。

### `fault-005` 的注入永远不触发 —— 数据集要改, 而且要顺带堵住这类洞

`get_available_actions` 运行时从不调用, 所以这条注入是空的。两件事:

1. **runner 加一条断言**: 一条用例声明了 `inject`, 但整跑下来那个工具**一次都没被
   调用**过 → 判这条用例"注入未生效", 在报告里单列。
   **这才是根治** —— 否则下次换个工具名同样的洞会再开一次, 而且照样是绿的。
2. **`fault-005` 的 `inject.tool` 改成一个真会被调用的只读工具**, 数据集升
   `v1.1`, `CHANGELOG.md` 写明: 改的不是期望、不是难度, 是**一条声称在测故障
   重试、实际什么都没测的用例**。这不是看过分数之后的拟合。

**顺带一个发现要记下来但不用处理**: `get_available_actions` 在工具清单里
(SPEC-002 第五节的 13 个之一), 而运行时从不调它 —— 因为 Schema 已经在
system prompt 里了。**一个存在但永远不被调用的工具**, 写进报告的"与 SPEC 不一致"
那一节, 留给 W6 决定是删还是让模型能用。

### 因此: L0 要重跑

数据集从 `v1` 变 `v1.1`, 按我们自己的规矩"用例内容变更后, 旧 run 的分数不许与
新 run 混在一张表里比较"。加上 `artifact` 字段和注入按 `case_id` 匹配这两处改动,
**重跑一遍 L0 是唯一干净的做法**。

代价很小: **¥1.9, 墙钟按 P50 4.1s / 并发 4 估算约 3–5 分钟。** 值得。

## 三、你没当成问题、但我认为最要紧的一件: `discovering` 是运行时驱动的

你在成本表里顺口写了一句:

> "A1 与 A0 同为 1 次/条 (SPEC 初稿估 5 次是把工具调用算成模型调用, 实现是运行时驱动)"

**这句话把 A1 的含义整个改掉了, 而它顺带暴露了一处 W4 遗留的 SPEC 与实现不符。**

SPEC-002 第五节的裁剪表写的是 "`discovering` 给模型六个只读工具" ——
意思是**模型自己选择查什么**。而按你说的, 运行时把只读工具挨个调完、结果塞进
messages, 模型不参与决策。**两者不是一回事, 而 W4 复核时没人抓到。**

后果:

- SPEC 初稿以为的 A0→A1: **模型主动去查** vs 一次性塞给它;
- 实现里的 A0→A1: 清单以**工具结果消息**进来 vs 以**系统 prompt 文本**进来。
  **信息量完全相同, 只是位置与包装不同。**

**这不是要你改代码。** 但如果不说准, "资源发现工具有没有用"这个问题会被一个
根本没在回答它的实验假装回答掉 —— 而这正是本项目一路在修的那类毛病
(声明的和执行的不是一回事)。

**跑 L1 之前必须先做这件事, 而且要跑出来不要读出来:**

1. **写个探针**, 用打桩客户端跑一条完整任务, 把 `discovering` 阶段的
   `LLMRequest.tools` 与实际发生的 `agent_steps` 打出来。**回答三个问题**:
   - `discovering` 阶段到底给不给模型工具? 给的话是几个?
   - 那几个只读工具是模型 `tool_call` 触发的, 还是运行时无条件调的?
   - 一条 happy 路径里模型调用总数到底是几次, 分别在哪个阶段?
2. **把探针结果原样写进报告**, 不要只给结论。
3. 若确认是运行时驱动: 在报告里按事实重写 A1 的一句话定义
   (我会同步改 SPEC 与 README 的措辞), 并说明 A0→A1 这一格实际在比什么。
   "让模型自己决定查什么"若确实没实现, 就明写它是非目标或 W6, **不留一个
   听起来做了、其实没做的字母。**

**探针零成本、几分钟的事, 但它决定 L1 那 ¥1.9 花得有没有意义。**
