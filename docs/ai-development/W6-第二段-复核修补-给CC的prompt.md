## 四个容器的 mem_limit 合计不能等于整机内存

现在是 `db 384m + api 448m + web 64m + caddy 128m = 恰好 1 GiB`,
而 1 GB 是**整台 Lightsail Micro** 的全部内存。宿主机的内核、dockerd、sshd、
以及每日 04:00 那个重置 cron (它自己是个 python 进程, 还要跑 device-sim
回放 1258 条) 都还没算进去。

要紧的不是"会不会 OOM", 是**这套限制在实机上拦不住任何东西**:
`mem_limit` 是上限不是预留, 容器涨到各自上限之前, 内核的 OOM killer 已经
先挑一个进程杀了 —— 很可能是 Postgres。也就是说这套数字通过了本机验收,
但它在实机上不起作用。**本机验收证明的是"四个容器在各自上限内跑得动",
不是"这台 1 GB 的机器跑得动"。**

(你在 OOM 反向验证上做得对 —— 纯分配不计 RSS 那一层坑挖得比我提示的深。
这一条是同一个毛病的上一层: 验证方法对了, 被验证的那个数字定错了。)

## 要做的

1. **把四个容器的 `mem_limit` 合计压到 ≈ 750 MiB**, 给宿主机留 ~250 MiB。
   具体分配你定 (Postgres 与 api 是大头, web/caddy 很小), 覆盖层注释里写清楚
   **这个合计是怎么来的** —— 是"整机 − 宿主机开销", 不是"整机";
2. **重跑 docker job 的全部断言**, 确认在新的 (更紧的) 限制下仍然全绿。
   要是某个容器在新限制下起不来, **那正是这次要发现的东西** —— 报上来, 不要
   为了让断言绿而把限制调回去;
3. **runbook 加一条开机检查项**: 实机上先 `free -m` 量一次空载开销, 与覆盖层
   里假设的 ~250 MiB 对一次; 对不上就按实测值重新分配。**这是本机验不到的
   第五件事**, 与 SPEC 第六节那四条并列, 一起写进那一节。
