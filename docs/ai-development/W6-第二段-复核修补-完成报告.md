# W6 第二段 · 复核修补 · 完成报告

> 范围: 只有一件 —— 四个容器 mem_limit 合计从 1 GiB 压到 ≈750 MiB
> (SPEC-009 第六节第 4 条修订后的数字)。零真实模型调用, 零花费。
>
> 改动文件: `docker-compose.prod.yml` (四个 mem_limit + 注释)、
> `docs/deploy-runbook.md` (开机检查项一条 + 开头措辞校正)、
> `scripts/ci/test-docker.sh` (仅一处 section 文案, 见第一节第 2 条)。
> 第 0 件、Caddyfile、生产种子、断言内容、其余 mem 相关数字均未动。

## 一、与 prompt 的出入 (两处, 都是报备不是偏离)

1. **合计取 736 MiB, 不是字面的 750**: 分配是 db 320 + api 320 + caddy 64 +
   web 32 —— 四个都取 2 的幂次倍数, 736 = 1024 − 288, 给宿主机留 ~288 MiB
   (比 prompt 的 ~250 略宽)。"怎么来的"按要求写进覆盖层注释: 合计是
   **(整机 1024 − 宿主机开销估值 ~288)**, 不是整机; 并写明本机验收证明的是
   "四个容器在各自上限内跑得动", 不证明"这台 1 GB 机器跑得动"。

2. **`test-docker.sh` 动了一处**, 但不是断言: section 标签原文写着
   "mem_limit 合计 1 GB", 数字改完它就成了错话, 改成 "合计 736 MiB"。
   断言逻辑、等待时长均未动 —— 新限制下没有任何容器起不来或变慢,
   `up -d --wait` 默认节奏一次通过, 不需要调等待。

## 二、新增/改动各由什么守着

| 改动 | 守着它的东西 |
|---|---|
| 四个 mem_limit 新值 | docker job 全套断言在新限制下整跑 (第三节); `docker inspect` 四容器求和 = 771751936 字节 = 恰 736 MiB |
| "合计 = 整机 − 宿主机开销"的定法 | 覆盖层注释 + SPEC-009 第六节修订文 (评审方已改) 互为出处 |
| 宿主机开销 ~288 是估值这件事 | runbook 第一节新检查项: 实机 `free -m` 量空载, 对不上就按实测重分并在实机重跑 `test-docker.sh` —— 这是本机验不到的第五件, 已与另外四件并列写明 |
| runbook 开头不再过头宣称"1 GB 已验证" | 措辞改为两句话分开: 容器组验过 / 整机要等实机 |

## 三、验证结果 (数字与产生它的配置)

- **新限制下 docker job 全部断言绿, 整跑 2 次** (改数字后一次、改 section
  文案后干净重建一次), `SCRIPT_EXIT=0`。机器: 本机 macOS (Darwin 25.5.0,
  Docker 29.6.2 / Compose v5.3.1), 与之前所有验收同一台。
- **限制核对**: `docker inspect` HostConfig.Memory —— db 335544320 (320 MiB) /
  api 335544320 (320 MiB) / caddy 67108864 (64 MiB) / web 33554432 (32 MiB),
  合计 771751936 字节 = **736 MiB**。
- **空载余量** (`docker stats` 单帧, 起稳后): api 76.9 MiB / 320 (24%),
  db 27.2 MiB / 320 (8.5%), caddy 18.6 MiB / 64 (29%), web 8.7 MiB / 32 (27%)。
  每个容器都不到上限的三成 —— prompt 预告的"某容器在新限制下起不来"没有发生,
  不是把限制调回去换来的。
- prompt 说"若起不来那正是要发现的东西": 没起不来, 但照实说 —— 空载 ≠ 负载,
  api 在跑 Agent 任务、db 在回放 1258 条时会更高; 那一层只有实机 (以及第三段
  的真实使用) 能回答, 已由 runbook 的 `free -m` 检查项与"实机重跑 test-docker"
  接住。
