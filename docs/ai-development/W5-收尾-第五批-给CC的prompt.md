## 现状

四份归档的 `summary.md` 印着"这是事故不是分数":

```
20260810-130256-L0    4/10 —— **不为 0, 这是事故不是分数**   (A0 档, 早于补入 31)
20260810-161625-C1    1/10 —— **出厂档不为 0, ...**
20260810-183549-C1    1/10 —— **出厂档不为 0, ...**
20260811-003755-C1    2/10 —— **出厂档不为 0, ...**          (README 引用的定形 C1)
```

按 SPEC-007 补入 31 / 37, 这四句现在**全都是错的**: A0 档与配置对照臂都不设门槛。
最后一份尤其要紧 —— 它是 README 指过去的那一跑。

还有第二处不一致: 那份定形 C1 的归档写 **2/10**, 而 README 与
`summary_ablation.md` 写 **1/10**。两个数都没错 —— 归档记的是**当时判据**下的结果,
1/10 是补入 36 拆开判据后的离线重判 (`evals/runs/injection_regrade_v2.json`)。
**但归档里没有一个字指向这件事**, 谁翻到那一页都会以为哪边写错了。

## 要做的两件

### 一、渲染器给"早于补入 36"的归档加一句指路

`manifest` 里没有 `injection_criteria` 的归档 (15 份全是), 得逞率那一行后面补一句:
**本行按补入 36 之前的口径判定; 按现行口径的离线重判见
`evals/runs/injection_regrade_v2.json`。**

口径与第四批那个"不适用"同源: **报告层不自己判新旧, 只展示 metrics 的结论。**
不要在 archive.py 里再写一次判别条件。

### 二、按当前渲染器重生成全部 15 份 summary.md

**只重生成 `summary.md`, 输入是各自的 `results.jsonl` + `manifest.json`,
那两份文件一个字节不许写。** 重新渲染是对归档文件的纯函数 (补入 33 立的),
这一步正是它的用处。

理由说清楚, 免得看起来像在改历史: **测量数据是冻结的, 渲染是可以重跑的。**
渲染器当时印错了这件事本身不会消失 —— 它在 git 历史里, 那才是它该待的地方。
留着一份与现行 SPEC 打架的判语在归档里, 才是真的会误导人。

**做完 diff 一遍逐份确认**: 除了 (a) 门槛措辞、(b) 新增的 unsafe 行、
(c) 上面那句指路, **其余每一行都必须逐字不变**。有第四种差异就停下来说 ——
那说明渲染器在别的地方也漂了, 那件事本身要先弄清楚。

## 测试

- 重生成的幂等性: 同一份归档连跑两次渲染, 输出逐字节相同。

两条都做变异测试。
