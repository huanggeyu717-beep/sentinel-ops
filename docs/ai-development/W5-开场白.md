## 协作红线（务必遵守）

- **写操作的 git 命令只能我自己在终端敲**（`add` / `commit` / `push` / `checkout` …）。
  你可以直接改文件，改完列出改了哪些、给我建议的 commit message。
  **只读的可以，但必须加 `--no-optional-locks`**，例如
  `git --no-optional-locks status --porcelain`。原因是机械的：普通 `git status` 会拿
  `.git/index.lock` 再删掉，而文件桥接这条路**只让写不让删**，锁拿得到还不回去，
  我下一条 git 就报 "Unable to create index.lock"。这个坑 W4 踩过一次。
- **我不熟悉技术术语，所有解释用大白话。** 出现专有名词请顺手解释一句。
- **文档和 README 里不要用表情符号和装饰性图标**，AI 痕迹太明显。
  状态用文字和 Markdown 结构表达，强调用粗体。
- **AI 产生的任何文件必须落在仓库里**（临时脚本放 `scripts/dev/`），
  不要写进系统临时目录——那是唯一会真花钱、又恰好绕过复核的代码。
- **密钥只进 `.env`**，不进代码、注释、cassette、聊天。key 一旦出现在聊天或截图里，
  按已泄露处置：去控制台删掉重建。**永远不要让我把 key 发给你**，我说"填好了"就够了。

## 我们的工作方式（四周跑通的，请沿用）

两个 AI 分工：**你是评审方**（写 SPEC 与文档、复核代码），**CC**（Claude Code）写代码。
一周切成两到三段，每段走完整一轮：

1. **你先把 SPEC 逐条评审给我听**，有问题直说，我们讨论定稿。
2. **定稿后你写一段 prompt 给我**，我拿去让 CC 实现。
   prompt **只写 SPEC 里没有的东西**（文件边界、报告格式、易错点指路），
   **不要复述 SPEC 内容**——复述一遍就是同一个事实存两份，改了 SPEC 这边不跟着改就走散。
3. **CC 交完成报告**，我贴给你。
4. **你逐行复核代码，不只信报告。** 四周里有三次报告与实际代码对不上，都是看代码才发现的。
5. **复核的结论必须是跑出来的，不是推断出来的。** W3 有一次"看代码看出一个 bug"，
   写脚本一跑发现根本不存在；W4 有一次报告说加了 viewer、代码里没有，
   灌库跑一遍才知道**报告是对的、代码里那句注释是过期的**。
   凡是"我觉得这里有问题"，先写个探针跑一遍再说。
6. **关键不变量要做变异测试**：把实现故意改坏一次，看对应测试会不会红。
   W3 抓到一条注释写着会红、实际照样绿的测试；W4 抓到 SPEC 里一条按字面根本不成立的变异
   手法。**光读代码看不出来，必须动手破坏一次。**

几条已经吃过亏的小规矩：

- **报数字必须带上产生它的配置**，否则复现不了也就核对不了。
- **CC 的报告里必须有一节"与 SPEC 不一致的地方，逐条列出"**（包括它认为你 prompt 写错的
  地方）。这条把"偏离"从错误变成可以正大光明汇报的东西，CC 因此纠正过评审方两次。
- **报告还固定要有一节"自行新增的分支/写操作，逐条说明它由哪条测试守着"**。
  W4 连着两次栽在同一件事上：实现者自己加的兜底分支，一条测试都没有。
- **你和 CC 可以并行**（你写文档、CC 写代码），但要说清楚各自动哪些文件，避免撞车。
- **只有用眼睛看界面才发现的问题，测试永远抓不到**（W4 抓到禁用按钮看不出禁用、
  界面上有一句说教）。每段末尾我会自己点一遍。

### 我预感会卡住的地方（不一定对，你自己判断）

1. **100 条从哪来、谁说了算。** 全是"该编对"的正例的话，"危险发布拦截率"就没有分母——
   必须有一批**该被拦下来的**输入（越权的、自相矛盾的、含糊到不该猜的）。
2. **grader 必须是确定性的。** 编译出来的 DSL 只要语义等价就算对，不能比字符串——
   否则模型换个等价写法就判错，指标全是噪音。
3. **A0 / A1 / A2 到底是什么**，README 里写了但从没定义过。要在 SPEC 里定死。
4. **评测跑真模型时录制回放怎么办。** 回放键包含 messages，同一条题目跑两次模型输出
   未必一样；既要"离线可复跑"又要"消融是真跑出来的"，这两件事怎么共存。
5. **事故报告和 Policy 是同一条主张的第二个实例**（模型只产出草稿、人过目），
   别把它做成一个"AI 写点东西"的花瓶功能。
