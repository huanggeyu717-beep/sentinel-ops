## 案例 1 — 补一个洞的时候开了另一个洞 (2026-08-08)

**日期 / 模块**: 2026-08-08 / `apps/api/app/services/agent_service.py` (W4 第一段)。
Claude Code 实现, prompt 见 `W4-第一段-给CC的prompt.md`; 缺陷由评审方逐行复核 +
探针发现。

**生成上下文**: SPEC-002 第二节要求"任务失联靠租约判死"。实现者在照做之余
**自己发现并补了一个 SPEC 没写的场景**: 进程在"建任务"与"认领"之间死掉的任务
从没打过卡, `heartbeat_at` 是 NULL, 只按打卡时间判死会让它永远挂在 `running` 上
堵住去重索引。这个补充本身是对的, 实现者也在完成报告里主动列了出来。

**缺陷**: 那个兜底分支拿 `created_at` 当起算点。而**一条被人回答后复活的任务**,
`created_at` 可能是十分钟前 —— 它一变回 `running` 就已经满足判死条件,
**零宽限期**。后果: 用户隔十分钟回答了 Agent 的澄清问题, 任务刚活过来,
下一次清扫 (默认 5 秒一轮) 就把它判成 `dead_letter`, 并顺手把草稿标 `discarded`。
用户看到的是"我刚回答完, 系统说任务失联, 草稿也没了"。

**发现**: 逐行复核时看出可疑, 但**没有直接下结论** —— 按项目规矩先写探针跑一遍:
把 `0001_initial.sql` 灌进一个真 Postgres 16, 加上 `0008` 里与 `agent_tasks` 有关的
DDL, 然后把实现里 `_ANSWER_RESUME` 与 `_REAP_STALE` 两条 SQL **原文照搬**执行。
复现输出:

```
--- 澄清中:      status=clarifying   已存在时长 00:10:00
--- 人现在回答:   status=running  stage=discovering  heartbeat=NULL
--- 一次清扫:    -> dead_letter / lease_timeout
```

修法也在同一个探针里验了两个方向: 加上"变回 running 时打一次卡"之后,
刚回答完跑清扫 `0 rows`; 回答后 120 秒仍没人认领, 照样 `dead_letter`。

**为什么 39 条测试一条都没抓到**: 两件事叠在一起 ——

1. `conftest.py` 把 `SENTINEL_AGENT_HEARTBEAT_SECONDS` 设成 3600 (理由成立: 5 秒一轮
   的清扫事务会与夹具的反向 TRUNCATE 偶发死锁), 所以 `maintenance_loop`
   **在整套测试里从没真跑过**, 只有 `beat()` / `reap()` 被直接调用;
2. 所有 reap 测试都是手工把 `heartbeat_at` 改老, 走的都是第一个分支。
   **实现者自己新加的那个兜底分支, 一条测试都没有。**

一句话: **唯一没被测试碰过的那个分支, 正好是出问题的那个。**

**根因**: 一个判断用了两个不同的起算点 (`heartbeat_at` 与 `created_at`), 而这两个
时间在"任务复活"这种情形下含义完全不同。同一个判断依赖两份事实, 是本项目反复在修
的那类毛病换了个位置出现。

**修复**: SPEC-002 第二节写死一条规矩 —— **任何让任务变回 `running` 的写操作都要
同时把 `heartbeat_at` 置成 `now()`**, 把它当作"这一刻刚活过来"的一次打卡;
判死条件随之收敛成单一判据, 不再看 `created_at`。修补 prompt 见
`W4-第一段-修补-给CC的prompt.md`。

**防回归**: SPEC-002 验收 15c 两条 (清扫的两个分支各一条, 其中第二条正是本缺陷的
场景) + 变异 22b (把那句打卡去掉, 第二条必须红)。

**这一例的教训值得单独记**: 实现者主动补 SPEC 没写的场景, 是最该鼓励的行为 ——
但**补出来的分支必须跟着补测试**, 否则它就是全套代码里唯一没人守的那一块。
下一份 prompt 的报告格式已加一条: "自行新增的分支, 逐条说明它由哪条测试守着"。

## 案例 2 — 看起来在守、其实永远不会失败的断言 (2026-08-08)

**日期 / 模块**: 2026-08-08 / `apps/api/tests/test_agent_service.py` (W4 第一段)。

**缺陷**: `test_reap__stale_heartbeat_becomes_dead_letter` 的最后一行写成

```python
assert any(r["task_id"] == task["id"] for r in reaped) or task["status"] == "dead_letter"
```

而 `task["status"] == "dead_letter"` 在上面三行已经断言过了 —— `or` 的右边恒为真,
**整条断言不可能失败**。它本想守的是"`reap()` 确实把这个任务 id 报了出来"
(调用方要靠这个返回值去把草稿标 `discarded`), 实际什么都没守。

**发现**: 逐行复核测试代码时读出来的。**这类缺陷靠跑测试永远发现不了** ——
它在任何实现下都是绿的, 只有读它才知道它是空的。

**根因**: 写测试时"多加一个条件更保险"的直觉, 在断言里恰好是反的 ——
`assert A or B` 比 `assert A` **弱**, B 恒真时整条作废。

**修复**: 去掉 `or` 后半截。

**防回归**: 复核清单加一条 —— 见到 `assert A or B`, 先问 B 在这个用例里是不是恒真。
这类断言比没有测试更坏: 没有测试时人知道这里没人守, 空断言让人以为有人守。
