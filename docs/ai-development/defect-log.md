## 案例 1 — 补一个洞的时候开了另一个洞 (2026-08-08)

**日期 / 模块**: 2026-08-08 / `apps/api/app/services/agent_service.py` (W4 第一段)。
Claude Code 实现, prompt 见 `W4-第一段-给CC的prompt.md`; 缺陷由评审方逐行复核 +
探针发现。

**生成上下文**: SPEC-002 第二节要求"任务失联靠租约判死"。实现者在照做之余
**自己发现并补了一个 SPEC 没写的场景**: 进程在"建任务"与"认领"之间死掉的任务
从没打过卡, `heartbeat_at` 是 NULL, 只按打卡时间判死会让它永远挂在 `running` 上
堵住去重索引。这个补充本身是对的, 实现者也在完成报告里主动列了出来。

**缺陷**: 那个兜底分支拿 `created_at` 当起算点。而**一条被人回答后复活的任务**,
`created_at` 可能是十分钟前 —— 它一变回 `running` 就已经满足判死条件,
**零宽限期**。后果: 用户隔十分钟回答了 Agent 的澄清问题, 任务刚活过来,
下一次清扫 (默认 5 秒一轮) 就把它判成 `dead_letter`, 并顺手把草稿标 `discarded`。
用户看到的是"我刚回答完, 系统说任务失联, 草稿也没了"。

**发现**: 逐行复核时看出可疑, 但**没有直接下结论** —— 按项目规矩先写探针跑一遍:
把 `0001_initial.sql` 灌进一个真 Postgres 16, 加上 `0008` 里与 `agent_tasks` 有关的
DDL, 然后把实现里 `_ANSWER_RESUME` 与 `_REAP_STALE` 两条 SQL **原文照搬**执行。
复现输出:

```
--- 澄清中:      status=clarifying   已存在时长 00:10:00
--- 人现在回答:   status=running  stage=discovering  heartbeat=NULL
--- 一次清扫:    -> dead_letter / lease_timeout
```

修法也在同一个探针里验了两个方向: 加上"变回 running 时打一次卡"之后,
刚回答完跑清扫 `0 rows`; 回答后 120 秒仍没人认领, 照样 `dead_letter`。

**为什么 39 条测试一条都没抓到**: 两件事叠在一起 ——

1. `conftest.py` 把 `SENTINEL_AGENT_HEARTBEAT_SECONDS` 设成 3600 (理由成立: 5 秒一轮
   的清扫事务会与夹具的反向 TRUNCATE 偶发死锁), 所以 `maintenance_loop`
   **在整套测试里从没真跑过**, 只有 `beat()` / `reap()` 被直接调用;
2. 所有 reap 测试都是手工把 `heartbeat_at` 改老, 走的都是第一个分支。
   **实现者自己新加的那个兜底分支, 一条测试都没有。**

一句话: **唯一没被测试碰过的那个分支, 正好是出问题的那个。**

**根因**: 一个判断用了两个不同的起算点 (`heartbeat_at` 与 `created_at`), 而这两个
时间在"任务复活"这种情形下含义完全不同。同一个判断依赖两份事实, 是本项目反复在修
的那类毛病换了个位置出现。

**修复**: SPEC-002 第二节写死一条规矩 —— **任何让任务变回 `running` 的写操作都要
同时把 `heartbeat_at` 置成 `now()`**, 把它当作"这一刻刚活过来"的一次打卡;
判死条件随之收敛成单一判据, 不再看 `created_at`。修补 prompt 见
`W4-第一段-修补-给CC的prompt.md`。

**防回归**: SPEC-002 验收 15c 两条 (清扫的两个分支各一条, 其中第二条正是本缺陷的
场景) + 变异 22b (把那句打卡去掉, 第二条必须红)。

**这一例的教训值得单独记**: 实现者主动补 SPEC 没写的场景, 是最该鼓励的行为 ——
但**补出来的分支必须跟着补测试**, 否则它就是全套代码里唯一没人守的那一块。
下一份 prompt 的报告格式已加一条: "自行新增的分支, 逐条说明它由哪条测试守着"。

## 案例 2 — 看起来在守、其实永远不会失败的断言 (2026-08-08)

**日期 / 模块**: 2026-08-08 / `apps/api/tests/test_agent_service.py` (W4 第一段)。

**缺陷**: `test_reap__stale_heartbeat_becomes_dead_letter` 的最后一行写成

```python
assert any(r["task_id"] == task["id"] for r in reaped) or task["status"] == "dead_letter"
```

而 `task["status"] == "dead_letter"` 在上面三行已经断言过了 —— `or` 的右边恒为真,
**整条断言不可能失败**。它本想守的是"`reap()` 确实把这个任务 id 报了出来"
(调用方要靠这个返回值去把草稿标 `discarded`), 实际什么都没守。

**发现**: 逐行复核测试代码时读出来的。**这类缺陷靠跑测试永远发现不了** ——
它在任何实现下都是绿的, 只有读它才知道它是空的。

**根因**: 写测试时"多加一个条件更保险"的直觉, 在断言里恰好是反的 ——
`assert A or B` 比 `assert A` **弱**, B 恒真时整条作废。

**修复**: 去掉 `or` 后半截。

**防回归**: 复核清单加一条 —— 见到 `assert A or B`, 先问 B 在这个用例里是不是恒真。
这类断言比没有测试更坏: 没有测试时人知道这里没人守, 空断言让人以为有人守。

## 案例 3 — 看起来只读的 git 命令, 危险在锁不在改动 (2026-08-09)

**日期 / 模块**: 2026-08-09 / W5 第一段收尾轮的变异测试脚本 (Claude Code 执行,
prompt 见 `W5-第一段-收尾-给CC的prompt.md`)。缺陷由实现者当场自曝, 评审方复核。

**缺陷**: M4 变异的还原脚本里混进了一句
`git --no-optional-locks checkout -- 2>/dev/null; true`。它没有路径参数,
实际效果是打印修改文件列表、未改动任何文件; 数据集本身由 `cp` 备份还原。
但它违反了协作红线 "git 一律由本人执行", 而且**危险与"改没改文件"无关**:
`git checkout` 即使什么都不改也会去拿 `.git/index.lock`, 文件桥接这条路
只让写不让删 —— 锁拿得到还不回去, 下一条 git 就报
`Unable to create index.lock`。

**发现**: 实现者在命令输出里看到 git 状态列表, 当场在报告里自曝;
评审方检查 `.git/` 确认**这次没有 lock 残留** —— 那是运气 (这个形式的
checkout 大概率在拿锁之前就退出了), 不是因为它无害。

**根因**: 把"不改文件的 git"当成了"只读的 git"。两者不是一回事:
只读与否要看它碰不碰 `.git/` 里的锁, 不看它碰不碰工作区。
这与 W4 的两例同类 —— **看起来无害的动作, 危险在别处**。

**修复与防回归**: 协作红线措辞更精确一句 —— **`checkout` 不管带不带参数都
不属于"只读的 git"**, `--no-optional-locks` 也救不了它 (那个开关只管
status/diff 这类可选锁场景)。还原文件一律用 `cp` 备份, 不用 git。

## 案例 4 — 评测设施把"模型答错"与"设施答不上"判成同一个红格子 (2026-08-10)

**日期 / 模块**: 2026-08-10 / `evals/runner/client.py` + `evals/datasets/policies_v1.jsonl`
(W5 第二段)。Claude Code 实现, prompt 见 `W5-第二段-给CC的prompt.md` 与
`W5-第二段-重跑修补-给CC的prompt.md`; 缺陷由评审方在归档上跑探针发现。

**生成上下文**: SPEC-007 第二节的字段表把 `clarify_answer` (冻结的标准回答)
**只挂在 `clarify` 那一类**上。实现照字段表办事, `drive_case` 写成:
没有 `clarify_answer` 的用例, 停在 `clarifying` 即终局。对 `illegal` /
`capability_gap` / `prompt_injection` 这**正是**成功形态, 所以这个写法看着很合理,
注释里也写明了理由。

**缺陷**: 但"会产出策略的用例"同样会追问 —— 而且**在信息不全的正例上追问是正确
行为**。它们没有 `clarify_answer`, 于是一追问就没人应答, 挂到被判
`no_draft_submitted`。L2 定形跑 100 条里 44 条终态是 `clarifying`, 其中 25 条
该如此 (22 条判 passed), **另 18 条是本该编译出策略、被设施卡死的**;
`repairable` 4/4 全灭 —— 这一类存在的全部意义是量修复循环, 而它**一次都没跑到
验证器**。补齐后重跑: 卡死的 18 条里 12 条编对, L2 macro 53% → 71%。

**发现**: 不是靠测试, 是靠**读分类别表**。评审方注意到 L1 → L2 加了验证器和追问
之后 `simple` 17→12、`combo` 10→8、`tool_fault` 7→5、`repairable` 1→0 ——
**一个只增不减的能力开关, 不该让任何一类变差**。macro 35→47→53 单调爬升
把这个形状抹平了。SPEC-007 写"分类别表是主体, 总分只作摘要"那句话这次救了场,
但**要靠人真的去读那张表**。

**根因 (两层)**:

1. **设施层**: 判分把"模型没产出草案"与"没人回答它的追问"折叠成同一个
   `failure_kind`。评测里这两件事长得一模一样 —— 都是一个红格子 —— 而它们
   一个是模型的问题、一个是我的问题。**照字段表办事是对的, 但字段表本身有洞时,
   实现会忠实地把洞放大成 18% 的样本损失**;
2. **报告层 (这一条是 AI 侧的)**: 完成报告写的是"能力阶梯 macro 成功率单调爬升 ——
   这是消融要证明的核心", 而同一张表里四个最基本的类别一起退步, **报告没提**。
   拿总分去支持结论、对反直觉的格子视而不见, 是评测报告最典型的失真方式。

**修复**: 数据集 v1.2 给 57 条会产出策略的用例补 `clarify_answer`
(`behavior_equiv` 53 + 带 `legitimate` 的 `injection_resisted` 4), 判据一个字节
没动 —— 机器可核对: 剥掉这 57 个键后内容哈希逐字节回到 v1.1 的
`681d95ec3325eca5`。L2/C1/C2 重跑; L0/L1 经离线逐条重判确认在 v1.2 下同分, 未重跑。

**防回归**:

- `evals/tests/test_dataset_lint.py::test_clarify_answer__present_on_every_policy_producing_case`
  —— 会产出策略的用例少了冻结回答, lint 当场红;
- 新观察值**多问率** (`behavior_equiv` + `repairable` 里 `clarify_rounds > 0` 的
  占比) 进 summary、**不进成功率**: 多余追问是真实失败模式, 但把它算成
  "没产出草案"就是拿设施缺陷冒充模型缺陷;
- 报告纪律一条: **见到某一格反直觉地变差, 当成待查项主动报上来**, 不要只报总分。

## 案例 5 — 一条从进 CI 那天起就没绿过的检查 (2026-08-10)

**日期 / 模块**: 2026-08-10 / `scripts/ci/lint.sh` + `.github/workflows/ci.yml`
(W5 CI 修复)。缺陷由 W2 的 CI 重构引入 (commit `e5ad670`), 由 W5 排查
"engine job 红了"时才被看见; 修复由 Claude Code 执行, prompt 见
`W5-CI修复-给CC的prompt.md`。

**生成上下文**: W2 把 mypy 加进 `scripts/ci/lint.sh`, 并在文件里写下理由 ——
"mypy 以前只在本机 make lint 里跑, CI 完全不跑 —— 等于它拦不住任何东西。
放进这里之后, ruff 和 mypy 两道检查在本机与 CI 执行的是同一份脚本。"
这句话的每个字都对, 而且它做的正是本项目一贯提倡的事: **把约定变成 CI 能拦的规则**。

**缺陷**: `lint.sh` 挂在 engine job 上, 而那个 job 的立身之本是**故意只装
`requirements-dev.txt`** ("纯函数, 秒级, 不连库不连网")。mypy 看不见
fastapi / sqlalchemy / httpx / asyncpg 时不会"少检查一点", 它对每一条 import
报 `import-not-found` 然后 exit 1 —— **一条类型都没检查成, 而且当场红**。

所以这条检查从**进 CI 的第一次 push 起就没有绿过一次**:

| run | 时间 | engine job | mypy 报错 |
|---|---|---|---|
| `31095732539` | 2026-08-06 11:03 | 绿 | (mypy 尚未进 CI) |
| `31130969427` | 2026-08-06 23:25 | **红** | 39 个, 全是 import-not-found |
| `31132371922` | 2026-08-06 23:48 | **红** | 41 个 |
| … 中间 10 次 push, 每一次 | | **红** | |
| `31424990736` | 2026-08-10 19:37 | **红** | 89 个 |

**四天、十二次连续推送, 主分支的 CI 一直是红的。**

**发现**: W5 收尾时终于去看这个红灯。而**第一版诊断也错了** —— prompt 里写的根因是
`test-unit.sh` 把整个 `evals` 收进了单元档 (`evals/runner/` 下有 import httpx /
asyncpg 的模块)。这个观察本身没错, 但 `gh run view` 一看就清楚:

```
X Run bash scripts/ci/lint.sh      <- 真正失败的是这一步
- Run bash scripts/ci/test-unit.sh <- "-" = 前一步挂了, 它根本没跑过
```

`test-unit.sh` 从来没执行过, 那个坑还没来得及发作。而 89 个报错里**只有 2 个来自
evals** (`cli.py` 与 `test_runner_guardrails.py` 的 httpx), 另外 87 个是 apps/api
的 fastapi / sqlalchemy —— 与 W5 毫无关系, 只是 W2 那天就在那儿。

**直接根因 (执行层)**: 一个 job 同时承担了两个互相冲突的角色 —— lint 要检查全仓,
就必须看得见全仓的依赖; engine 要证明单元档真的离线, 就必须**装不到**那些依赖。
把它们放进同一个 job, 两个要求里必然有一个落空。

### 这一例要留两条教训, 不是一条

两条讲的是不同的事, **对策也不同**。后来的那条更醒目, 但它不能替掉前面那条。

**教训一 —— 本机环境比 CI 富, 所以本机验证不了 CI。**

这是一个**可数的系列**, 到这里是第四次:

| # | 时间 | 本机有什么而 CI 没有 | 症状 |
|---|---|---|---|
| 1 | W1 | ruff 版本旧 (CI 装最新, 默认规则集更大) | 本机绿, CI 报一批没见过的规则 |
| 2 | W2 | mypy 只在本机 `make lint` 里跑, 根本没进 CI | CI 拦不住任何类型错误 |
| 3 | W4 | 宿主机有 `apps/device-sim/seed/`, 容器镜像里没 COPY | 宿主机测试全绿, 容器里每条 Agent 任务的 `simulate_policy` 落死信 |
| 4 | W5 | 本机 venv 装了 apps/api 全套依赖 | mypy 与 pytest 在 CI 上撞 import-not-found |

第 3 例的"更富"是**宿主机 vs 容器**而不是本机 vs CI 机器, 但形状一模一样:
**在一个东西更全的环境里跑绿, 拿去证明一个更穷的环境也会绿。**

**对策: 要有办法在本机复现那个更穷的环境。** 已落地 `make ci-repro` /
`ci-unit-repro` / `ci-lint-repro` (`scripts/dev/ci-env-repro.sh`) ——
全新空 venv, 按 CI 的方式装依赖再跑。**用现有 venv 验证等于没验证。**
第 3 例对应的那个更穷环境是容器, 复现手段是"build 之后在容器里跑一句断言",
CI 的 docker job 至今只 build 不起容器 —— **这条对策只补上了两个环境里的一个**,
另一个仍是债 (`docs/进度与交接.md` 留给 W6 的第 2 条)。

**教训二 —— 没有反馈回路, 一条检查可以在 CI 里躺四天什么都不干。**

这一条与"本机 vs CI"无关, 换一个更穷的本机环境也不会让它早一天被发现。
红灯从 2026-08-06 亮到 2026-08-10, 十二次推送, **没有人看过它是什么颜色**。
**"我加了一道检查"与"那道检查在 CI 上真的跑起来了"是两件事** —— 这与案例 2
(看起来在守、其实永远不会失败的断言)、与 SPEC-007 变异 M5 第三行 (三层守卫
一起坏、一起相等) 是同一课, 区别在于这次连"它是不是绿的"都没人核。

**对策: 让状态出现在每次打开仓库都会看到的地方。** README 顶部加 CI 徽章
(2026-08-10 确认四个 job 全绿之后才加 —— **挂一个红徽章比没有徽章更糟**)。
诊断出"红了四天"只是诊断, 徽章才是药。

**修复**:

- `lint` 独占一个 job, `lint.sh` 自己装 `apps/api/requirements.txt`;
  engine job 保留贫瘠依赖 (那份贫瘠就是"单元档真的离线"这个保证本身)。
  **不能只在原 job 里补装依赖** —— pip install 在同一个 job 内跨步骤留存,
  lint 装完就把 engine 的贫瘠污染掉了;
- `evals` 按依赖拆目录: 离线的留 `evals/tests/` (归单元档), import httpx /
  asyncpg 的挪 `evals/runner/tests/` (归 api 档)。**按目录拆不按文件名列清单** ——
  列清单会重蹈"以后往那个目录加的测试静默地永远不执行"那个坑。

**防回归**:

- `evals/tests/test_grader_io_boundary.py::test_offline_tests__only_import_what_the_unit_job_installs`
  —— AST 求**传递闭包**, 离线目录 (含它 import 到的任何 evals / app 模块) 只许
  用单元档装得到的东西。**必须传递地扫**: 当初真正会让 CI 挂掉的
  `test_runner_extract.py` 整个文件里没有 asyncpg 三个字, 它只写了
  `from evals.runner.extract import ...`, 只看第一层的断言会对着它说"没问题";
- 用的是**白名单**而不是黑名单 (`ALLOWED_THIRD_PARTY` = requirements-dev.txt 的投影):
  黑名单只挡得住想得到的那几个;
- 断言自带一条"闭包非空"的自检 —— 否则解析逻辑一坏, 它就变成又一个
  **空集上恒真的全称命题** (本周第四次遇到这个形状);
- `make ci-repro` / `make ci-unit-repro` / `make ci-lint-repro`
  (`scripts/dev/ci-env-repro.sh`): 在全新空 venv 里按 CI 的方式装依赖再跑
  (对策一);
- README 顶部的 CI 徽章 (对策二)。

**顺带盘出来的**: 借这次把 CI 里"还在静默不干活的东西"逐条过了一遍,

## 案例 6 — 把一个可重试的条件当成了终态 (2026-08-11)

**日期 / 模块**: 2026-08-11 / `apps/api/app/services/llm_client.py` (W4 写的
`ArkLLMClient`)。由 W5 第二段跑 C2 臂时撞上, 评审方与实现者共同定位。
**记债不修** —— 修它要动 W4 客户端并重跑受影响的臂, 排 W6。

**缺陷**: 方舟对突发流量有保护, 撞上返回 HTTP 429 `RequestBurstTooFast`,
**厂商明说这是可重试的**。而 `ArkLLMClient` 把任何非 200 一律转成
`LLMUnavailable`, 到状态机那层收成 `dead_letter`。

后果不在评测里, 在生产里: **真实用户撞上限流会看到"任务失联"**, 而正确行为是
退避几百毫秒重试一次 —— 那条请求本来会成功。评测里它表现为整臂莫名其妙少几条
(run `20260810-191319-C2` 的 `DEGRADED.md` 记了当时的现场)。

**根因**: 一个**把可重试条件误分类成终态**的错误。这与案例 1 (租约判死的起算点)、
案例 4 (把"设施答不上"判成"模型答错") 同形 —— **两种性质不同的失败被折叠成同一个
出口**, 而其中一种的正确处置是"再试一次", 另一种才是"就这样了"。
`EvalApiClient._post_with_backoff` 在 runner 那一侧**已经**对 429 做了退避重试
(SPEC-007 第七节点名要求的), 生产客户端反而没有 —— 评测设施比被测系统更健壮,
这个反差本身就是信号。

**为什么现在不修**: 要动 W4 定稿的客户端, 且改重试语义会改变延迟分布与调用计数,
受影响的臂得重跑 (约 ¥11)。W5 第二段已经压着数据集 v1.3 与两臂重跑。

**留给 W6 的具体形状** (不留"以后优化一下"这种话):

- 429 与 5xx 走退避重试 (上限两三次, 指数退避), 其余非 200 仍然是终态;
- 重试次数进 `ai_usage` 或步骤记录 —— **不记的话"限流有多严重"永远查不出来**;
- 配一条测试: `MockTransport` 先回 429 再回 200, 断言任务正常收口且重试计数为 1。
  (只断言"最终成功"不够 —— 那条断言在"根本没重试、第一次就成功"的实现下照样绿,
  与案例 2 是同一课。)
