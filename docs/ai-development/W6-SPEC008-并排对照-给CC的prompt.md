## 任务

做 SPEC-008 第六节那件事: **挑一条已解决事故, 把"模板把事实全铺开"的那份报告与
Agent 写的那份并排放进 README。**

第一、二段都已完成并推上 main。这一轮**只做这一件事**, 不改任何既有代码逻辑。

先读 `docs/specs/SPEC-008-incident-report.md` 第六节 —— 它写清了这个对照要证明
什么、以及**它拿不到什么**。后半句同样重要。

## 花钱的硬边界

- **上限 3 次真实模型调用。** 一次跑通就停; 最多允许两次重试 (例如撞上限流)。
  **跑第 3 次之前必须停下来问人。**
- 跑之前先确认 `.env` 里的 key 就位, **不要把 key 打印到任何地方**,
  不要贴进报告、不要写进脚本、不要 echo 到终端;
- 跑完从 `ai_usage` 把这一条任务的实际花费查出来, 报告里写明:
  **模型名 / prompt_version / 调用次数 / input+output tokens / estimated_cost_cny 合计**。
  "报数字必须带产生它的配置"这条规矩对花费本身同样生效。

## 三件产出

### 一、模板那一份 (确定性, 不花钱)

写一个脚本 `scripts/dev/render_template_report.py`:

- 吃一个 incident_id, 走 `report_task_service.load_fact_pack()` 拿到同一份事实包;
- **把每一条事实都铺成一句话**, 按事实包顺序全量输出 —— 这就是"模板"的定义:
  它不做取舍, 有什么说什么;
- 输出纯文本, 不落库。**绝对不要往 `incident_reports` 插行** ——
  同一条事故已经有 Agent 那份, 部分唯一索引会把它拦住 (SPEC 第七节);
- 它是确定性的: 同一条事故跑两次输出必须逐字节相同, 配一条测试钉住这一点。

### 二、Agent 那一份 (一次真实调用)

挑一条**已解决**的事故。挑选标准 (按顺序):

1. 事实包里**有几条是缺失的** (例如未派单直接刷卡 → `assigned_to` 是"无此记录"),
   这样对照里能看见"缺失也走占位符"这个机制;
2. 时间线不要太短 (至少 4 条), 也不要触发截断 (不超过 20 条);
3. 最好是人工解决的 —— `resolve_policy` 自然缺失, 又多一条缺失事实。

从现有种子/场景里选, **不要为了好看专门造一条**。选了哪条、为什么选它, 写进报告。

走正常路径生成: `POST /incidents/{id}/report` → 等它停在 `awaiting_review` →
`GET /reports/{id}` 拿渲染后的正文。**不要绕过状态机手工拼一份。**

### 三、README 那一节

加在 `## 为什么需要 Agent` 之后 (那一节讲的是同一件事的另一半)。要有:

- 两份报告并排 (模板那份在前, Agent 那份在后), 各自标明是怎么产生的;
- **两个倾向计数** (`bare_fact_attempts` / `dangling_ref_attempts`) 的实际值,
  并说明**为 0 不能说明模型老实, 只能说明这一跑里它没试** (SPEC 第三节原话);
- 一段话说清这个对照证明了什么: 模板什么都说了、又长又平; Agent 那份短,
  说的是该说的那几条。**取舍是模型干的活, 事实是代码给的。**

**README 里的三条禁令 (SPEC 第六节与第三节定死的)**:

1. **只说这是一个例子, 不给任何百分比。** 没有覆盖率与冗余率那两个数,
   "模型的价值在取舍不在产生事实"这句话是**靠一个例子撑着, 不是靠一个统计量** ——
   照这样写, 不要把一个例子说成一个结论;
2. **不出现"幻觉率"这个词。** 能说的是"模型在正文里写不出自由数字与专名
   (语法层面拦住), 而它想写的次数被记了下来";
3. **把"用了对的占位符但放错句子拦不住"这条已知边界一并写出来。**
   它是这套机制真正的边界, 被问到要照实说, 不许只摆好看的那一半。
