## 一、与 SPEC 不一致的地方 (含我认为需要评审方确认的)

1. **`user_task_quota_daily` 的 limit 列改名 `limit_count`**。SPEC 第七节写的是
   `CHECK (used <= limit)`, 但 `LIMIT` 是 SQL 保留字, 裸用要处处加引号且极易写出
   坑下一个人的 SQL。语义不变。

2. **`llm_spend_daily` 比 SPEC 的 DDL 多一条 `CHECK (spent_cny >= 0)`**
   (`llm_spend_daily_nonnegative`)。易错点四要求回补用 `GREATEST(0, ...)` 兜住
   不减成负数 —— 这条约束把"不许为负"从应用层的自觉变成数据库的事实, 与整个
   SPEC "只有第三层是真的"的路数一致。若认为多余可以删, 有测试单独守它
   (`test_spend_check__negative_spent_rejected`), 删约束时测试会告诉你。

3. **两个 429 的"错误码与文案分开", 码放在 `X-Error-Code` 响应头**, 不放响应体。
   原因: `apps/web/src/api/client.ts` 的 `ApiError` 把 `detail` 直接
   `String(...)` 当文案渲染, 把 detail 改成结构体会让前端显示
   `[object Object]`, 而 `apps/web/` 本段冻结。三种 429 的码:
   `capacity_exceeded` (系统忙, 等会儿再来) / `daily_budget_exhausted`
   (全站额度, 明天再来) / `user_quota_exhausted` (账号配额, 明天再来或换账号),
   文案各自成句, 各配一条测试。**顺手给既有的 CapacityExceeded 429 也加了码**
   (只加响应头, detail 原文未动, 既有测试原样通过)。

4. **回补的触发点越出了"路由层只动 429 那条路径"的字面边界一处**:
   回补钩子 (`budget_service.refund_when_done`) 挂在 `spawn_task` 返回的后台
   协程的 done_callback 上, create 与 **reply** 两个 spawn 点各加了一行。
   不挂 reply 那行的话, 经澄清恢复后才走完的任务永远不回补。挂在路由层而不是
   `agent_runtime` 里, 是因为 runtime 不在本段可写清单内; 若评审方愿意让
   runtime 自己收口, 这两行可以下沉 (行为等价)。

5. **回补金额用回补时刻的 `agent_task_hold_cny` 配置值**。预扣额没有单独落库
   (SPEC 第七节只批了三张表), 所以预扣与回补之间改配置会造成台账偏差 ——
   偏差只影响当天额度的松紧, 永远不会违反 CHECK, 也不会跨天累积
   (次日新行从零起算)。已写进 `budget_service` 注释。

6. **四类任务的预扣不回补** (代码注释已写): 被租约清扫收尸的 (`lease_lost` /
   清扫先到)、进程关停被 cancel 的、停在 clarifying 直到超时判死的、本轮结局
   `not_claimed` 的。方向刻意保守 —— 宁可当天额度少用一截, 不可多放行;
   次日自然清零。若要收这笔尾账, 得让清扫循环 (agent_runtime) 也调回补,
   属于上一条同一个边界。

7. **重置脚本的通行证判据是"demo_marker 里有那一行", 不是"有这张表"**。
   SPEC 第三节写"库里没有一张 demo_marker 表就当场退出", 但迁移 0010 给**每个**
   库都建了这张表 —— 按字面实现, 护栏对一切跑过迁移的库形同虚设。行由生产种子
   写入 (第二段), "跑过迁移"与"是演示库"因此是两件事。表不存在同样拒绝
   (迁移都没跑过的库更不该被它碰)。

8. **重置脚本刻意不清三类表** (模块注释里有全文):
   花钱台账两张 (重置不能变成"把今天预算清零再来一轮"的按钮)、demo_marker
   (通行证要活过重置)、身份与库存表 (users/zones/devices/sensors/employees ——
   种子对它们是幂等 upsert, 访客也没有改它们的接口; employees 被
   users.employee_id 引用, 清了要连座)。

9. **重置后 API 进程的内存状态是陈的** (策略引擎缓存、已加载的发布策略)。
   脚本只管数据库; 04:00 的 cron 需要在重置后重启 api 容器或触发引擎重载 ——
   这属于第二段 compose 的事, 先记在这里别丢。

10. **SPEC 第二节"前端显示今日剩余额度"本段未做**: 那是 apps/web 的事 (冻结),
    且 SPEC 自己把它归为"提示, 不是护栏"。

## 三、变异测试 (SPEC 第九节 1/2/3/6, 逐条实跑)

每条: 怎么改坏 → 哪条红 → 红成什么形状。做法: 改坏实现 → (涉及 DDL 时用
未变异/已变异的迁移把 sentinel_test 降到 0009 再升回) → 跑对应测试 → 还原。

**1. 去掉 `llm_spend_daily` 的 CHECK** (迁移里删 `llm_spend_daily_within_limit`,
重建 schema): **4 条红** ——
`test_spend_check__direct_update_beyond_limit_rejected` 红成
`DID NOT RAISE CheckViolationError`;
`test_budget_zero__...` 红成 `AssertionError: {"ok":true,"task_id":1,
"created":true,...}` (预算 0 的库里任务照建, 201);
`test_concurrent_creates__...` 红成 `[201, 201, 201, 201, ...]` (十条全进);
`test_guardrail_tables__exist_with_named_checks` 红在约束名集合不含
`llm_spend_daily_within_limit`。

**2. 预扣改成事后记账** (reserve 改为"SELECT 合计, 够就放行, 不写库"):
`test_concurrent_creates__only_holds_within_budget_succeed` 红成
`AssertionError: [201, 201, 201, 201, 201, 201, ...]` —— 十个请求同时读到
"还有余额", 额度只够 3 笔却全放行。**值得记录**: 单独跑 limit=0 那条用例在此
变异下**仍绿** (应用层检查也挡得住单发请求) —— "预扣在事务里"与"先查再扣"的
差别只有并发用例看得见, 这正是它必须存在的理由。

**3. 删掉重置脚本的 demo_marker 检查** (护栏整段删除):
`test_reset__refuses_without_marker_and_touches_nothing` 红成
`AssertionError: stdout=已清空 16 张演示数据表 / assert 0 == 2` ——
脚本在非演示库上退出码 0 并真的清了库, 护栏没了立刻现形。

**6. 判据恒真检验** (把路由层的预扣调用整个删掉): 6 条护栏用例中 **5 条红**,
`test_budget_zero__...` 红成"期望 429 实得 201" —— 断言跑在 limit=0 这条
**真的会打满额度**的用例上, 预扣一消失它就报, 不是恒真;
唯一仍绿的是 `test_capacity__429_carries_its_own_code` (它测的是槽位, 与预扣
无关, 绿是对的)。limit=0 直接设零、不等自然花完, 遵守第八次记下的那条规矩。

变异 4 (Dockerfile COPY) 与 5 (compose ports) 属第二段, 未做。
