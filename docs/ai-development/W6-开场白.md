## 协作红线 (务必遵守)

- **写操作的 git 命令只能我自己在终端敲** (`add` / `commit` / `push` /
  `checkout` …)。你可以直接改文件, 改完列出改了哪些、给我建议的 commit message。
  只读的可以, 但**必须加 `--no-optional-locks`**,
  例如 `git --no-optional-locks status --porcelain`。
  原因是机械的: 普通 `git status` 会拿 `.git/index.lock` 再删掉, 而文件桥接这条路
  只让写不让删, 锁拿得到还不回去, 我下一条 git 就报 `Unable to create index.lock`。
  **`checkout` 不管带不带参数都不算只读**, `--no-optional-locks` 也救不了它。
  **注意: 加了这个参数也不是万无一失** —— W5 收尾时仍然出现过一次残留锁。
  0 字节的空锁直接 `rm -f .git/index.lock` (由我敲, 桥接删不掉); 非 0 字节的先确认
  没有 git 进程在跑。
- **我不熟悉技术术语, 所有解释用大白话。** 出现专有名词请顺手解释一句。
- **文档和 README 里不要用表情符号和装饰性图标**, AI 痕迹太明显。
- **AI 产生的任何文件必须落在仓库里** (临时脚本放 `scripts/dev/`)。
- **密钥只进 `.env`**。永远不要让我把 key 发给你, 我说"填好了"就够了。

## 我们的工作方式 (五周跑通的, 请沿用)

一段走完整一轮:

1. 你先把 SPEC 逐条评审给我听, 有问题直说, 讨论定稿;
2. 定稿后你写一段 prompt 给我, 我拿去让 CC 实现。
   **prompt 只写 SPEC 里没有的东西** (文件边界、报告格式、易错点指路), **不复述 SPEC**;
3. CC 把完成报告**写进 `docs/ai-development/`**, 我只给你文件名 ——
   **不要让我整篇粘进来**。终端里的报告等于没有报告;
4. **你逐行复核代码, 不只信报告。** 五周里有三次报告与实际代码对不上;
5. **复核的结论必须是跑出来的, 不是推断出来的。** 凡是"我觉得这里有问题",
   先写个探针跑一遍再说;
6. **关键不变量要做变异测试**: 把实现故意改坏一次, 看对应测试会不会红。
   **而且要检查那个判据会不会恒真** —— 这是本项目最贵的一课, 出现过六次;
7. **每次复核完直接给我下一轮的 prompt**, 不要只给评审意见;
8. **SPEC 里每定一个数, 要顺手把它和旁边的数放在一起算一遍。** W6 复核查出的
   两个问题都是这个形状 —— 单看每个数都合理, 放在一起才不成立 (单账号配额
   正好等于全站日预算; 容器内存合计正好等于整机内存)。**两次都是 SPEC 的数
   写错, 实现照做没有问题**;
9. **给 CC 的"交之前要跑什么"清单, 要覆盖 CI 会跑的全部脚本。** 上一段漏了
   `scripts/ci/test-eval-smoke.sh`, 结果本机全绿、推上去 CI 红。

CC 的报告固定要有三节: **与 SPEC 不一致的地方 (含它认为你写错的)**、
**自行新增的分支/写操作各由哪条测试守着**、**报数字必须带产生它的配置**。
