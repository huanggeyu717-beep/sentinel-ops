## 第一部分：六处修补

**一、录制脚本挪进仓库，并加调用次数硬上限。**

现在它在 `/private/tmp/claude-501/.../scratchpad/` 下。三个问题：`/private/tmp`
重启即清；它不在版本库里；**而它是整个项目唯一会真实花钱的代码，恰恰没经过复核**。

挪到 `scripts/dev/record_cassettes.py`。另外**加一个整脚本的调用次数硬上限**
（建议 20 次，超出直接退出并说明），并在 `--help` 里写明。录制脚本失控是这类工具
最常见的翻车方式，而它跑的时候人多半没盯着。

**二、Postgres 换端口 5433。**

宿主机的 Homebrew `postgresql@17` 占着 5432，Docker 那个起不来。**让本项目让路，
不动 brew 那个**——brew 那个是另一个项目在用、可能有数据；而本项目的端口只写在自己
的配置里，改完对 CI 没有任何影响（CI 的 Postgres 是独立起的）。

**把 5432 这个数字在仓库里出现的地方全找出来一次改完**，别只改看得见的那一处——
这与 `.python-version` 那条待办（3.12 硬写四遍）是同一类问题。改动处就地注释写明
为什么不是默认端口。容器内部仍是 5432，改的是对宿主机暴露的那一侧。

**三、`config.py` 的 LLM 默认值改对。**

`llm_model` 还写着 `doubao-lite-32k`（W1 填的，早已不存在），两个单价
`0.042 / 0.083` 看形状是按美元猜的。改成上面 `.env` 那四个真值，
**并在单价旁边就地注明是人民币**，以及为什么它暂时进一个名叫 `_usd` 的列
（理由见 SPEC-002 第九节末尾，那一列的改名留给 W5，本轮不要动迁移）。

**四、核对请求路径：`/chat/completions` 还是 `/responses`。**

控制台给的示例 curl 用的是 `POST {base_url}/responses`，而 `ArkLLMClient` 实现的是
OpenAI 兼容的 chat completions。**同一个 base_url 下的两个不同接口，请求与响应
格式不一样。**

确认你发的是哪个、以及工具调用（function calling）在该接口下的字段名对不对
（`tools` / `tool_choice` / 响应里的 `tool_calls`）。这件事打桩阶段完全暴露不出来，
第一次真调用就会撞上。**在报告里写明你核对的结论和依据。**

**五、`list_sensors` 带上"这个探头有没有上报过"。**

dev seed 里有一个占位传感器 `id=0`（挂在 `UNKNOWN_DEVICE` 上，`app/db.py` 第 145 行
有注释说明是刻意放的，用来让前端"未定位"分支在演示数据里可见）。它现在以
`active: true` 的正常姿态进了模型的库存清单——模型完全可能给一个从来不说话的占位
设备写一条监控策略，而静态验证器会放行（它确实在 `sensor_ids` 里）。

**W2 给 `/status` 打过同一仗**：装了却从没上报的探头、上报了却没登记的探头，
两个方向都不能吞，为此加了 `never_reported`。把同一个口径搬到 `list_sensors`，
让模型看得见"这个探头装了但从没说过话"。`CANONICAL_INVENTORY` 跟着更新。

**六、`CANONICAL_INVENTORY` 的 docstring 里那个理由是错的，要改。**

它写着 sensor 0 / `UNKNOWN_DEVICE`"是 ingest 测试跑过才有"。**不是**——它在 dev seed
里，每个全新库都有，`db.py` 里有注释。评审方另外核过：测试中没有任何一处往
`sensors` / `zones` / `devices` / `employees` 插行，四个只读查询都带 `ORDER BY`，
**按查到的证据，库存不会漂**。

钉死库存这件事本身留着（让 cassette 不依赖库状态是好卫生），但**理由必须改成真的**，
否则下一个人会去追一个不存在的问题——这就是"注释和事实走散"。

**顺带请你说清楚你当时到底观察到了什么**：如果确实见过库存漂移，那是另一个我们没
找到的原因，值得挖出来；如果只是看见 `id=0 / UNKNOWN_DEVICE` 长得像垃圾数据就推断
成测试污染，就照实说。**这一条不影响评价，说错了改过来就行**——本项目立过的规矩是
"凡是我觉得有问题，先写个探针跑一遍再说"。

## 第二部分：补录三件套

修补做完、`make lint` 与全量测试绿了之后再开始。这是本项目**第一次真实花钱**，
按 SPEC-002 第八、九节做。

**跑之前先做一次最小连通性验证**：用一次真实调用确认 key、base_url、模型 ID、
请求路径四样都对。一次调用不到一分钱，比录到一半失败再回头查便宜得多。

**关于断言，有一条口径必须先说清楚。**

你在上一份报告里写"如果真模型的产出不同形，以录制到的真实行为为准调整断言"。
**这条按字面执行是反的**：那三个断言（生鲜区、两个探头、通知 manager）是招牌句
编译正确的定义。真模型编不出来，那是 **prompt 不够好**，不是断言太严；照着模型的
实际输出改断言，验收 1 从此什么都不证明了。

**断言分两层**：

- **不许为迁就模型放宽的**：引用的 zone / sensor 真实存在、`target_role` 在册、
  `cooldown_s` 合法、**静态校验必须通过**、招牌句那三个要素齐全；
- **可以协商的**：挑了 `zone` 还是 `sensor` 作用域、`window_s` 取 180 还是 200、
  动作顺序——这些确实有多种合理写法，随录制到的行为调整没问题。

第一层要是过不去，**改 prompt 重录，不要改断言**。真改不动就停下来说，
连同模型的实际输出一起报上来，我们再判断是 prompt 的问题还是 SPEC 的要求不合理。

**验收 4 的 cassette** 按上一轮定的做：允许手工编辑造出那个错 zone，
但必须在文件里就地标注手编了哪一段（SPEC-002 第九节第 3 条）。
