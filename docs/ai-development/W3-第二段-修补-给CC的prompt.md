## 一、遥测路径没有状态回退（这条会真出事）

你在 `tick()` 里做了快照 + 失败回退 + 域事件放回队首，理由写得也对。
**但 `on_telemetry()` 一点保护都没有，而道理完全一样。**

我实测过：让 `open_incident` 抛错模拟数据库出错，第一次调用后请求事务回滚、
事故没开成，但引擎状态已经推进（`wet_since={1: 1000}`、`last_fired={(1,1): 1000}`）；
同一传感器再报湿时 `open_incident` 被调用 **0 次**——因为
`sensor_state_changed` 是边沿触发，持续报湿不构成新边沿。**这张单永远补不回来。**

要做：`on_telemetry` 也照 `tick()` 那样做状态快照与失败回退。
两条路径的保护要一致，别再留不对称。

## 二、tick 的状态回退没有任何测试守着

8 条 runtime 测试里没有一条向 `tick()` 注入失败事务——把 `self._state = state_backup`
那行删掉，全套照样绿。这和第一段验收 6 那个问题是同一类：代码对，但保护没被锁住。

要做：**两条路径各配一条注入失败事务的测试**，断言失败后引擎状态与域事件队列

确认测试真的会红，**报告里贴红灯输出**。

## 三、引擎状态没有上界

已解决的事故永远留在 `state.incidents` 里，从不清理。实测 5000 个完整生命周期之后
全部 5000 条还在，而 `tick()` 每轮要对它做一次快照（36 毫秒），
`incident_elapsed` 每个 tick 还要遍历一遍——开销随「历史上开过多少单」增长，
不是随「当前有多少未解决」。

项目自己在 SPEC-005 决策 4 立过「内存里的东西必须有上界」（演练历史照此只留最近 N 次），
这里没照做。

要做（规则见 `SPEC-001` 第四节末）：

- **未解决的事故一条都不淘汰**——它们的数量数据库已经封住了（partial unique index
  保证同一传感器最多一条），上界就是传感器数；
- **已解决的保留最近 N 条**，`SENTINEL_ENGINE_INCIDENT_HISTORY` 默认 200，超出丢最旧；
- 事故被淘汰时**它名下的 `tick_edge` 与 `last_fired` 一并清理**，否则只是换个容器继续涨；
- `EngineState` 的 docstring 里写明**清内存不丢历史**（事实源是 `incidents` /
  `incident_events` / `policy_runs`），免得后来者以为动它会丢数据而不敢清；
- 补测试：跑够多的开单/解决循环之后，`incidents`、`tick_edge`、`last_fired`
  三个容器都不超过上界，且未解决的一条没丢。

回放模块用的是同一个 `EngineState`，改完请确认第一段那 54 条测试仍然全绿。
