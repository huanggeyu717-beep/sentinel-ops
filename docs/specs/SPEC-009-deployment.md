# SPEC-009 · W6 部署与公开演示环境

> 状态: **草案** (2026-08-22 起草, 待评审定稿)
>
> ADR-004 已经定了**架构**(Lightsail 单实例 + compose + Caddy, 生产形态用
> Terraform 描述不开支)。本 SPEC 定的是**怎么做与验收是什么**, 并且按拍板结果
> 分成两半: **先在本机把生产形态整条跑通**, 机器等投递前再开 —— 那 $8 压到
> 最短的几个月里。
>
> 它是 JD 第 7 节 P0 三项里**唯一还空着的一项** (Docker Compose 一键启动、
> GitHub Actions 都已满足)。所以它不是加分项, 是缺口。
>
> 起草时逐条核对过 `docker-compose.yml`、`apps/web/Dockerfile`、`.env.example`、
> `config.py` 与 CI 的现状, **发现的五处问题写在第一节与第四节**。

## 目标

1. **一份生产形态的 compose 覆盖层**, 本机可以完整起来并通过验收; 将来开机器时
   跑的是**同一份文件、同一份镜像**, 不是另抄一套。
2. **花钱护栏下沉到数据库**: 公开演示里 Agent 真调模型, 但今日总花费与单账号
   配额由**约束**兜住, 不靠应用层自觉 —— 与 ADR-007 同一手。
3. **演示数据每天自动重置**, 并且重置脚本**拒绝在非演示库上运行**。
4. **CI 的 docker job 从"只 build"改成"起容器跑断言"**, 并补 build `web`
   与 `sim-replay`。这不是并列的第四件事, **是部署的前置** —— 要部署的正是那个
   从未被构建、更没被启动过的镜像。
5. **一份可逐条打勾的开机手册**, 含成本护栏与**关机路径**。
6. 全程 **¥0 模型花费**: 本 SPEC 一次真实调用都不需要。

## 非目标 (v1 明确不做, 理由随附)

- **不做 Terraform apply**。ADR-004 已定: 生产形态只描述、不开支, `plan` 在 CI 跑通即可。
- **不做多实例、零停机、蓝绿**。单人单实例, 切换阈值 ADR-004 已写死。
- **不做真域名与 Let's Encrypt 证书签发**(本阶段)。本机用 Caddy 的内部 CA 验证
  **反代与 HTTPS 这条链路成立**, 真证书等开机器那天。这条限制写进第六节, 不含糊。
- **不做 OTel / 日志聚合**。W6 已砍。
- **不做真实邮件与 LED 出口**。它们在不变量 1 的能力之外。

## 一、生产形态与开发形态差在哪 (逐条列出, 每条都是现状里的真问题)

现在的 `docker-compose.yml` 是**开发用**的, 直接拿去上线有五处会出事:

| # | 现状 | 上线后果 |
|---|---|---|
| 1 | `db` 把 5432 映射到宿主机 5433 | **数据库端口暴露在公网**。默认口令是 `sentinel`/`sentinel` |
| 2 | `api` 暴露 8000、`web` 暴露 5173 | 绕开 Caddy 直连, HTTPS 形同虚设 |
| 3 | `SENTINEL_ENVIRONMENT=development` | Secure cookie 不生效, 且默认 JWT 密钥**不会**被拒 |
| 4 | `SENTINEL_JWT_SECRET=dev-only-change-me` | 任何人可以自己签一个 admin 会话 |
| 5 | 种子里五个演示账号**同一个弱口令** `sentinel-demo` | admin 账号等于没有密码 |

**做法: 用覆盖层 `docker-compose.prod.yml`, 不用 profile。**
这是一个机械理由, 不是偏好: **compose 的 profiles 只能决定服务起不起, 不能撤掉
已经声明的 `ports`。** 要把 1、2 两条端口收回来, 只能靠覆盖层把 `ports` 覆写成空。

覆盖层做四件事: 撤掉 db/api/web 的宿主机端口; 加一个 `caddy` 服务占 80/443 并
反代 `/api/*` 到 api、其余到 web; 注入生产环境变量; 把重启策略设成
`unless-stopped`。

**第 5 条单独定一条决策**: 生产种子**不写入 admin 账号**, 公开的只有
`viewer` / `operator` / `manager` 三个演示账号, 口令仍公开 (它们本来就是给人试的)。
需要 admin 时由开机手册里一条命令**当场生成随机口令**创建。
理由: 演示的价值在于"你自己点点看", 而 admin 能做的事 (改角色、改权限) 不是
演示内容, 只是攻击面。

## 二、花钱护栏: 预扣 → 调用 → 回补, 约束在数据库上

**威胁模型说清楚**: 一个能点开的 Agent, 就是一个任何人都能替我按的花钱按钮。
公网上不需要恶意, 一个好奇的人循环点几十次就够。所以护栏必须在开门之前存在,
而且**不能是应用层的一个 if**。

三层, **只有第三层是真的**(写法照 SPEC-002 第五节那张"四层只有前三层是安全措施"的表):

1. **前端显示今日剩余额度** —— 提示, 不是护栏;
2. **应用层检查配额** —— 挡住诚实用户, 挡不住并发;
3. **数据库约束** —— `llm_spend_daily` 一行一天, `CHECK (spent_cny <= limit_cny)`。
   **超了那条 UPDATE 物理上写不进去**, 于是调用发不出去。

**流程是预扣, 不是事后记账**, 因为调用之前不知道会花多少:

```
建任务 → 同一事务里 UPDATE llm_spend_daily SET spent = spent + 预扣额
       → CHECK 失败 = 今日额度用完, 任务根本建不起来 (返回 429 + 人话)
       → 任务跑完, 按 ai_usage 的真实合计回补差额
```

- **预扣额取单任务最坏情况**: `agent_max_llm_calls` (12) × 单次调用的保守估值。
  宁可预扣多了跑完回补, 不可预扣少了。
- **事后记账挡不住并发**: 十个人同时点, 每个都读到"还有余额", 十条任务全起来。
  预扣是在同一个事务里做的加法, 并发下由数据库串行化。
- **这是本项目第三次用"先预留再干活"这一手**: W3 的 `start_drill` 同步函数、
  W4 的 `reserve_task_slot()`, 现在是钱。前两次预留的是内存里的东西, 这次预留的
  东西在数据库里, 因为它必须跨进程、跨重启。

**账号配额**同表同事务: `(user_id, day)` 每日任务数上限, 默认 5 条。
理由是钱以外的一层: 一个人循环点 100 次会把当天额度占光, 让后面来的面试官
什么都试不了 —— **额度耗尽的体验比额度存在更糟**。

**配置项** (全部进 `config.py`, 默认值写在这里): 日总预算 `¥3`、
单账号每日 5 条任务、单任务预扣 `¥0.60` (= 12 次 × 保守 ¥0.05)。
按 W5 实测, 一条策略任务中位约 ¥0.05–0.17, 所以 ¥3/天 大约够 20–40 条真实体验。

## 三、演示数据每天重置

公网演示跑三天必然被点乱: 策略被发布、事故被解决、审批被批完。

- 每天 04:00 (服务器 UTC) 重置: 清演示数据 → 重跑种子 → 回放那 344 条真实读数。
  **幂等已经验证过** (W1: 重复执行输出"提交 1258 条, 新增 0 条"), 这次派上用场。
- **重置脚本必须拒绝在非演示库上运行**: 库里没有一张 `demo_marker` 表 (由生产
  种子写入) 就当场退出, 非零码。**这是一段会删数据的代码, 它的护栏比它本身重要。**
- 重置会清掉访客建的策略与报告 —— README 写明, 并在界面顶栏显示"每天 04:00 重置"。

## 四、CI 的 docker job: 从"只 build"改成"起容器跑断言"

现状 (`docker compose build api device-sim`) 拦得住"快炸"(缺 COPY 源, build 当场失败),
**拦不住"慢炸"**(根本没写的 COPY 行 —— W4 的 seed CSV 就是这么漏的: build 全绿、
容器起得来、界面打得开, 只有有人点"模拟"才断)。

**顺手要修 `apps/web/Dockerfile` 的两处**, 它们上线时会咬人:

- 只 `COPY apps/web/package.json`, **不 COPY `package-lock.json`**, 用的是
  `npm install` 现解现装 —— 服务器上装到的依赖版本可以与本机、与 CI 都不同。
  改成 COPY 锁文件 + `npm ci`;
- **这个 Dockerfile 在 CI 里一次都没被构建过** (docker job 只 build api 与 device-sim),
  而 README 承诺的是"一键 `docker compose up` 复现"。

新的 docker job 要断言这五条:

1. `compose up -d` 之后 `/health` 返回 200 (**迁移真跑过、`app.main` 真 import 得进去**);
2. `/status/sensors` 返回 5 个传感器 (**种子真写进去了**);
3. 容器里 `seed/waterlevel_readings.csv` 路径存在 (**W4 那笔债的钉子**);
4. Caddy 的 `/api/health` 与首页各返回 200 (**反代真的通**);
5. `web` 与 `sim-replay` 也在 build 目标里。

## 五、开机手册 (`docs/deploy-runbook.md`, 本阶段只写不执行)

## 六、本机验证的边界 (照实写, 不含糊)

本机跑通生产形态, **验不到**这四件:

1. **真证书**。Caddy 用内部 CA 能验"反代 + HTTPS 链路成立", 但签不到
   Let's Encrypt 的真证书 —— 那要一个真域名和一次真的 ACME 挑战;
2. **公网延迟与带宽**;
3. **Budgets 告警是否真会发到邮箱**;
4. **1 GB 内存够不够**。Lightsail Micro 只有 1 GB, 要同时跑 Postgres 16 +
   FastAPI (含 tick 循环与租约打卡) + Caddy + nginx。**这一条本机可以逼近**:
   用 `deploy.resources.limits.memory` 把整组压到 1 GB 跑一遍验收,
   **跑不过就是跑不过, 不要等开了机器再发现**。这是本节唯一一条我认为
   **必须**在本阶段做掉的。

## 七、数据库变更 (迁移 0010)

1. 新建 `llm_spend_daily`:

```sql
CREATE TABLE llm_spend_daily (
    day date PRIMARY KEY,
    spent_cny numeric(10,4) NOT NULL DEFAULT 0,
    limit_cny numeric(10,4) NOT NULL,
    CHECK (spent_cny <= limit_cny)
);
```

2. 新建 `user_task_quota_daily (user_id, day)` 主键 + `used int` +
   `CHECK (used <= limit)`;
3. 新建 `demo_marker` 单行表, 由生产种子写入, 重置脚本的通行证。

**号段说明**: 本 SPEC 占 `0010`; SPEC-008 的迁移**顺延为 `0011`** (已同步改
SPEC-008 第七节)。两份 SPEC 都写 0010 的话, Alembic 会因为**多个 head 直接报错**
而不是静默乱套 —— 这正是 ADR-006 换掉"按文件名排序"的理由, 这次是第一次真用上。

## 八、验收

- `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` 起得来,
  **宿主机上只有 80/443 两个口是开的** (用 `ss -ltn` 逐个数, 不靠印象);
- 直接访问 `http://localhost:8000` **连不上**(端口已收回), 走 Caddy 能访问;
- `SENTINEL_JWT_SECRET` 保持默认值时 **API 拒绝启动**(SPEC-004 埋的那一手, 这是
  它第一次真生效), 且错误信息说人话;
- 生产种子里**没有 admin 账号**, 三个演示账号能登录;
- **日预算打满之后**, 再建 Agent 任务返回 429 + 人话, 且**绕过应用层直接 UPDATE
  也写不进去**(数据库 CHECK 拦住);
- **并发十条任务只有额度内的那几条能建起来**(预扣在事务里);
- 单账号当天第 6 条任务被拒, 换一个账号仍可用;
- 重置脚本在**没有 `demo_marker` 的库上拒绝运行**并返回非零码;
- 重置之后 `/status/sensors` 仍是 5 个、事故清空、真实读数 1258 条在位;
- **整组限制到 1 GB 内存**跑完上面全部验收;
- CI 的 docker job 五条断言全部生效, `web` 与 `sim-replay` 在 build 目标里;
- `make lint` 与全部测试绿。

## 九、变异测试 (每条把实现改坏一次, 看测试红不红)

1. 去掉 `llm_spend_daily` 的 CHECK → 超预算的任务应该建得起来 → **有测试红**;
2. 把预扣改成事后记账 → 并发用例应该击穿额度 → **有测试红**;
3. 去掉重置脚本的 `demo_marker` 检查 → **有测试红**;
4. **删掉 `apps/api/Dockerfile` 里 seed CSV 那行 COPY → CI 的 docker job 应该红。**
   这一条是 W4 那笔债的正主, 也是这次唯一能证明新 job 真的比旧 job 强的变异;
5. 覆盖层里把 `ports` 覆写删掉 → 端口断言应该红;
6. **判据会不会恒真**: 额度用尽那条断言必须跑在一条**真的会打满额度**的用例上
   (把 limit 调成 0 而不是等它自然花完), 否则"从没超过"与"检查失效"长得一样。
   这是本项目第八次记这件事。

## 已知边界 (写进代码注释, 不只写在这里)

- **单点**。实例挂了演示即不可用, 缓解是本地 compose 始终可用且 README 显式说明
  (ADR-004 后果一节已写);
- **预扣是保守估值**, 实际花费低于预扣时当天额度用不满 —— 这是为了安全付的代价,
  照实说, 不要在界面上把"剩余额度"说得比实际紧;
- **配额按账号, 而账号是公开的**。真要刷, 五个账号轮着用就是五倍。
  日总预算那一层才是真正的地板, 账号配额只是让正常人不至于把额度一次占光;
- **429 被当成终态那笔债 (defect-log 案例 6) 在这里会更显眼**: 演示环境撞限流的
  概率比本机高。修它要动 W4 客户端。
