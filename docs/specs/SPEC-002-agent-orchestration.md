## 目标

把管理员的一句人话 ("生鲜区两个探头三分钟内都湿了就通知这个区的主管") 变成一条
**已通过静态校验、已在历史数据上回放过、正在等人审批**的 Policy 草案。

Agent 只做四件事: 理解、编译、听不懂就问人、把校验与模拟的结果摆到人面前。

**它没有任何对外可见、不可撤销的动作权限** —— 发布那一步由人点, 且被数据库外键强制
(ADR-007)。这句话的精确含义见下面"不变量 1 的精确措辞"一节。

W3 已经把大部分底座做好了: DSL 是封闭白名单 (SPEC-001)、双层验证器给结构化错误码、
生命周期接口按本 SPEC 需要的形状实现 (SPEC-006 第五节)。W4 是在这些之上包一层,
但**不是纯粹的包一层** —— 第二轮评审确认还缺三个只读 service、两处 W3 函数要改签名、
数据库缺六列一表 (见第七节迁移清单)。

## 非目标

- **自由代码执行、让模型直接调数据库**: 与整个设计前提冲突。
- **通用对话**: 本 SPEC 的多轮**只用于澄清歧义**, 不做"把已经做好的策略再改改"那种
  自由聊天。后者仍然是"再说一句话、开一条新任务"。这条线必须守住,
  否则 v1 会滑向做一个通用聊天机器人。
  (初稿写的是"不做多轮对话式修改", 与状态机里的 `clarifying` 直接打架 ——
  状态机要求能接住人的回答, 那就是多轮。已在第二轮评审改掉, 见文末决定 3。)
- **跨策略编排**: 模型一次只处理一条策略。
- **自动发布**: 永远不做。这是项目的核心主张。

## 一、Agent 以什么形式存在: 后台任务, 不是一个 HTTP 请求

**这一节是第二轮评审新增的, 它是本 SPEC 最大的一个洞。**

初稿只写了 Agent 内部怎么想, 没写这个 Agent 在系统里以什么形式跑。而"决定 4: 模拟
同步跑"只是**其中一步** (实测 16 毫秒那一步), 一整轮任务包含好几次 LLM 往返,
预算是 120 秒 —— 两件事被混在一起了。

**定死: 任务在后台的 asyncio 任务里跑, HTTP 接口立刻返回。**

```
POST /agent-tasks {input}          -> 立刻返回 {task_id, status: running}
GET  /agent-tasks/{id}/events      -> SSE, 一步步推
GET  /agent-tasks/{id}             -> 当前快照 (SSE 用不了时的兜底)
POST /agent-tasks/{id}/reply       -> 人回答澄清问题 (见第三节)
```

**为什么不能同步跑完再返回**: 一是 Trace UI 的 SSE 会变成摆设 —— 人拿到响应时全部
步骤早已结束, "一步步冒出来"是假的, 而这个效果正是本功能要展示的东西; 二是一个跑
120 秒的请求会被浏览器、nginx、负载均衡各掐一刀。

后台任务的形态**照抄 W3 的 tick 后台任务** (`policy_runtime.tick_loop`): 应用启动时
拉起、关停时干净取消、已知边界写进代码注释。

**已知边界 (写进代码注释, 不只写在这里)**:

- 多实例部署时每个实例各跑各的任务, 靠租约区分归属 (第二节), 不做选主;
- 进程重启会让在跑的任务失联, 由租约清扫收尾 (第二节);
- SSE 连接是进程内的, 多实例下前端可能连到没跑这个任务的实例上 ——
  W4 单实例, W6 若扩多实例需要改用数据库轮询或消息总线转发。

## 二、租约: 任务失联了怎么办

**先承认一件事: 一个进程没法判断另一个进程是死了还是只是很慢。** 这两种情况从外面看
长得一模一样 (垃圾回收停顿、磁盘卡住、虚拟机被暂停调度, 都会让进程僵住几十秒)。

所以做法不是"确定它死了", 而是 **"把它踢出局, 并且保证它就算活过来也写不进去"**。
三件事:

### 1. 打卡

`agent_tasks` 加两列: `runner_id` (谁在跑, 进程启动时生成一个随机串) 与
`heartbeat_at` (最后一次打卡时间)。任务运行期间每 `SENTINEL_AGENT_HEARTBEAT_SECONDS`
(默认 **5** 秒) 更新一次。这件事**搭在已有的后台循环上**, 不新开一个。

### 2. 判死靠时间差, 不靠"启动"这个事件

```sql
UPDATE agent_tasks
   SET status = 'dead_letter',
       error_detail = '任务失联, 可能是服务重启或进程异常'
 WHERE status = 'running'
   AND heartbeat_at < now() - interval '60 seconds'   -- SENTINEL_AGENT_LEASE_TIMEOUT_SECONDS
```

**判死阈值必须远大于打卡间隔** (默认 5 秒打卡 / 60 秒判死, 十二倍)。改小一点平时看不出
问题, 一次垃圾回收停顿就会误杀正在好好跑的任务 —— 这是那种"上线才炸"的数字,
所以两个值都进 `config.py`, 且在那里就地注释写明它们的比例关系。

**初稿写的"启动时把所有 running 一律标成 dead_letter"是错的, 已删除。** 两个毛病:
它假设"启动"等于"上一个进程死了"(不成立, 多实例下实例 B 重启会把实例 A 正在跑的任务
误杀); 而且它对"进程僵住但没重启"这种情况完全无效。

**"从没打过卡"也算失联**: 进程在建任务与认领之间死掉的任务 `heartbeat_at` 是 NULL,
只按 `heartbeat_at` 判会让它永远挂在 `running` 上堵住去重索引。所以判死条件是
`heartbeat_at 过期` **或** `heartbeat_at 为 NULL 且距上一次"变成 running"超过阈值`。

**注意这里的起算点必须是"上一次变成 running 的时刻", 不能用 `created_at`。**
一条被人回答后复活的任务, `created_at` 可能是十分钟前, 拿它当兜底等于**零宽限期** ——
任务刚活过来就满足判死条件, 下一次清扫直接把它杀掉并把草稿标废。
(第一段实现时踩过, 已实测复现: 建任务 → 提问 → 十分钟后回答 → 一次清扫 →
`dead_letter / lease_timeout`。修法见下。)

**落地方式定死**: **任何让任务处于 `running` 的写操作都要同时把 `heartbeat_at`
置成 `now()`**, 把它当成"这一刻刚活过来"的一次打卡。目前是四处 —— 新建、认领、
打卡、人回答澄清后的恢复。判死条件因此收敛成**一个起算点**: 只比对 `heartbeat_at`,
不看 `created_at`。没人认领时照样在阈值后被判死, 宽限期真实但有界。

**由此 `heartbeat_at IS NULL` 而 `status = 'running'` 就是一个不可能状态。**
它只会来自代码回归 (有人新写了一处让任务变 running 却忘了盖戳) 或手改库。
定为**立即判死**, 不给宽限 —— 把不变量被破坏这件事变成当场、显眼的失败,
好过悄悄多活六十秒。但**这一格的 `error_detail` 必须与真正的失联区分开**:
写成"心跳戳缺失"并指向本节, 不能沿用"可能是服务重启"那句 ——
否则排查的人会去追一个根本没发生过的重启。

**每新增一处让任务变成 `running` 的写操作, 必须同时盖戳并配一条测试。**
这四处目前只有三处被测试守着 (见验收 15c); 盖戳这件事一旦漏掉, 后果是任务在
被认领之前就被清扫杀掉 —— 与第一段踩过的那个坑是同一个, 只是发生在另一头。

`clarifying` 的任务**不参与这个清扫** —— 它没有进程在跑它, 本来就不打卡。
它由生存期上限收尾, 见第三节。

### 3. 那道闸: 每次写库都带上"我还是不是主人"

**这一条是防"假死复活"的, 不能省。**

场景: 进程僵住两分钟, 被判死, 用户重开了一条任务并顺利跑完。然后那个僵住的进程醒了 ——
它不知道自己被判过死刑, 以为还在第 5 步, 于是接着写草稿、提交审批。
结果一句话产出两份草稿、两条审批请求。

闸的做法是把"确认归属"和"写"**合并成同一条 SQL**, 中间不能有缝:

```sql
UPDATE agent_tasks SET ...
 WHERE id = :id AND status = 'running' AND runner_id = :me
```

受影响行数为 0, 就说明租约已被收走, **当场停手, 一个字都不写**。

不能写成"先查一下是不是我的, 是就去写" —— 查完到写之间那一瞬间情况可能又变了。
合成一条, 由数据库保证没有缝。

**这就是 W3 事故状态机那一招** (`UPDATE ... WHERE status = 旧状态`, 受影响行数为 0
即 409), 同一个手法换个地方用。

### 代价 (写进已知边界, 不藏)

服务崩溃之后**最多 60 秒内**, 用户重说同一句话会被去重索引挡住 (那条 `running` 行
还没被判死)。这时候**接口不能报"重复提交"** —— 用户明明什么都没等到, 那样说他会
一头雾水。正确做法: 返回那条卡住的任务, 界面上标"疑似中断, 稍后可重试"。

这套东西的正式名字是**租约与栅栏** (lease and fencing)。

## 三、多轮澄清

**定死: 澄清是多轮的, 同一条任务、同一条 Trace, 人回答后从原地继续。**

(初稿把 `clarifying` 画进状态机却在非目标里写"不做多轮", 自相矛盾。第二轮评审定为
正经做多轮 —— 模型不懂就问、不许猜, 这本来就是本项目主张的一部分。)

### 谁能回答

**必须是发起这条任务的人本人** (`agent_tasks.user_id`), 不是任意 operator。

理由: 草案的 `created_by` 记的是发起人。如果 A 的任务能被 B 回答, "这条策略到底是谁的
意思"就说不清了 —— 而那正是加 `created_by` 要解决的问题。

### 存哪: 独立一张 `agent_clarifications` 表

一次澄清就是一行, 问题和回答在同一行:

```sql
CREATE TABLE agent_clarifications (
    id            bigserial PRIMARY KEY,
    task_id       bigint NOT NULL REFERENCES agent_tasks(id),
    asked_seq     int NOT NULL,          -- 问题在时间线上的位置
    question      text NOT NULL,
    asked_at      timestamptz NOT NULL DEFAULT now(),
    answered_seq  int,                   -- 回答在时间线上的位置, 没答就是 NULL
    answer        text,
    answered_by   bigint REFERENCES users(id),
    answered_at   timestamptz
);

-- 一个任务同时最多一个没被回答的问题
CREATE UNIQUE INDEX agent_clarifications_one_pending
    ON agent_clarifications (task_id) WHERE answer IS NULL;
```

**为什么不塞进 `agent_steps`**: 那张表的列是为工具调用设计的 —— `tool_name`、
`arguments`、`latency_ms`、`retry_count`、`input_tokens`、`output_tokens`, 对"人答了
一句话"没有一个是有意义的。硬塞的结果是一行里大半的列永远为空, 还得加一个类型列来区分,
而且没法给任何一列加 NOT NULL 约束。

按 SPEC-006 第二节自己立的标准 —— **同一个事实存两份才叫冗余, 两个不同的事实分开存
是正常建模** —— 工具调用与人的回答是两个不同的事实, 分表是对的。
(评审第一版曾以"`agent_steps` 是 Trace 唯一事实源"为由主张单表, 那是把 SPEC 的一句话
当结论用, 没有往下想。已推翻。)

**"最多一个未回答的问题"由数据库保证**, 应用层不写并发判断。这个形状与 W3 的
`approvals_one_pending` (`WHERE decision IS NULL`) 逐字同构, 照抄即可。
**这是本项目"约束下沉到数据库"的第五次应用** (W1 幂等唯一键 → W2 事故 partial unique
index → W3 发布的审批外键 → W4 防重复提交 → W4 这一条)。

### 两张表, 一条编号

分表之后有一个必须一起解决的工程问题: **Trace UI 需要一条按顺序排好的时间线**,
而 SSE 断线重连是"从我收到的最后一个 `seq` 之后接着推"。两张表各有各的 `seq`,
就是两条各自从 1 开始的编号, 合不出确定的先后顺序, 断点续传会漏推或重推 ——
而这种 bug 只在断线时冒出来, 平时测不到。

**解法: `agent_tasks` 加一列 `next_seq`, 两张表共用它。** 每写一条时间线记录 (无论进
哪张表), 在同一个事务里把它加一, 拿到的号写进那条记录。

一句话: **表按"东西的种类"分, 编号按"时间线"统一。**

### 上限 (多轮引入的新东西, 必须定死)

| 项 | 值 | 说明 |
|---|---|---|
| 单轮执行预算 | 120 秒 | **只算机器在跑的时间**, 跨轮不累加。待实测回填, 方法见第五节 |
| 任务生存期 | 24 小时 | 停在 `clarifying` 超过这个时间 → `dead_letter`, `error_detail` 写"等待澄清超时"。**起算点是那条未回答问题的 `asked_at`, 不是任务的 `created_at`** —— 进入 `clarifying` 必然伴随一个提问, 用提问时刻才是"这个问题挂了多久没人答" |
| 澄清轮次 | ≤ 3 | 超出 → `failed` |
| 单任务 LLM 调用总数 | ≤ 12 | 硬上限, **跨轮累加不重置**。防的是模型和人来回绕圈把账单绕上去 |
| 修复次数 | ≤ 2 | **每轮澄清后重置为 0**, 与上一行相反 |
| **单次 LLM 调用** | 60 秒 | 与"单工具 10 秒"是两码事: 工具是本地查询与纯函数, LLM 是网络往返。必须**小于单轮预算**, 否则一次卡住的调用就把整轮拖死, 谁超时的都分不清。**这一格与"深度思考开关"是绑在一起的**, 见下 |
| 单工具 | 10 秒 | 已实测确认够用, 见第五节 |

**"修复次数每轮重置、调用总数不重置"这一对必须写死**, 否则实现者会随便挑一个,
而两种挑法的行为差别只在绕圈的时候才看得出来。

### 回答之后回到哪一步

**回 `discovering`**, 不是 `compiling`。因为人的回答很可能提到新的东西
("我说的主管是后场那个"), 需要重新捞一遍区、传感器、角色。这几个工具都是本地只读查询、
毫秒级, 重跑的成本可以忽略, 换来的是不必去推理"这次回答有没有引入新实体"。

## 四、状态机

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   parsing → discovering → compiling → validating ──(有错误)──→ repairing
                  ▲                        │                       │
                  │                   (通过)│              (修满 2 次仍不过)
                  │                        ▼                       │
        (人回答, ≤3 轮)                simulating                   ▼
                  │                        │                   clarifying
                  │                        ▼                       │
                  │                 awaiting_approval               ├─→ (人回答) 回 discovering
                  │                        │                       │
                  └────────────────────────┼───────────────────────┘
                                           │
                           (人在 Studio 里批准或否决)
                                           ▼
                                       completed
```

失败出口 (都落 `failed` 或 `dead_letter`, 各有 `error_detail`):

| 情况 | 落到 |
|---|---|
| 澄清轮次用尽 | `failed` |
| LLM 调用总数用尽 | `failed` |
| **模型没按协议来** (该调工具时没调、或调了本阶段之外的工具) | `failed`, `error_code = model_protocol_error`。判 `failed` 而不是 `dead_letter`: 这是模型输出的问题, 不是系统故障, 用户重说一遍就能重开 |
| 单轮执行超预算 | `dead_letter` |
| 单工具不可重试错误 | `dead_letter` |
| 任务失联 (租约超时) | `dead_letter` |
| 停在 clarifying 超过 24 小时 | `dead_letter` |

几条要写明的:

- `parsing` 读懂说的是什么; `discovering` 调只读工具把区、传感器、角色捞回来;
  `compiling` 产出 Policy 草案; `validating` 调静态验证器; `simulating` 调回放。
- **`repairing` 修完必须回到 `validating` 重新校验**, 不是直接去 `simulating`。
  修完不验等于没修。
- **修满 2 次仍不通过 → `clarifying`, 不是直接 `failed`。** 连续两轮都改不对,
  说明多半不是模型手滑而是需求本身有歧义 (比如"主管"指哪个角色), 该回头问人。
- `awaiting_approval → completed` **由 `policy_service.decide_approval` 回写**,
  见第六节。**批准和否决都推进到 `completed`** —— 批没批通过与 Agent 无关,
  实现时不要写成只有批准才算完。
- 每次状态迁移写一条 `agent_steps`, 并经 SSE 推给前端 (见第八节)。

**`agent_tasks.status` 里的 `rejected` 这个取值在本 SPEC 用不到** (审批被拒是策略版本
的事, 不是任务的事)。`0001` 建表时留下的, 不删也不用, 就地注释说明, 免得下一个人
以为漏实现了。

| 草案 | `update_policy_draft` | **修复循环用**: 就地改本任务这一版的 body |
| 模拟 | `validate_policy` | 静态校验, 返回结构化错误码 |
| 模拟 | `simulate_policy` | 历史回放, 返回 `ReplayReport` |
| 写 | `request_approval` | 建 approvals 记录, 版本转 awaiting_approval |
| 终止 | `ask_clarification` | 把问题抛回给人, 任务转 clarifying |

**`publish_policy` 不在清单里。** 初稿有它, 第一轮删除 —— 发布是人在 Automation Studio
里点的动作, 不该出现在 Agent 的能力范围内。少一个工具, 就少一处需要论证"为什么它不会
乱用"。

**工具清单与实现里的注册表必须有一条相等断言测试。** 现在往注册表里加一个工具却忘了
更新分级表, 不会报任何错。手法与 SPEC-001 那条"审批分级表的键集合必须等于动作白名单"
一致, 这是本项目第五处这么干的地方。

### 三处初稿写错或写漏的

**一、`list_roles` 的取值域写错了。** 初稿写"取值域是 `roles` 表", 但静态验证器的
`E_ROLE_NOT_STAFFED` 查的是 **`user_roles`** ("当前有哪些角色下挂着账号",
SPEC-001 第五节把这个事实源定死过, 正是为了修"三套角色名")。

如果工具把 `roles` 表四个角色全给模型, 模型挑了一个没有账号的角色, 草案必然被验证器
打回, **白白烧掉一次修复配额 —— 而修复次数只有两次**。工具必须和验证器同一个来源。

**二、草案的创建要分成两个工具。** 新建一条策略要**起名字** (名字在 `policies` 表,
SPEC-001 已把它移出 DSL), 给已有策略加一版不用名字。这是两件事, 一个工具说不清楚。

**名字由模型起**, 但服务端要校验长度 (1–60 字符) 并去掉首尾空白; 名字进 Trace,
人在审批时可以改。这条初稿完全没回答, 实现者只能自己编。

**三、`simulate_policy` 的数据源只暴露枚举, 不暴露路径。** W3 的
`policy_service.simulate_version(session, version_id, source)` 的 `source` 参数经
`_resolve_source` 解析, 允许任意仓库内相对路径 (那段 docstring 自己写着"W4 会把这个
参数直接暴露给 HTTP")。让模型填一个路径字符串是没必要的自由度。

工具只暴露一个枚举: 场景名 (来自 `scenarios/` 目录) 或 `history_csv` (那 344 条真实
读数, **默认值**)。模型选不了别的东西。

### `get_available_actions` 的 Schema 只能有一个来源

**必须与 `policy_json_schema()` 同一个来源。** W3 已经做到了 (请求体直接用
`policy_engine.Policy` 模型, OpenAPI 里暴露的就是它, 且有一条测试钉着这件事),
W4 直接 import 即可, **不要另生成一份** —— 两份 Schema 一定会走散,
而走散的那份从外面看不出来 (W1 教训)。

### 权限与拦截: 四层, 只有前三层是安全措施

| 层 | 干什么 | 是不是安全措施 |
|---|---|---|
| 数据库 | `policy_publications.approval_id` NOT NULL 外键 | **是**, 最终防线 |
| service | RBAC 闸 + 自批 CHECK (W3 已实现) | **是** |
| 路由 | `require_permission` 最外层快速失败 | **是** |
| 工具清单 | 按调用者角色 (以及当前状态) 裁剪能给模型的工具 | **不是**, 只是减少模型做无用功 |

**初稿的验收写着"越权 → 工具列表内无 `publish_policy`", 这是错的, 而且是退步。**
SPEC-005 已经立过一条: "前端按角色隐藏按钮不是安全措施, 真正的拦截在服务端。"
同一个道理 —— 不把工具给模型也不是安全措施, 因为模型的输出经过的是同一批接口。
定稿把两件事分开写: 裁剪工具是优化, 拦截在下面三层, 且各有测试。

**按状态裁剪工具也归在这一档**。这是让模型少犯错, 不是安全措施 ——
服务端那三层照样各判各的。分档如下:

| 阶段 | 给模型的工具 |
|---|---|
| `parsing` | `ask_clarification` |
| `discovering` | 六个只读工具 |
| `compiling` (还没有草稿) | `create_policy` / `add_policy_version` / `ask_clarification` |
| **`compiling_with_draft`** (澄清回来那一轮, 草稿已存在) | `update_policy_draft` / `ask_clarification` |
| `repairing` | `update_policy_draft` / `ask_clarification` |

**`compiling_with_draft` 这一档不能省。** 澄清回来重新走到 `compiling` 时若还把
`create_policy` 给模型, 它会再建一条策略, 直接违反"每个任务只新建一版草稿"(第六节)。
运行时按"本任务有没有草稿"选档, 不问模型。

**注册表里有三个工具不由模型选, 由运行时确定性执行**: `validate_policy`、
`simulate_policy`、`request_approval`。第四节状态机图上那几条箭头本来就是自动的 ——
校验完必然去模拟、模拟完必然提交审批, 没有可让模型发挥的余地。它们仍留在注册表里
(工具数 13 就是这么算的): 一是要走同一套超时、重试与 `agent_steps` 记录,
二是第二段接真模型后仍可能改成由模型驱动。**这一点要写在注册表旁边**,
否则下一个人会以为裁剪表漏了它们。

**`update_policy_draft` 的 `version_id` 由运行时钉死为本任务那一版, 不采信模型
给的值** —— 第六节的规矩是"就地改**本任务这一版**的 body", 模型报错版本号也不该
改到别的版本上去。

### 接口的权限档位

`POST /agent-tasks` 与 `POST /agent-tasks/{id}/reply` 用**已有的 `policies:draft`
权限点** (operator+, W3 为 `POST /policies` 加的那个), **不新增权限点、不改 SPEC-004
的权限表**。跨文档的权限口径分叉是本项目反复在修的毛病, 能复用就复用。

## 六、草稿只有一条, 中间态记在 Trace 里

**定死: 一个 Agent 任务只在 `policy_versions` 里留下一条草稿行。**

修复循环**就地改这一版的 `body`** (状态一直是 `draft`), 不每修一次就新开一版。
理由: 策略列表里挂着三条半成品是噪音, 而且那几版从没被任何人看见过。

**但中间态不能丢**: 决定 5 (失败草案不删) 的出发点是 W5 要评测编译质量, 而
**"它第一次写错成什么样"正是唯一能回答"为什么没编译对"的东西**。所以:

- 每次 `update_policy_draft` 之前那一版的完整 body, **原样记进 `agent_steps`**
  (`result_summary` 里)。Trace UI 上"第 3 步: 校验失败 → 第 4 步: 修复"这两行本来
  就要给人看改了什么, 内容存在那里是它本来的职责;
- W5 的评测样本从 `agent_steps` 取, 一条不丢。

### 这需要在 SPEC-006 里划一条线

`policy_versions` 的"版本不可变"是 SPEC-006 第二节立的规矩。就地改草稿看起来是违反它,
其实不是 —— 那条规矩保护的从来不是"所有写过的字", 而是**"已经被人看过、成为过决策
依据的东西"**。所以边界要说清楚, 已同步补进 SPEC-006 第二节:

> **版本不可变的边界是"提交审批"。** 一旦进入 `awaiting_approval`, 这一版永远不再
> 改动 —— 从这一刻起有人要看它、批它, "当时批的到底是什么"必须永远查得到。
> 在那之前的 `draft` 是工作台。

**在已有策略上改的情况**: 必须先 `add_policy_version` 新开一版 —— 已有的那些版本
可能已经发过、批过, 动不得。规则一句话: **Agent 每个任务只新建一版草稿,
此后所有修复都在这一版上就地改, 提交审批即冻结。**

### 失败任务的草稿: 标 `discarded`, 不是 `rejected`

**初稿把它标成 `rejected` 是错的 —— 那个词在 SPEC-006 里已经是"人审批时否决"的意思。**
一词两义之后, W5 想把"人看了觉得不行"和"模型自己没编译出来"分开统计就做不到了,
而这两类恰恰是完全不同的样本。

`0008` 给 `policy_versions.status` 的 CHECK 加一个 `discarded`。列表接口默认过滤掉,
Trace UI 与评测仍读得到。用户看到的是一条失败提示 + 出错原因, 看不到半成品。

## 七、数据库变更 (迁移 0008)

按 ADR-006 手写, 必须写 downgrade。**十一件, 逐条核对**:

| # | 表 | 做什么 | 为什么 |
|---|---|---|---|
| 1 | `agent_tasks` | 加 `error_detail text` | 死信的人话解释。现在只有 `error_code`, 没地方放解释; 塞进某条 `agent_steps.result_summary` 会让"这个任务为什么死了"变成要翻步骤才知道 |
| 2 | `agent_tasks` | 加 `input_hash text` | 归一化后输入的哈希, 去重用 |
| 3 | `agent_tasks` | **删掉 `idempotency_key` 列** | 见下"两个坑" |
| 4 | `agent_tasks` | 建部分唯一索引 `agent_tasks_one_open` | 见下 |
| 5 | `agent_tasks` | 加 `runner_id text` + `heartbeat_at timestamptz` | 租约 (第二节) |
| 6 | `agent_tasks` | 加 `next_seq int NOT NULL DEFAULT 0` | 两张表共用的时间线编号 (第三节) |
| 7 | `agent_tasks` | `user_id` 设 NOT NULL | 见下 |
| 8 | `agent_steps` | 加 `UNIQUE (task_id, seq)` | 见下 |
| 9 | — | 新建 `agent_clarifications` + `agent_clarifications_one_pending` | 第三节 |
| 10 | `policy_versions` | 加 `created_by bigint REFERENCES users(id)` **与** `source text` | 见下 |
| 11 | `policy_versions` | status 的 CHECK 加 `discarded` | 第六节 |

**(初稿这一节写着"四件事"、下面只列了三个圆点, 本身就数不清楚。这次做成能逐条打勾的
表, 就是为了不再出现这种情况。)**

### 第 10 条: `policy_versions` 没有 `created_by` 这一列

**已灌进真实 Postgres 确认**: 这张表只有 `id / policy_id / version / body / status /
created_at` 六列。`created_by` 在 `policies` 表上 (策略这个实体), 不在版本上。
W3 的 `policy_service._INSERT_VERSION` 也只写 `(policy_id, version, body, status)`。

所以**两列都要加**, 而且 W3 的 `create_policy` / `add_version` 两个函数的 INSERT
要跟着改 (见第九节的越界改动清单)。

初稿的决定 1 ("`created_by` 记发起的人, 另加 `source`") 判断是对的, 只是漏了这一列
根本不存在这个事实。

### 第 3 条与第 4 条: 两个坑

**坑一: `idempotency_key` 的 UNIQUE 是约束不是索引。** 已实测确认它是
`agent_tasks_idempotency_key_key` 这个 UNIQUE **CONSTRAINT**, `DROP INDEX` 会失败,
必须 `ALTER TABLE ... DROP CONSTRAINT`。而且按 0007 立的规矩, **约束名从 `pg_constraint`
查出来, 不猜**。

**坑二: 去掉 UNIQUE 之后这一列就没人用了。** 它和 `input_hash` 表达的是同一件事。
按项目自己的标准 (`policies.enabled` 刚刚就是因为这个被删的), **整列删掉, 不留**。

初稿写的是"去掉 `idempotency_key` 的全局 UNIQUE、换成部分唯一索引", 留着列不用 ——
那就是同一个事实存两份, 是本项目一直在修的毛病。

**索引本身**:

```sql
CREATE UNIQUE INDEX agent_tasks_one_open
    ON agent_tasks (user_id, input_hash)
 WHERE status IN ('running', 'clarifying');
```

**注意条件不是只有 `running`。** 已实测: 只写 `running` 时, 老任务停在 `clarifying`
等人回答, 用户重说一遍会开出第二个任务, 老的那个永远挂着没人收尸。

四种情况都实测过: 建索引本身没问题 (常量 IN 列表可以用在部分唯一索引上);
`clarifying` 期间重说同一句话被挡住; 人回答后同一条任务从 `clarifying` 回到
`running` 不会撞自己; 任务彻底结束后同一句话能重新开。

索引的名字与注释都不要再写"最多一条 running", 准确的说法是
**"同一个用户同一句话, 最多只有一条还没走完的任务"**。

### 第 7 条: `user_id` 必须 NOT NULL

它现在是可空的。部分唯一索引里 NULL 永远不冲突, 等于这条防线对空 user 静默失效。
迁移里先断言表内无 NULL 再加约束 (目前这张表还没有任何行)。

### 第 8 条: `agent_steps` 现在只有主键

已实测: 没有 `(task_id, seq)` 上的任何索引或唯一约束。SSE 断线重连按 `seq` 续传,
`seq` 一旦重复或跳号就会漏推或重推 —— 而这种 bug 只在断线时出现, 平时测不到。
补上唯一索引, 顺带当查询索引用。

### `input_hash` 的归一化规则

写进 service 的 docstring, 并且**必须包含"改的是哪条策略"**: 同一句"把冷却改成 600 秒"
用在两条不同策略上是两件事, 只哈希文本会误挡。

归一化 = 去首尾空白 + 压缩连续空白 + 目标 policy_id (新建时为 0), 然后取哈希。

### 去重规则一览

| 情况 | 结果 |
|---|---|
| 手抖点两下提交 | 第二次撞上索引 → 返回正在跑的那个, 用户看到"只跑了一次" |
| 网络超时前端自动重发 | 同上 |
| **上一条正停在 `clarifying` 等你回答** | **撞索引 → 返回那条任务, 引导人去回答, 不开新的** |
| 前一次已跑完, 隔几分钟故意重说一遍 | 上一条已是终态 → **新任务** |
| 同时编译两条不同的策略 | 输入不同 → 两个任务, 不挡 |
| 前一次失败后立刻重试 | 上一条是 `failed` → 新任务 |
| **服务刚崩溃, 60 秒判死窗口内重试** | **撞索引 → 返回那条卡住的任务, 标"疑似中断"** |

**曾经考虑过、都不如它的两个方案**:

- **前端每次点提交生成一个随机 id 随请求发上来** (Stripe 那套)。也能精确防双击,
  但要求前端老实生成并传递 —— 多一个环节就多一处可能漏, 而这条规则服务端自己就能保证。
- **"5 分钟内说同样的话算重试"**。两头都不准: 双击若跨过窗口边界仍会开两个任务;
  而用户 3 分钟后故意重说一遍 (比如刚补了数据想重跑) 会被当成重试、拿回旧结果。

## 八、预算与恢复的数字

单工具 10 秒、单轮 120 秒、退避只对可重试错误做指数退避。其余上限见第三节那张表。

**`simulate_policy` 的 10 秒曾被怀疑不够, 实测证明绰绰有余。** 拿 344 条真实读数
(装载后 1258 条事件、仿真时长 55434 秒) 跑三条带条件的策略, 五次取中位:

| | 中位 | 最慢 |
|---|---|---|
| 1 条策略 | 14 ms | 16 ms |
| 3 条策略 | 16 ms | 18 ms |

**比预算小三个数量级。** 引擎是纯 Python 的确定性循环, 不连网、不查库、不调模型 ——
慢的从来是 LLM 那一跳, 不是模拟这一跳。

**因此: 模拟同步跑, 不引入异步等待态。** 曾考虑过"提交模拟后不等结果、稍后推送"
这种更接近成熟产品的形态, 现在明确不做 —— 它会给状态机多加一个等待态、多一条推送
链路, 而换来的是省掉 16 毫秒。**这不是"以后再说", 是量过之后确定不需要。**

(方法论: 数字不改变产品能做成什么样, 但决定更复杂的那个形态值不值得做。
若实测是 40 秒, 同步就没法用、异步是必须的; 实测是 16 毫秒, 异步就是纯粹的过度设计。
所以先量再定, 而不是先定再说。)

**注意这一条只管"模拟"这一步, 不管整个任务。** 整个任务是后台跑的 (第一节) ——
这两件事初稿混在一起了。

### 深度思考开关: 它和上面两个预算是绑在一起的

**第二段接真模型第一天就撞上了这件事**, 记在这里, 因为它是那种"打桩阶段完全暴露
不出来、第一次真调用当场翻车"的坑。

`Doubao-Seed-2.1-pro` **默认开深度思考**。同一个 `parsing` 请求, 两臂实测对照:

| | 耗时 | reasoning_tokens | 输出是否正确 |
|---|---|---|---|
| 默认 (不指定 thinking) | **83.2 秒** | 2533 | 正确 |
| `thinking: disabled` | **1.9 秒** | 0 | 正确 |

默认档单步就 83 秒, **直接爆掉"单次 LLM 调用 60 秒"那一格** —— 头两次录制就是这么
落的 `dead_letter / llm_timeout`。

**定为默认 `disabled`**, 开关进 `config.llm_thinking`。要写明的三件事:

1. **这是一个取舍, 不是一个结论。** 目前关掉它的直接理由是延迟, 不是"已经证明思考
   对这个任务没用"。真正的判断要靠数据 —— **W5 的消融把它作为一臂**
   (`enabled` vs `disabled`), 与"主力档 vs 同代降档 (`2.1-turbo`)"是两个独立维度;
2. **它改变模型输出, 所以必须进回放键**, 否则同一批 cassette 会在两种档位间串味;
3. **一旦翻回 `enabled`, 上面两个预算立刻不够** (单步 80 秒级 × 一轮至少两次调用)。
   谁改这个开关, 就得同时重估 60 秒与 120 秒两格。这条依赖要写进 `config.py` 注释,
   不能只写在这里。

### 120 秒的实测回填

方法: 真实调用 (`mode=off`, **不读不写录制** —— 回放几乎是 0 毫秒, 拿它回填等于没量)
跑同一条招牌句任务 5 次, 每次 2 次 LLM 调用。

配置: `doubao-seed-2-1-pro-260628` / prompt `v2` / `thinking=disabled` / 北京。

| | 五次原始值 (秒) | 中位 | 最慢 |
|---|---|---|---|
| 单轮墙钟 | 8.20 / 6.83 / 7.20 / 9.97 / 6.58 | **7.20** | **9.97** |

**比 120 秒的预算小一个数量级半, 预算数字不动。** 但注意它是在 `thinking=disabled`
下量的 —— 换档位这张表就作废, 见上一小节第 3 条。

(方法论与第三节那 16 毫秒的模拟耗时一样: 先量再定。区别是这次量出来的结论是
"预算定得没错", 而不是"某个更复杂的形态不值得做"。)

**报数字必须带上产生它的配置** —— W3 踩过 65 次 / 35 次那个坑 (同一份数据换个作用域
差一倍)。这条规矩同样适用于摆给审批人看的 `ReplayReport`: 报告里必须一起显示这条策略的
`scope` 与 `cooldown_s`, 否则那个坑会在 Studio 界面上原样重演一次。

## 九、LLM 接入与可复现

- 走火山方舟 (豆包), OpenAI 兼容协议, key 在 `.env` 的 `SENTINEL_LLM_API_KEY`。
- **每次调用落 `ai_usage`**: 模型、prompt 版本、输入输出 token、预估成本、延迟、
  是否命中缓存。W5 的消融实验要靠这张表算成本。
- **录制回放**: 调用与响应写进 `SENTINEL_LLM_RECORD_REPLAY_DIR` (默认 `.llm-cache`)。
  W5 的评测必须能离线复跑, 否则每跑一次评测集都要真花钱、且结果不可复现。

  三条落地规矩:

  1. **回放的键只由"会改变模型输出的输入"决定** —— 模型名、prompt 版本、消息、
     可用工具、**深度思考开关** (第八节: 它是开是关, 模型给出的东西完全不同)。
     **任务 id、阶段名、时间戳、随机串一律不进键** (阶段已完整体现在 system prompt
     与工具清单里), 否则每次算出来的键都不一样, 回放永远命中不了,
     而症状是"跑得通但每次都在真花钱";
  2. **模式是三态**: `record` / `replay` / `off`, 且 **`replay` 下没命中就直接失败**,
     不许悄悄回退去调真模型。回退看着friendly, 实际是让 CI 在你不知道的时候花钱、
     并且把"离线可复跑"这条验收变成假的;
  3. **进 git 的那批录制与临时录制分开放**。测试与评测依赖的录制必须进版本库
     (否则换台机器、CI 上那条离线复跑验收根本跑不了), 开发时随手产生的不进。
     手工编辑过的录制**必须就地标注**它是手编的 —— 否则下一个人会把它当成
     模型的真实行为去分析。
- **prompt 版本号进 `ai_usage.prompt_version`**, 改 prompt 就换号 ——
  否则消融实验里"这次好是因为改了 prompt 还是换了模型"分不清。

**模型客户端在第一段就抽成一个接口**, 打桩实现与录制回放实现是同一个接口的两个实现。
这样第二段接真实模型时不必回头改状态机, 第一段那批确定性测试也能原样继续跑。

## 十一、不变量 1 的精确措辞

`CLAUDE.md` 不变量 1 写的是"LLM 永远没有副作用执行权限"。**按字面读, 这句话被本 SPEC
的工具清单打脸了** —— `create_policy` 与 `request_approval` 都往数据库写行, 都是副作用。

说过头的主张比说得小的主张更危险: 别人一对照工具清单就会问"你不是说没有吗",
而这一问会把前面所有关于安全的论述一起带塌。

**准确的说法 (也更强)**:

> 模型能做的只有两件事, 而且两件都是**可撤销的、只在系统内部留痕的**:
> 写一份草稿 (没人看它就等于不存在), 和举手请一个人来看一眼 (人可以不理它)。
>
> 而**不可撤销、外部世界看得见**的三件事 —— 发布上线、真的发出邮件、真的点亮现场的
> 灯 —— 模型一件都碰不到。其中"发布"这一件不是靠代码自觉挡住的,
> **是数据库外键在物理上挡住的**: 没有一条真实的审批记录, `policy_publications`
> 那一行插不进去 (ADR-007)。

原来那句是一个**承诺** ("我们不让模型乱来"), 需要别人相信你;
改过之后是一个**事实** ("边界在这里, 最要紧的那条由数据库强制, 你可以绕过所有代码
直接写库来验")。验收里那几条"绕过应用层直接写库"的测试就是这句话的证据。

**这段话要同步进 README 与面试口径, 不要留旧说法。**

## 十二、验收

**正常路径**

1. 一句人话 → 产出草案 → 静态校验通过 → 回放出报告 → 提交审批,
   全过程在 Trace UI 上逐步冒出来。
2. `POST /agent-tasks` **立刻返回** `task_id` (不等任务跑完), 随后 SSE 逐步推。
3. 草案的 `created_by` 是发起人的 user id, `source` 是 `agent`;
   直接提交 DSL 的那条路径 (`POST /policies`) 产出的版本 `source` 是 `human`。

**修复循环**

4. 故意让模型产出一个引用了不存在 zone 的草案 → 静态验证器返回 `E_UNKNOWN_ZONE` →
   Agent 仅凭错误码与 hint 修对 → 重新 `validating` 通过。
   **这条要验的是"错误码够不够修复用"**, 是 SPEC-001 第五节那套错误码的真实检验。
   **这条必须跑在录制的响应上** (`.llm-cache`), 不能跑真实模型 ——
   否则"故意让模型产出一个错 zone"没法稳定复现, 测试会飘。
5. 修复过程中 `policy_versions` **始终只有一条草稿行**; 每次修复前的 body 能在
   `agent_steps` 里查到 (第六节)。

**多轮澄清**

6. 说"漏水了通知一下" (没说通知谁、几个探头) → Agent 问回来, 不猜。
7. 修满两次仍不过 → `clarifying` 而不是 `failed`。
8. 人回答后**同一条任务**从 `discovering` 继续, `task_id` 不变, Trace 接着往下长。
9. **只有发起人能回答**: 换一个同为 operator 的账号去 `reply` → 403。
10. 一个任务同时只能有一个未回答的问题: 并发回答两次只有一个成功;
    **另配一条绕过应用层直接写库的测试**, 断言
    `agent_clarifications_one_pending` 真的拦得住。
11. 澄清满 3 轮仍不通过 → `failed`; 停在 `clarifying` 超过生存期 → `dead_letter`,
    `error_detail` 里有人话。

**去重与租约**

12. 同一用户同一段输入并发提交两次 → 只开出一个任务, 第二次拿回正在跑的那一个;
    **另配一条绕过应用层直接写库的测试**, 断言部分唯一索引真的拦得住
    (与 W3 那六条数据库约束测试同一路数 —— 端到端证明正常路径走得通,
    这条证明异常路径走不通)。
13. 上一条任务停在 `clarifying` 时重说同一句话 → **不开新任务**, 拿回那一条。
14. 前一个任务结束后同样的输入能开出新任务。
15. 把 `heartbeat_at` 手工改老 → 清扫把任务判成 `dead_letter`;
    随后那个"假死复活"的写操作**受影响 0 行, 不产生任何写入**。
    这条要直接断言"没有第二份草稿", 不能只断言状态。

15b. **判别性测试 —— 只有 `runner_id` 那半边闸能拦的场景。** 验收 15 里任务已经是
    `dead_letter`, 闸的 `status = 'running'` 半边**独自就能拦住**僵尸写入, 所以
    单独拆掉 `runner_id` 那半边, 验收 15 照样绿 (第一段实现后用变异测试验过)。
    必须另构造一个 **status 仍是 `running`、但主人已经换人**的场景:
    A 提问后僵住 → 人回答 → 新进程 B 认领续跑 → A 醒来写库。
    那一刻唯一拦得住它的就是 `runner_id` 对不上。
    **这条才是那个不变量的真正守卫, 不能省** —— 与 SPEC-001 验收 6b 同一课。

15c. **四处盖戳每一处都要有一条测试守着**, 少一处就是一个没人守的分支:
    - 建任务后从没认领过, 超过阈值 → `dead_letter`;
    - **老任务被人回答后刚变回 `running`** (`created_at` 是很久以前) → 跑一次清扫,
      **必须还是 `running`**; 再老化过阈值 → `dead_letter` (宽限真实但有界);
    - **刚新建、还没被认领的任务立刻跑一次清扫 → 必须还是 `running`**。
      这条守的是新建那一处盖戳。**不能靠"建完老化再清扫"那条代劳** ——
      `NULL - interval` 仍是 `NULL`, 而 NULL 本来就判死, 所以那条测试在
      "新建不盖戳"这个变异下**照样绿** (第一段修补后复核实测);
    - `status = 'running'` 却 `heartbeat_at IS NULL` 的行 (绕过应用层裸插) → 立即判死。

**权限与安全**

16. operator 的会话跑 Agent, 产出的草案能提交审批但发布按钮是灰的;
    **绕过前端直接调发布接口仍然 403** —— 这条才是安全测试, 工具裁剪那条不是。

**可靠性**

17. 工具超时: 注入一次超时 → 可重试错误退避后成功; 不可重试错误干净失败并落
    `dead_letter`, `error_detail` 里有人话。
18. 每步落 `agent_steps` 或 `agent_clarifications` 并 SSE 推送;
    **两张表的记录按同一条 `seq` 排出唯一顺序**; 断线重连从 `seq` 续传不重复不遗漏。
19. 离线复跑: 关掉网络, 用 `.llm-cache` 里的录制把同一条任务原样跑一遍, 结果一致。

**变异测试 (W3 最值钱的产出, W4 继续做)**

20. 把 `agent_tasks_one_open` 索引删掉 → 验收 12 与 13 必须红。
21. 把发布路由上的 manager 门拆掉 → 验收 16 必须红。

    **本段实测推翻了这条原本写的手法, 记在这里。** 初稿沿用 W3 留下的设想 ——
    "路由门在碰数据库之前就拒绝, 给一个不存在的版本号, 有门是 403、
    没门会先查库变成 404"。**实测不成立**: `policy_service.publish_version` 的
    `has_permission` 检查排在读版本那句 SQL **之前**, 所以拆掉路由门之后,
    service 层的第二道闸照样在查库前就 403, 状态码分不出两层。

    这不是缺陷, 恰恰相反 —— **纵深防御比当初设想的还早一层**。但它意味着
    那个"更结实的写法"在本代码上不存在, 得换一根钉子:

    **断言"请求根本没走到 service"**: 把 `policy_service.publish_version`
    换成一个只记调用次数的替身, 用 operator 的会话请求发布 ——
    有路由门时**调用次数为 0** (请求在路由层就被挡回), 拆掉门则为 1
    (进了 service 才被第二道闸拒绝)。这是结构性断言, 与错误文案无关。

    (第三段先落的是"断言两层话术不同"那根钉子, 能红, 但它守的是文案 ——
    谁改一句错误提示都会误伤, 而文案变了不代表那道门没了。上面这根更准,
    建议在 W5 收尾或 W6 加固时换掉。)
22. 把那道闸的 `runner_id` 半边去掉 (只留 `status = 'running'`) → **验收 15b 必须红**。
    **不要写成"验收 15 必须红"** —— 实测过, 那条在这个变异下照样绿,
    因为它的场景里 status 条件与 runner_id 条件重叠。
22b. 把**人回答后恢复**那一处的盖戳去掉 → **验收 15c 的第二条必须红**。
22c. 把**新建**那一处的盖戳去掉 → **验收 15c 的第三条必须红**。
    (这一条是第一段修补后复核补的: 当时四处盖戳里只有三处有人守,
     新建那一处删掉之后整套测试照样全绿。)
23. 把 `agent_clarifications_one_pending` 删掉 → 验收 10 必须红。

**工程**

24. `make lint` (ruff + mypy) 与全部测试绿; 测试命名遵循 `test_<行为>__<条件>`;
    新模块进 mypy 严格档白名单 (`mypy.ini`), 否则新代码会悄悄退回默认档。

## 定稿决定 (第一轮 2026-08-07 四条, 第二轮 2026-08-08 九条)

### 第一轮 (仍然成立)

1. **草案的归属: `created_by` 记人, 另加 `source` 列记来源。**

   一度想把这件事描述成"人写的 vs AI 写的可以分开统计", 那个框架是错的 ——
   **这里从头到尾只有一条流程: 人说自然语言, Agent 去编译。** Agent 不是另一个作者,
   是这个人手里的工具; 每一条草案背后都有一个真实的人, `created_by` 就记他,
   没有"agent 系统账号"这种东西。

   仍然要加 `source` (`human` / `agent`), 但理由不是记功劳, 是 **W5 要用**:
   评测 Agent 的编译质量, 前提是能把"经 Agent 编译的草案"从"直接提交 DSL 的草案"
   里挑出来。后一种路径确实存在 —— W3 的 `POST /policies` 接受直接提交的 DSL body,
   测试走的就是它, 而且 LLM 挂了的时候它是兜底。**留着这条直连路径, 也让 Agent
   保持"可选"而不是"必需"** —— 系统不会因为模型不可用就瘫掉。

   (第二轮补: 这两列在库里都不存在, 见第七节第 10 条。)

2. **重复提交由数据库的部分唯一索引挡住, 不靠前端传 id、也不靠时间窗猜。**
   **这是本项目"约束下沉到数据库"的第四次应用。** 详见第七节。
   (第二轮补: 索引条件从 `status = 'running'` 放宽到
   `status IN ('running','clarifying')`。)

3. **失败任务的草案不删, 但不出现在策略列表里。**

   出发点是对的: 半成品没法直接用, 堆在列表里只是噪音。但**删掉是错的** ——
   W5 要评测 Agent 的编译质量, **失败的草案恰恰是信息量最大的样本**
   ("它当时写成了什么样"是唯一能回答"为什么没编译对"的东西), 删了就没得评了。

   (第二轮改: 状态用 `discarded` 而不是 `rejected`, 见第六节; 修复循环的中间态
   不进版本表而进 `agent_steps`, 见第六节。)

4. **模拟同步跑, 不做异步。** 已实测, 见第八节 —— 16 毫秒, 比预算小三个数量级。
   (第二轮补: 这一条只管"模拟"这一步, 整个任务是后台跑的, 见第一节。)

### 第二轮 (2026-08-08)

5. **Agent 是后台任务, 不是一个 HTTP 请求。** 见第一节。初稿完全没写这件事,
   而它决定了 SSE 有没有意义、`status='running'` 这个词指什么。

6. **失联判定用租约, 不用"启动时扫一遍"。** 见第二节。一个进程没法判断另一个进程
   是死了还是很慢, 所以做法是踢出局 + 那道 `runner_id` 闸, 而不是假装能判断。

7. **多轮澄清正经做, 非目标那句"不做多轮"删掉。** 见第三节。模型不懂就问、不许猜,
   本来就是本项目主张的一部分。带出来的五样东西 (谁能回答、存哪、编号、上限、
   回到哪一步) 一并写死。

8. **澄清独立建表 `agent_clarifications`, 不塞进 `agent_steps`。** 见第三节。
   工具调用与人的回答是两个不同的事实, 分表是正常建模; 塞一张表会得到一行里
   大半列为空、还要加类型列区分的结构。两张表共用 `next_seq` 一条编号解决排序。
   **这是"约束下沉到数据库"的第五次应用。**

9. **一个任务只留一条草稿行, 修复就地改; 中间态记进 `agent_steps`。** 见第六节。
   同时把 SPEC-006 的"版本不可变"划出边界: **不可变从"提交审批"那一刻开始**,
   在那之前的 draft 是工作台。

10. **失败草稿标 `discarded` 而不是 `rejected`。** 见第六节。一词两义会让 W5 分不清
    "人否决"和"模型没编译对"。

11. **`awaiting_approval → completed` 由 `decide_approval` 回写,
    `request_approval` 加 `task_id` 参数。** 见第四节与第九节。
    初稿这条边没有任何人会去写, `approvals.task_id` 也没有填的入口。

12. **`list_roles` 的取值域是 `user_roles` 而不是 `roles` 表。** 见第五节。
    与静态验证器同一个来源, 否则模型挑到没人的角色会白烧一次修复配额。

13. **`create_policy_draft` 拆成三个工具, `simulate_policy` 的数据源只暴露枚举。**
    见第五节。新建策略要起名字、加版本不用、修复是就地改, 三件事一个工具说不清楚。

14. **`CLAUDE.md` 不变量 1 的措辞要改准。** 见第十一节。
    从"没有副作用权限"改成"没有不可撤销、外部可见的动作权限, 且发布由外键强制"。
