# SPEC-008 · W6 事故报告生成

> 状态: **定稿** (2026-08-22 起草, 2026-08-23 评审定稿)
>
> W4 让模型把一句人话编译成策略。本 SPEC 让模型把一条**已解决事故**的事实写成
> 人能读的报告。它是"模型只产草稿、人过目"的第二个实例, 关键设计是
> **模型不许自己产生任何数字、任何专名** —— 因而"它会不会编"不是一句需要别人
> 相信的承诺, 而是一个**当场被拦下来、并且数得出来**的量。
>
> 与 SPEC-007 一样, 这一份没有前置草稿, 从零起草。依据是 `CLAUDE.md` 不变量 1、
> SPEC-002 的 runtime、SPEC-003 的事故事实、SPEC-007 第三节的判分方法论。
> 起草时逐条核对过这四份与 `0001_initial.sql` 的现状, **发现的四处矛盾写在第九节**。

## 目标

1. **一条已解决事故 → 一份结构化报告草稿**, 全过程在 Automation Studio 里
   一步步看得见, 最后由人过目定稿。
2. **报告里的每一个数字与每一个专名, 都可溯源到一条 SQL 查出来的事实。**
   做法不是"叮嘱模型别编", 是让它**在语法上就写不出**一个自由数字 (第二、三节)。
3. **"它会不会编"变成可拦、可数的东西, 且拆成三个数不许合并**: 两个是被拦下的
   "倾向"计数; 第三个 (错配率) 要答案键才测得出来, **已随第六节砍掉**。
   因此**对外不报"幻觉率"这个比率**, 口径见第三节。
4. **复用 W4 的 runtime** (`task_type = incident_report`), 不 fork 状态机、
   不新起一套协议层 —— 与 SPEC-007 的"能力开关不许 fork 状态机"同一条理由。
5. **正面回答"既然数字全是代码算的, 那还要模型干嘛"** —— 用一次并排对照
   (同一条事故, 模板铺开的那份 vs Agent 写的那份) 摆进 README。
   原计划的 20 条评测集**已砍**, 理由见第六节。
6. **花费封顶 ¥1** (实际预计 ¥0.2, 留 5 倍余量给重跑), 护栏复用 SPEC-007
   第六节那一套。**原写 ¥8, 那是第三段两组真跑的预算, 随第三段一起作废。**
   留着它等于这道护栏永远不会触发, 与 SPEC-009 查出的
   "配额 5 条 × ¥0.60 = 全站日预算" 同形。

## 非目标 (v1 明确不做, 理由随附)

- **不做 PDF / 邮件 / 任何外部导出**。W6 已砍掉真实邮件出口; 导出是"外部世界
  看得见"的动作, 按不变量 1 它在模型能力之外, 而人手工复制粘贴不需要我写代码。
- **不做未解决事故的报告**。事故还在跑的时候事实包是会变的, 而报告一旦定稿就
  应该是那一刻的定影。要看进行中的事故有 Dashboard。
- **不做定时批量生成**。批量生成会让"人过目"这一关名存实亡 —— 一次冒出来 30 份
  没人真看。报告由人在事故详情页点一下才生成。
- **不做 LLM judge** (`CLAUDE.md` 工程约定), 判分全部确定性。
- **不做 RAG / 历史报告检索**。ADR-002 已经拒过一次, 理由未变。
- **不做报告的评测集与消融** (2026-08-22 砍, 见第六节)。评测设施这项能力 W5
  已经用 100 条、五组对照、772 个变异体证明过, 再做一套 20 条的是**同一个能力
  的重复, 规模还小一号**。
- **不做自由长文**。报告是五个字段的结构化对象, 理由见第一节。

## 一、报告是什么: 五个小节的结构化对象, 不是一篇长文

```json
{
  "summary":   "……",   // 发生了什么, 一到两句
  "handling":  "……",   // 处理过程: 谁派的、谁到的、怎么关的
  "impact":    "……",   // 影响与耗时
  "notable":   "……",   // 值得注意的一两点 (可以为空字符串)
  "suggestion":"……"    // 建议 (可以为空字符串)
}
```

每个字段是纯文本, 各自有字符上限 **200 / 300 / 200 / 200 / 200**。

**上限判在渲染之后的正文上, 不是判在占位符原文上** (2026-08-23 定)。
`{{response_duration}}` 原文 21 个字符, 渲染出来的 "1 小时 12 分" 只有 8 个 ——
判在原文上, **模型每多用一个占位符就多吃 20 个字符额度, 越守规矩越容易撞上限**,
约束方向和第三节的设计目标正好反着来。
另设一道渲染前的宽松硬顶 **800 字符/字段**, 防止模型写出一串爆炸性引用把渲染结果
撑爆 —— 它是防呆, 不是风格约束, 正常输出碰不到。

**为什么不让它写一篇长文**: 长文没法确定性判分。拆成五格之后, "该提的事实提没提"
变成集合比较, "根因写没写对"变成一个字段里的一次引用比对 —— 这正是 SPEC-007
第三节那套判分法能用上的前提。**`notable` 与 `suggestion` 允许为空**: 没什么好说的
时候硬写一句是这类系统最常见的胡话来源。

## 二、事实包: 数字不经过模型的手

事实包分两半, **因为"读一次数据库"和"纯函数"这两句话放在一起不成立**
(2026-08-23 改准措辞, 顺带满足 `CLAUDE.md` 不变量 4 "只有 services/ 层可以碰数据库"):

- `load_incident_facts(conn, incident_id)` —— **唯一碰数据库的那一半**, 一次读取,
  返回原始行, 不做任何格式化;
- `build_fact_pack(raw, *, tz)` —— **真的纯函数**, 吃上一步的原始行, 产出有序事实表。
  它连同渲染器与两道检查一起, **一行 IO 都不许有**; 这条边界由一个传递 import
  断言守着 (照 `evals/tests/test_grader_io_boundary.py` 的做法), 不靠人记得。
  **入口模块用白名单不用黑名单** (2026-08-23 改): `report_render` 只许 import
  `re / collections.abc / dataclasses / datetime / typing / zoneinfo`, 多一个就红;
  传递到的 `app.*` 模块继续用黑名单。理由是实测出来的 ——
  黑名单版本 (`asyncpg/sqlalchemy/httpx/app.db`) 挡不住 `import os` +
  `os.environ.get(...)`, 而模块开头明写着"不读环境变量", 且 **tz 显式传入的整个
  理由就是快照可复现**。声明的和执行的不是一回事, 正是本项目反复在修的那件事;
  黑名单只挡得住上次那个, 白名单挡的是下次那个。

每条事实四个字段:

| 字段 | 说明 |
|---|---|
| `id` | 语义 id, 蛇形命名, 例如 `handle_duration`、`ack_by`、`tl_3` |
| `label` | 人话标签, 例如 "处理时长" |
| `value` | 原始值 (供判分与重渲染用) |
| `text` | **已经格式化好的中文串**, 例如 "1 小时 12 分"、"生鲜区"、"Bo Wang" |

事实的六类 (v1 固定, 加类要同时补评测用例):

1. **基本**: `incident_id` / `zone` / `sensor` / `severity`
2. **时刻**: `opened_at` / `acknowledged_at` / `resolved_at`
3. **时长**: `response_duration` (开→接单) / `handle_duration` (开→解决) /
   `onsite_duration` (接单→解决)
4. **人**: `assigned_to` / `ack_by` / `cross_zone` (是否跨区派单)
5. **解决来源**: `resolved_kind` (人工 / 自动, 判据是 `resolved_by` 的前缀,
   SPEC-003 决策 4) / `resolve_policy` (自动时是哪条策略的哪一版)
6. **上下文**: `tl_1 … tl_n` (时间线逐条) / `sensor_30d_count` (这个探头近 30 天
   开过几次单) / `zone_concurrent` (同区同期还有几条未解决)

**事实包一律产全: 六类里的每一条都出条目, 一条不少** (2026-08-23 定)。
该事故没有的那一条**不是不给**, 而是 `value = null`、`text = "无此记录"`。
三个好处是连在一起的:

- **`id` 集合变成静态清单**, `E_DANGLING_REF` 从"查这次的事实包"变成"查一张固定
  的表", 判据更硬;
- **"事实不足时不许编"从叮嘱变成机制。** 无人接单时模型只能写 `{{ack_by}}`,
  由渲染器吐出"无此记录" —— 它写不出一个编造的人名, 也写不出一句
  "当时没人接单"式的、没有任何东西核对得了的自由中文;
- 验收里"无人接单的事故 → 报告里出现无此记录字样"**因此可以自动测**,
  不必靠人眼看。

缺失是常态不是边角: SPEC-003 决策 3 明写 `open → acknowledged` 跳过分配时
`assigned_employee_id` 保持为空不回填, 它的验收里专门有"未派单直接刷卡"一条。

**时刻与时长的格式化时区显式传入, 不读环境变量** (2026-08-23 定):
`build_fact_pack(incident_id, *, tz)`, 调用方给 `Asia/Shanghai`。
读环境变量会让同一份快照在不同机器上渲染出不同的时间 —— 与
"报数字必须带产生它的配置"是同一条纪律。

**时间线超过 20 条就截断**: 保留最早 5 条 + 最晚 15 条, 并多产一条事实
`tl_truncated` (`text` = "另有 N 条时间线未列入")。这样"明写截断了几条"也是机制,
不是叮嘱 —— 与上面那条同一个理由。

**截断之后, 缺口要在事实包里看得见** (2026-08-23 补): `tl_truncated` **排在
tl_5 与 tl_6 之间**, 不排在事实包末尾; 后半段的 `label` 写成"时间线末段第 N 条",
不写"时间线第 N 条"。**模型读的是 label** —— 排在末尾又都叫"第 N 条", 它会以为
tl_6 紧接 tl_5, 写出"随后第 6 条记录显示……"这种连贯叙述, 而中间实际断了 7 条。
这是"事实包不许让模型误会"的同一条纪律: id 是引用句柄可以重排, **label 是给人
和模型看的话, 不许说谎**。

**模型看得到 `text`。** 这一条要写明白, 因为它看起来与"不许产生数字"矛盾:
不给它看值, 它就没法判断哪条值得写进 `notable` (一次 4 分钟到场和一次 4 小时
到场, 该说的话是反的)。**限制不在"看", 在"写"** —— 见下一节。

## 三、约束怎么下沉: 正文里只能出现占位符

模型写 `handling` 字段时, 必须写成:

> 主管把单派给了 {{assigned_to}}, 实际到场刷卡的是 {{ack_by}}, 从开单到接单
> 用了 {{response_duration}}。

渲染时由代码把 `{{id}}` 换成该事实的 `text`。**三道检查, 前两道是 0 容忍的硬拦**:

| 码 | 判据 | 处置 |
|---|---|---|
| `E_BARE_FACT` | 正文里裸写了事实 (判据三条, 见下) | 拒收, 回 `repairing` |
| `E_DANGLING_REF` | 引用了事实包里不存在的 id | 拒收, 回 `repairing` |
| (无码) | **引用存在、但用错地方** (把"响应时长"塞进"处理时长"那句话) | **拦不住**, 只能测 |

**`E_BARE_FACT` 的判据 (三条, 2026-08-23 收窄, 缺一条这道检查就不能用)**:

1. **检查跑在剔除全部 `{{...}}` 之后的残余文本上。** 占位符自己就含数字 ——
   `{{tl_3}}`、`{{tl_12}}`、`{{incident_id}}` —— 不先剔掉, 模型每写一条时间线
   引用都被自己拦死;
2. **阿拉伯数字 0 容忍** (它是编造数字的主要载体, 中文报告正文里正常不需要它);
   **中文数字只拦"时间与时长"** —— 中文数词后面跟的是 `分钟 / 小时 / 秒钟 /
   秒 / 天` 才算, 数词与单位之间允许一个约量词 (`个 / 来 / 多 / 余`), 数词含"半",
   且**序数"第X"整体放行**。
   (2026-08-23 复核改定, 实测见 `scripts/dev/probe_bare_fact_cn.py`。初稿写的单位表
   是 `分/秒/时/天/次/条/人/区/级`, 两头都不成立:
   **误伤** —— 单字"分"/"时"拦下验收点名放行的"十分明显"、"第一时间"; 只把它们
   换成两字并不够, 同形的"第一次报警"、"这是一次跨区派单"、"一次性"照样被拦,
   而 0 容忍 + 修 2 次不过就 `failed`, 误伤直接变任务失败;
   **漏拦** —— 没有约量词, "两个小时"、"半小时"、"一个半小时"、"十来分钟"一条都
   拦不住, 而"模型自己编时长"正是这道检查存在的理由。实测: 误伤 3/9 → 0/9,
   漏拦 5/10 → 3/10。**误伤会在 repairing 里暴露出来, 漏拦不会 —— 它悄无声息**,
   所以两害相权先堵漏拦。)
3. **`text` 裸写只查专名类事实** (`assigned_to` / `ack_by` / `zone` / `sensor` /
   `resolve_policy` / `cross_zone`), 且该 `text` 长度 ≥ 2 才查。**分类类事实
   (`severity` / `resolved_kind`) 不进裸写黑名单** —— `severity` 的中文取值形如
   "一般 / 高 / 紧急", 单字"高"会让正文里任何一个"高"字触发, "一般"里还带着
   一个"一"; `resolved_kind` 的取值是"人工 / 自动", 都是日常词。
   **`cross_zone` 进黑名单**(2026-08-23 补): 它的取值"跨区派单"/"本区派单"
   不是日常词, 它就是那条事实本身 —— 与 severity 那两条不同类, 别跟着一起豁免。
   代价照实写进已知边界, 不含糊。

前两道与 ADR-007 同源: **不是靠模型自觉, 是让它物理上写不进去。**
第三道是这套机制真正的边界。它本来是那个值得报出来的比率, 但测它要答案键 ——
已随第六节砍掉。**边界照旧存在, 只是不给数**, 被问到照实说。

**三个数, 分开命名、分开报, 不许加起来报一个"幻觉率 x%"** (做法照 SPEC-007
补入 36 把注入拆三件事):

- `bare_fact_attempts` —— 想裸写事实、被拦下的次数。**它是倾向, 不是事故。**
- `dangling_ref_attempts` —— 悬空引用、被拦下的次数。同上。
- **两个都按违规项计数, 不按轮计数** (2026-08-23 定)。一轮里裸写了三处就加 3。
  按轮计会把"一处手滑"与"通篇乱写"压成同一个数 —— 那正是本项目反复在修的
  "两种性质不同的东西折叠成同一个出口" (defect-log 案例 1 / 4 / 6 同形)。
  **两个数各占 `incident_reports` 一列** (第七节), 不藏在 jsonb 里。
- `misplaced_ref_rate` —— 错配率。它要答案键才测得出来, **随第六节一起砍了**。
  **由此定死一条对外口径: 本项目不报"幻觉率"这个词。** 能说的是"模型在正文里
  写不出自由数字与专名 (语法层面拦住), 而它想写的次数被记了下来" ——
  前者是机制, 后者是计数, 两者都不是比率。**机制比比率硬, 但不许混着说。**

前两个数为 0 不能说明模型老实, 只能说明这一跑里它没试; 而它们**大于 0 恰恰是
这套设计在干活的证据** —— 所以报告里要把它们摆出来, 不要藏。

## 四、状态机与工具清单

**复用 W4 的 runtime**, `agent_tasks.task_type = 'incident_report'`。阶段序列:

```
   collecting → drafting → validating ──(有错)──→ repairing ──┐
                              │(通过)                          │ (修满 2 次仍不过)
                              ▼                                ▼
                        awaiting_review ─── (人定稿或退回) ──→ completed
                                                             failed
```

- **阶段名是新起的两个, 不是"删掉两个"** (2026-08-23 改准措辞)。W4 的实际序列是
  `parsing → discovering → compiling → validating →(有错) repairing`
  (`agent_runtime.py`); 报告这条是 `collecting → drafting → validating → repairing`
  —— 删掉 `parsing` 与 `simulating`, 并把 `discovering`/`compiling` 换名为
  `collecting`/`drafting`。**换名是故意的**, 与第五节
  "`awaiting_review` 不复用 `awaiting_approval`" 同一条理由: 报告的"收集事实"与
  策略的"查现有资源"不是一回事, 共用名字会让下一个读代码的人误解。
  `agent_tasks.stage` 这一列**没有 CHECK 约束** (`0001_initial.sql` 第 94 行),
  所以新阶段名不动迁移; 代价是 `agent_runtime.py` 加两个分支、
  `agent_prompts.py` 的阶段字典加两个键。
- **`MAX_REPAIRS = 2` 是真复用**, `agent_runtime.py` 里已经是 2, 不改常量。
- **`repairing` 修完必须回 `validating`**, 与 SPEC-002 同一条理由: 修完不验等于没修。
- **修满 2 次仍不过 → `failed`, 不是 `clarifying`。** 这是与 W4 最要紧的一处不同,
  理由见下。

**工具只有三个** (少一个工具就少一处需要论证"它为什么不会乱用"):

| 类别 | 工具 | 说明 |
|---|---|---|
| 只读 | `get_incident_facts` | 返回整个事实包 |
| 草案 | `create_report_draft` | 写五个字段, 落 `incident_reports` 一行 |
| 草案 | `update_report_draft` | 修复循环用, 就地改本任务这一版 |

**没有 `ask_clarification`。** 事故已经结了, 现场没人可问, 追问只会把任务挂住到
超时。事实不足时 (例如无人接单、时间线只有两条) 的正确行为**由第二节的机制保证,
不靠叮嘱**: 事实包一律产全, 缺失那条的 `text` 就是 "无此记录", 模型照常写
`{{ack_by}}` 即可。**它写不出编造的人名, 也写不出一句没有东西核对得了的自由中文。**
这一条直接呼应 SPEC-007 补入 39 记下的那个产品缺口 —— W5 的教训是
"用户不肯定夺时系统该怎么办"没答案, 这里提前把答案定了, 而且定成了机制。

**两个终态分开, 不折叠** (2026-08-23 定, 上图两个箭头的归属):

- 人**定稿** → 任务 `completed`, 报告 `final`;
- 人**退回** → 任务 `completed` (任务本身干完了, 是人不要这一份), 报告 `discarded`;
- **修满 2 次仍不过** → 任务 `failed`, 报告 `discarded`。

`failed` 因此**专指"模型没写对"**。把"人退回"也落 `failed`, 正是第七节第 5 条
自己反对的那种折叠 —— 评测会分不清这两件事。

## 五、报告不设审批门 (2026-08-22 拍板)

**决定: 报告只有 `draft` / `final` 两态**, 事故处理人或任何 manager 点"定稿"即可,
不写 `approvals` 记录。三条理由:

1. **风险级别不同。** 策略发布会改变系统以后的行为, 报告只是一段描述已发生事实的
   文字, 写错了改一版就是。为不同风险配同一道闸, 是把"审批"这件事廉价化。
2. **`approvals` 表是策略专用的** —— 它有 `policy_version_id` 外键, 没有一列能装
   报告 (第九节矛盾 1)。所以走审批不是"复用", 是要改表。
3. **ADR-007 那条"没有审批记录物理上插不进去"讲一次就够了**, 讲两次不会更有
   说服力, 反而稀释。

**连带定死的两件事** (它们与本条是一起拍的, 不要分开改):

- `agent_tasks.status` 用**新取值 `awaiting_review`**, 不复用 `awaiting_approval`。
  后者的语义是"等审批", 报告等的是"过目" —— 一词两义会让下一个读代码的人以为
  报告也有审批门, 与本节的决定正好相反;
- 迁移 0011 要动 `agent_tasks.status` 的 CHECK, 把 `awaiting_review` 加进去。

## 七、数据库变更 (迁移 0011)

> 号段: 原写 `0010`, SPEC-009 (部署) 先实施并占了 `0010`, 本 SPEC 顺延为 `0011`。
> 两份都写 0010 的话 Alembic 会因为多个 head 直接报错, 不会静默乱套 (ADR-006)。

1. 新建 `incident_reports`:

```sql
CREATE TABLE incident_reports (
    id bigserial PRIMARY KEY,
    incident_id bigint NOT NULL REFERENCES incidents(id),
    task_id bigint NOT NULL REFERENCES agent_tasks(id),
    body jsonb NOT NULL,            -- 五个字段, 正文里是占位符原文
    fact_pack jsonb NOT NULL,       -- 生成那一刻的事实包快照 (不重算, 见下 2)
    status text NOT NULL DEFAULT 'draft'
        CHECK (status IN ('draft','final','discarded')),
    bare_fact_attempts    int NOT NULL DEFAULT 0,   -- 想裸写事实、被拦下的项数
    dangling_ref_attempts int NOT NULL DEFAULT 0,   -- 悬空引用、被拦下的项数
    created_by bigint NOT NULL REFERENCES users(id),
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    finalized_by bigint REFERENCES users(id),
    finalized_at timestamptz
);
```

**`task_id` 与 `created_by` 都是 NOT NULL** (2026-08-23 定): 没有哪一种报告是
不带任务、不带发起人的。第六节那次并排对照里"模板铺开的那一份"**不入库** ——
它是脚本产出、直接进 README, 否则会被下面第 3 条的部分唯一索引拦住。

**两个计数列 (`bare_fact_attempts` / `dangling_ref_attempts`) 是第三节那两个数的
落点**, 按违规项累加。它们必须是列不是 jsonb: 第三节要求"摆出来不要藏",
一个要写进 README 与面试口径的数, 不该躺在一坨 json 里靠 `->>'x'` 取。

2. **`fact_pack` 存快照, 不是每次重算** —— 这条要写进列注释。事故时间线以后不会
   变, 但**算事实包的代码会变**; 不存快照, 半年后重渲染同一份报告会得到不同的
   数字, 那它就不是"当时那一份"了。与"报数字必须带产生它的配置"是同一条纪律。
3. 一条事故**同时只能有一份非 discarded 的报告**: partial unique index
   `(incident_id) WHERE status <> 'discarded'`。做法与 W2 事故去重一致 ——
   约束下沉数据库。**这是本项目第四次用这一手**: W2 事故去重、W4 的
   `agent_tasks_one_open` (同一个用户同一句话只能有一条未走完的任务)、
   SPEC-009 的花钱护栏 (超限那条 UPDATE 物理上写不进去), 加这一次。
4. `agent_tasks.task_type` **补 CHECK** `IN ('policy_compile','incident_report')`。
   现在它只有一句注释, 拼错一个字母不会有任何东西报错 (第九节矛盾 3)。
   **`stage` 列同样没有约束, 但故意不补** —— 阶段名会随能力开关增减
   (SPEC-007 的五臂就在增减它), 锁死它等于每加一个阶段就要一次迁移。
   **这个不对称要写进迁移 0011 的注释里**, 否则下一个人会以为是漏了。
6. `agent_tasks.status` 的 CHECK **是匿名约束** (0001 里内联写的, 名字由
   Postgres 生成)。要加 `awaiting_review` 必须先按名字 drop ——
   `0007_policy_lifecycle.py` / `0008_agent_orchestration.py` 里已有
   `_constraint_name()` 辅助函数专门干这事, 直接复用, 不要硬编名字。
5. 失败任务的报告标 `discarded`, 不标 `rejected` —— 与 SPEC-002 第六节同一理由:
   一词两义会让评测分不清"人退回"与"模型没写对"。

必须写 downgrade, 手写不用 autogenerate (ADR-006)。

## 八、接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/incidents/{id}/report` | `reports:draft` (operator+) | 建任务, 202 + task_id; 事故非 `resolved` 返回 422 |
| GET | `/reports/{id}` | viewer+ | 报告 + 渲染后的正文 + 事实包快照 |
| GET | `/incidents/{id}/report` | viewer+ | 取该事故当前那一份 |
| POST | `/reports/{id}/finalize` | `reports:finalize` (operator+) | 定稿 |
| POST | `/reports/{id}/discard` | `reports:draft` (operator+) | 弃稿, 允许重生成 |

**权限点是代码常量不是数据库表** (`auth_service.py` 的 `_ROLE_PERMISSIONS`),
加这两个只改那一个文件, **不需要迁移**。

**`reports:finalize` 给 operator+, 不做"事故处理人"这个行级判断** (2026-08-23 定)。
第五节原写"事故处理人或任何 manager", 但"事故处理人"是**行级归属**条件, 而本项目
现有的 RBAC 全是角色级的 —— 代码里没有任何一处做过"这一行数据是不是你的"这种判断,
落地它等于新起一套授权维度。既然本节的立论就是"报告风险低、不设审批门",
再为它引入项目里第一次行级授权是自相矛盾。**能起草的就能定稿。**

**`discard` 允许作用在 `final` 上, 权限同为 operator+**: 第五节的理由是
"写错了改一版就是", 而部分唯一索引的条件是 `status <> 'discarded'` ——
`final` 也占位, 不许弃已定稿的等于"报告一旦定稿就永远开不出第二份",
与那条理由直接打架。弃稿一律进 `audit_log`。

**去重判据是"该事故有没有未走完的 `incident_report` 任务", 不是"有没有 draft
报告"** (2026-08-23 改)。报告那一行是 `create_report_draft` 在 `drafting` 阶段才
插进去的, 按"有没有 draft 报告"判, **`collecting` 阶段连点两次会漏过去**。
命中时**返回 200 与既有 task_id**, 不报 4xx —— 与 SPEC-002 第七节
"用户明明什么都没等到, 报重复提交会让人一头雾水"一致。

已有的 `agent_tasks_one_open` 索引 (`(user_id, input_hash) WHERE status IN
('running','clarifying')`) 只挡得住**同一个用户**; **两个不同的用户同时点同一条
事故**, 会开出两个任务, 第二个跑到 `drafting` 时撞上部分唯一索引直接 `failed` ——
用户看到"任务失败"而不是"已经有人在生成了"。服务层因此必须自己查一次,
不能只靠那个索引。

## 十、验收

- 一条人工解决的事故 → 点生成 → Studio 时间线依次出现 `collecting` / `drafting`
  / `validating`, 最后停在等人过目;
- 渲染后的正文里, **每一个数字都能在事实包快照里找到出处**。**这一条要写成自动
  测试, 不是人眼逐个数**: 把渲染后正文里的每一段连续数字抠出来, 断言它出现在某条
  事实的 `text` 里。人眼数一遍这件事本身就是"判据不会翻转"的高发地带;
- **事实包一律产全**: 无人接单的事故, `ack_by` 这条**仍在事实包里**,
  `value` 为 null、`text` 为 "无此记录";
- **字符上限判在渲染后**: 造一个字段, 占位符原文超 300 但渲染后不足 300 → 通过;
  渲染后超 300 → 拒收;
- **`E_BARE_FACT` 不误伤**: 正文写"第一时间赶到"/"一般"/"人工处理" → **全部通过**
  (这三条各写一个用例, 缺一条这道检查就可能被实现成噪音发生器);
- **变异: 把模型的输出手工改成裸写一个数字** → `E_BARE_FACT`, 进 `repairing`,
  且 `bare_fact_attempts` 加一;
- **变异: 引用 `{{nonexistent}}`** → `E_DANGLING_REF`, 同上;
- 无人接单的事故 → 报告里出现"无此事实"字样, **不是空字符串, 也不是编造的人名**;
- 同一事故连点两次生成 → 200 + 同一个 task_id, 不新建任务;
- 事故未解决时点生成 → 422;
- 报告定稿后事故时间线**再变化**, 报告正文不变 (快照生效);
- 绕过应用层直接往 `incident_reports` 插第二行 `draft` → **被 partial unique
  index 拦住**;
- 人退回一份草稿 → 任务 `completed` (**不是 `failed`**), 报告 `discarded`;
  修满 2 次不过 → 任务 `failed`, 报告 `discarded`;
- 测试命名遵循 `test_<行为>__<条件>`; **`make lint` 与 CI 会跑的全部五个脚本绿**
  (`scripts/ci/` 下的 `lint.sh` / `test-unit.sh` / `test-api.sh` /
  `test-eval-smoke.sh` / `test-docker.sh`)。**`make test` 只含中间两个** ——
  只跑它等于没验, W5 为此栽过一次 (本机全绿、推上去 CI 红)。

## 已知边界 (写进代码注释, 不只写在这里)

- **定性形容词拦不住。** "很快就到场了" 里没有数字, 占位符机制对它无效。
  这套设计管的是**可核对的事实**, 管不了语气与判断。照实说, 不含糊。
- **模型看不到渲染后的样子, 渲染结果可能读起来重复或别扭** (2026-08-24,
  第一次真实生成当场撞上)。模型写的是 `{{tl_3}}`, 它不知道那条事实的 `text`
  本身就以事件名结尾, 于是接着写"转干后", 渲染出来是"传感器转干 转干后"。
  **这是占位符机制的固有代价**: 让它看不见渲染结果, 才保证它写不出自由数字;
  代价是它也没法为渲染结果润色。**不给模型看渲染预览是刻意的** —— 给它看,
  它就有了照着渲染结果反推数字的路子。照实交付, 不替它润色。
- **修复循环会让句子丢语境**: 同一次真实生成里, 初稿在 `suggestion` 里裸写
  "三十天"被 `E_BARE_FACT` 拦下, 修复稿把那几个字整个删掉, 于是
  "该传感器近三十天开单 2 次"变成了"该传感器 2 次"。**拦得住裸写数字,
  拦不住修完的句子变难读。**
- **一小时以上的时长只到分** (`_fmt_duration` 的取舍, 误差 <60 秒)。
  **不足一小时时必须带秒** —— 响应 + 到场 = 处理这三条会印在同一句话里,
  丢余数会让读的人一做加法就发现算不平。理由与实例见该函数的注释。
- **中文写的计数拦不住** (第三节判据 2 的代价, 2026-08-23 定): 中文半边只拦时间
  与时长, "开了两次单"、"到场两人"、"二十余条记录"过得去。丢得起的理由是
  **计数类事实的 `text` 本身就带阿拉伯数字** ("2 次" / "0 条" / "3 号传感器"),
  模型抄它只能抄出阿拉伯数字, 已被判据 2 前半兜住; 残留的洞只有一种 ——
  **模型主动把"2 次"译成"两次"**。同理"三分"、"一个多小时"、"好几个小时"
  这类不带标准单位的写法也漏。照实说, 不含糊。
- **序数一律放行**: "第三次报警"里的"三"拦不住 (排除"第X"是为了放行"第一时间"
  与"第一次", 两者形状相同, 按个例修一个漏一个 —— 所以按规则整体放行)。
- **`severity` 与 `resolved_kind` 这两条事实的裸写拦不住** (第三节判据 3 的代价)。
  它们的中文取值形如"一般 / 高 / 紧急"与"人工 / 自动", 都是日常词汇, 进裸写黑名单
  会把正常句子全打掉。**这是权衡不是遗漏**: 两者各只有三五个固定取值, 编造空间
  接近零 —— 模型把"高"写成"紧急"是分类写错, 不是凭空造事实, 而分类写错这件事
  与第三节第三道 (引用存在但用错地方) 是同一个已知洞。
- **"用了对的占位符但放错句子"现在没有任何东西测得出来** (第六节砍了答案键)。
  校验器拦得住编造与悬空引用, 拦不住错配。这是交付时就知道的洞, 被问到照实说。
- **事实包是一次性给全的**, 长事故 (时间线二十条以上) 会占掉可观的输入 token,
  成本随时间线长度线性涨。若超预算, 止损做法是时间线**截断并明写截断了几条**,
  不是悄悄少给。
- **429 被当成终态那笔债 (defect-log 案例 6) 对本 SPEC 同样生效** ——
  报告任务用的是同一个客户端。修它要动 W4 客户端并重跑受影响的那几组。

## 定稿决定 (2026-08-22 拍板四条, 2026-08-23 评审补七条)

- **A. 不设审批门** (方案一)。连带 `awaiting_review` 与迁移 0011 的 CHECK, 见第五节。
- **B. 20 条, 两组都跑 —— 已被 D 推翻, 保留在此是因为它记下的口径以后还用得上。**
  原定 R0 模板组不花钱、R2 出厂档约 ¥1.2。**作废的是那 20 条, 不作废的是这条纪律:
  任何比率都要带分母。** 20 条里每一条值 5 个百分点, 单看百分比会把抖动读成差距;
  README 里那次并排对照因此只说"一个例子", 一个百分比都不给。
  (顺带记下: 第六节说"两组真跑约 ¥8", 而 R0 不花钱、R2 只要 ¥1.2 —— **这两个数
  在 SPEC 内部就差了 6.7 倍**, ¥8 是起草时拍的。按 SPEC-007 补入 34 的实测口径
  反算, 一条报告任务约 3–4 次调用、¥0.06–0.08, 目标 6 的封顶因此改成 ¥1。)
- **C. `notable` / `suggestion` 允许为空。** 演示时报告看起来单薄是可接受的代价,
  硬写一句是这类系统胡话的主要来源。
- **D. 第三段 (评测集与两组对照) 砍掉**, 换成 README 里一次并排对照 (第六节);
  连带**不报"幻觉率"这个词** (第三节)。
